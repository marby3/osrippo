# オープンソース立法府 仕様書

Nov 2, 2026 · @まーびい

「オープンソース立法府」（キャッチフレーズ：なれる！国会議員！）は、一般の参加者が課題と解決策を出し合い、現行法を起点にした「もう一つの日本の法律（IF世界）」を育てていく、ブラウザで遊べる無料の立法ゲームです。この版は2026年10月24日のドラフトを清書し、ドメイン・ホスティング・公開ミラーの検討結果を反映したものです。

## 概要と設計原則

議員は上位の課題と市民の解決策を閲覧し、自分の政策づくりの参考にできます。参加者は「自分が国会議員になったら？」を、気軽に、でも真剣に体験できます。裏テーマとして、法律がいつ変わり、いつから変わっていないかを誰でも見られるようにします。

**設計原則**

1. 賛成・反対そのものには報酬を出さない。報酬の対象は「相手側から認められたこと」と「法案を良くしたこと」
2. 課題は軽く、法案は重く。投稿の重さを段階で分けてゴミを減らす
3. 扱うのは課題だけ。特定の人物を対象にしない
4. 拘束力がないので一般参加者の本人確認はしない（議員・有識者の認証は別）。bot・多重投票の対策は安価な手段を重ねる
5. 無料で始められる構成にする。Cloudflareの無料枠に収め、超えた分だけ有料プランに移る
6. 10代から60代まで、ITに詳しくない人でも使えるようにする。画面ではgit、diff、マージ、ブランチのようなIT用語を使わず、ふだんの言葉で表す（「画面で使う言葉」を参照）
7. 政治的に中立。全政党・会派に同じ条件で提供し、国会・政府の公式サービスと誤認されない表示にする

## ゲームの基本ループと用語

課題の投稿から始まり、可決された法案だけがIF世界の法令に加わります。否決された法案や、定足数に届かず廃案になった法案は課題に戻り、再提出できます。発議に届かなかった下書きは次の会期に持ち越せます。

**役割ごとにできること**

| 役割 | 課題 | 解決策 | 法案 | 質疑・答弁 | 評価 | 投票 |
| --- | --- | --- | --- | --- | --- | --- |
| 一般 | 投稿・わかる | 投稿・わかる | 起草・賛同・修正案 | 可 | 可 | 可（1票） |
| 有識者 | 同上 | 同上 | 同上 | 可＋専門家の解説 | 可 | 可（1票） |
| 議員 | 閲覧・「検討中」を付ける | 閲覧 | 閲覧 | 任意で参加 | 不可 | 不可 |

法案を書いた人が提出者になり、修正案を取り込むかを判断します。有識者の票と評価の重みは一般と同じです。議員は閲覧が基本で、希望すれば質疑や答弁に加われます。

**用語**

| 用語 | ゲーム内の意味 | 現実の国会での対応 |
| --- | --- | --- |
| 課題 | 困りごとの投稿。誰でもワンタップで「わかる」を付けられ、自然文の「解決策」を添えられる | 請願・陳情 |
| 解決策 | 課題に紐づく自然文の提案。条文を書けない人でも出せる | なし |
| 法案 | 制定・改正・廃止の3種類。条文の変更点と3つの必須欄（何を変えるか・誰が困っているか・副作用） | 法律案 |
| 発議 | 賛同者が規定数に達し、法案が正式に提出された状態 | 議員立法の発議要件（衆議院で20人以上など） |
| 委員会 | 分野ごとの審議の場。参加者は関心のある委員会に所属する | 常任委員会 |
| 会期 | 1か月単位で途切れずに続く審議期間（1〜2週目：発議、3週目：質疑・修正、4週目：採決）。終わると採決結果を確定し、可決法案と現実の改正をIF世界に反映する | 国会の会期 |
| 修正案 | 法案への変更提案。採用されると提案者が共同起草者になる | 修正案 |
| 採決 | 締切まで票数を公開しない投票。可否は有効票で決める | 採決 |
| IF世界 | 可決法案が積み重なった、架空の法律の世界 | なし |

**発議要件と定足数は割合で決めます。** 母数は、その委員会で直近の会期に何か行動した人（アクティブ参加者）です。衆議院の発議要件（20人）は定数465の約4%なので、5%はそれに近い水準です。投票は誰でもどの委員会の法案にもできるため、定足数は実際には満たしやすい値になります。運用しながら割合を見直します。

| 項目 | 初期値の案 | 最低人数 |
| --- | --- | --- |
| 発議要件 | 委員会のアクティブ参加者の5% | 3人 |
| 修正案の先議要件 | 発議要件の半分 | 2人 |
| 定足数（採決の最低投票数） | 委員会のアクティブ参加者の20% | 10人 |
| 憲法改正原案の提出要件 | 全委員会のアクティブ参加者の15% | 10人 |

**ちょうどよい参加人数の目安（1委員会・1会期あたり）**：アクティブ参加者のうち法案を書くのは5%程度、ほとんどは投票と評価だけ、という仮定からの見積もりです。

| アクティブ参加者 | ゲーム体験 |
| --- | --- |
| 30人未満 | 発議される法案が1〜2本。立場別の統計は匿名化の基準（10人）に届かないことが多い |
| 50〜100人 | 法案が数本そろい、質疑もまわる。クローズドβに向く |
| 100〜300人 | 最もよい規模。法案が5〜15本に収まり、全部に目を通せる。立場別の統計も出せる |
| 1,000人以上 | 法案が多すぎて読まれないものが増える。分野を割って小委員会に分ける |

立ち上げは委員会を1つに絞り、100〜300人を目標にします。第1委員会のテーマは「消費者保護」で、対象は消費者契約法・特定商取引法・景品表示法の3本です。参加者には、このテーマにした理由を次のように説明します。

1. **誰もが当事者**：買い物、契約、サブスクは毎日のことで、専門知識がなくても「困ったこと」を課題として書ける
2. **党派で割れにくい**：消費者と事業者の利害はあるが、与野党の対立軸にはなりにくい。初めての会期でも、議論の中身に集中しやすい
3. **全部に目を通せる大きさ**：3本合わせて約270条。法案を書く人も、変える条文の前後を読み切れる
4. **現実によく改正されている**：2017年以降、3本で計45回の改正が施行された。霊感商法への対応（消費者契約法、2023年施行）や詐欺的な定期購入の規制（特定商取引法、2022年施行）など、「現実の国会がどう変えたか」と自分たちの法案を比べられる

2回目以降のテーマは、参加者の投票（「このテーマについて話したい」）で決めます。票の集まり方は、委員会を増やすかどうかの判断にも使います。

## 課題・解決策・法案

報酬の中心は「質疑と評価」です。どちら側に投票したかはスコアに一切影響しません。

**課題**

- 投稿項目：タイトル、困っている人、具体例（200字程度）
- 「わかる」はワンタップで付けられ、取り消しもできる
- 投稿前に類似の課題を上位3件まで表示する。いちばん目立つ選択肢を「この課題に『わかる』を付けて補足を書く」にし、新規投稿はその下に置く
- 投稿後に重複が見つかった場合は、通報を受けて委員長が統合する。「わかる」の数は合算し、元の課題は統合先へ転送する
- 並び順は「わかる」の数だけで決めない。普段立場の違う層からも支持された課題を上に出す（橋渡しスコア）。投票履歴がたまるまでは「わかる」の数で並べる
- 特定の人物名を含む投稿には警告を出し、人物ではなく課題として書き直すよう促す

**課題の橋渡しスコア**：「わかる」を付けた人を、その人の直近の採決での立場（賛成が多い法案の傾向）でグループに分け、グループごとの「わかる」率の低いほうを採る。グループ分けに使う投票履歴が10人分未満なら、「わかる」の数で並べる。

**解決策**

- 課題に紐づく、自然文の解決策。条文を書けない人でも出せる
- 解決策には「わかる」と「考えが変わった」を付けられる。立場は法案ごとに持つため、評価スコアの対象は法案の質疑と答弁に限る
- 法案は解決策を引用して起草する。1つの法案が複数の解決策をまとめてもよい
- 議員ダッシュボードには、課題と一緒に上位の解決策を出す

**委員会への所属**

- 誰でも、どの委員会の法案にも投票できる
- 所属は、通知と一覧の絞り込みと、割り当て法案の抽選（所属外から選ぶ）に使う

**法案**

- 種類は3つ：制定（新しい法律を作る）、改正（既存の条文を変える）、廃止
- 起草のときは、元になった解決策を引用する
- 改正と廃止は、IF世界の最新の条文を基に条・項・号の単位で変更点を編集する
- 制定は空の法令から書き始める。法令名と第1条（目的）を必須にし、ひな形を用意する
- 1本の法案で複数の法令を扱える。新法の附則で関連法を改正する形と、「○○法等の一部を改正する法律」のような一括改正の形を認める。対象法令は5本まで
- 必須欄は3つ：何を変えるか（条文の変更点）、誰が困っているか、副作用。提出者が書く「3行要約」は任意
- 状態：下書き → 発議 → 委員会付託 → 質疑 → 採決 → 確認中（異常検知時のみ） → 可決／否決／廃案
- 下書きは会期をまたいで残る。廃案になるのは発議した法案だけ
- 発議前は提出者と賛同者だけが編集できる。発議後の撤回には提出者全員の同意が必要で、賛同の取り消しはできない
- 法案の提出は登録から一定日数後に解放する（新規アカウントの乱造対策）

**法案同士の調整**

- 同じ条文に触れる法案は、発議の時点で自動的に「関連法案」として束ね、委員会で併合審査する（質疑をまとめて行う）
- 提出者どうしで統合案を共同提出できる。統合案が発議されると、元の法案は取り下げ扱いになる
- それでも同じ会期に複数が可決した場合は、発議日の早い順に反映する。後の法案が衝突したら「要調整」として次の会期で継続審議する

## 審議・評価・修正案

**質疑と評価**

- 投稿は「質疑（質問・指摘）」と「答弁（返答）」の2種類。答弁できるのは提出者・共同提出者・賛同者で、手分けできる。それ以外の人も「補足」を書ける。似た質疑は委員長がまとめ、答弁の負担を減らす
- 参加者は法案ごとに非公開の「暫定の立場（賛成寄り／反対寄り／未定）」を持ち、会期中2回まで変えられる
- スコアになるのは、立場の違う人と「未定」の人から付いた「同意しないが筋が通っている」評価だけ。同じ立場の人からの評価はスコアに数えない
- 「考えが変わった」ボタン：読んだ人が、自分の理解を変えた投稿に付ける
- 評価の不正対策：評価した時点の立場を記録して固定する。同じ相手との相互評価はスコアに上限を設ける

**評価スコアの計算**：件数ではなく「読んだ人のうち評価した人の割合」で数え、立場「未定」の人の評価も含めます。割合なので、相手側が少数でも多数でも同じ基準で比べられます。

- 数えるのは、投稿者と立場の違う人（相手側）と「未定」の人の2グループ。同じ立場の人は数えない
- 投稿者が「未定」のときは、賛成寄りと反対寄りの割合の平均を相手側の割合とする
- 「読んだ」は、投稿が画面に一定時間表示されたか、展開された場合に数える。読んだ時点の立場で記録する
- 読んだ人が少ないと割合がぶれるので、その法案全体の平均評価率に寄せて補正する（下の式のα）
- 相手側も未定も、読んだ人が3人未満なら「評価不足」として保留し、0点にはしない
- 「考えが変わった」は割合とは別に、1件ごとに加点する

```latex
r_g = \frac{e_g + \alpha p_0}{n_g + \alpha}, \qquad \text{score} = \frac{n_{\mathrm{opp}}\, r_{\mathrm{opp}} + n_{\mathrm{und}}\, r_{\mathrm{und}}}{n_{\mathrm{opp}} + n_{\mathrm{und}}}
```

e は評価した人数、n は読んだ人数、p0 はその法案の平均評価率、α は補正の強さ（初期値5）です。

**計算例**（賛成寄り90人・反対寄り10人・未定20人の法案、p0＝0.1）

| 投稿者 | 相手側：読んだ／評価 | 未定：読んだ／評価 | スコア | 件数方式なら |
| --- | --- | --- | --- | --- |
| 多数側（賛成寄り） | 8人／2人 | 15人／6人 | 0.28 | 8件 |
| 少数側（反対寄り） | 60人／12人 | 15人／3人 | 0.19 | 15件 |

件数方式では相手側が多い少数側の投稿が有利になりますが、割合方式なら、相手側が10人しかいない多数側の投稿も公平に評価されます。

**修正案**

- 3週目（質疑と修正の期間）に、誰でも法案の条文の変更案として修正案を出せる
- 提出者が修正案を受け入れると、その場で本案に反映される（取り込み）
- 提出者が受け入れなかった修正案は、賛同者が先議要件（発議要件の半分）集まれば、4週目の採決で本案より先に採決される。集まらなければ採決されずに終わる
- 修正案が可決されれば本案に反映したうえで本案を採決し、否決なら反映せずに本案を採決する
- 採用された（取り込まれた、または可決された）修正案の提案者は、共同起草者として記録する

**会期の進行**

- 1〜2週目：発議。3週目：質疑と修正。4週目：採決と次期委員長の選挙
- 発議の締切を過ぎた法案は、次の会期の審議に回る
- 会期の切り替えは日本時間の0時。会期の長さは設定値にする。開発環境では数分で1会期を回せるようにする

## 採決と投票の公正さ

**採決**

- 投票画面には変更点の一覧（あれば3行要約も）を必ず表示する。各変更の条文を開いて読むかは任意。棄権は、変更点の一覧を開いてからできる
- 締切まで票数は非公開。締切後に結果と立場別の分布を公開する
- 定足数に届かなければ廃案
- 可決要件は有効票の過半数。憲法改正は通常の会期とは別の特別イベントとして行う
- 可決した法案はIF世界に反映され、以後の法案の基になる
- 議員アカウントは投票できない

**投票の公正さ**：組織的な動員や多重アカウントで「IF世界で〇〇が可決された」という結果を作られ、政治的に利用されるのを防ぎます。本人確認はしない方針のまま、安価な対策を重ねて、動員にかかる手間を大きくします。

**投票資格（選挙人名簿の考え方）**

- 会期が始まる前日までに登録し、それまでに一定の参加（課題への「わかる」、法案の閲覧など）をしたアカウントだけが、その会期の採決で有効票を持つ
- 会期の途中で作られたアカウントの票は「参考票」として別に数え、可否の判定には使わない
- 投票のときにもbot対策（Turnstile）を通す

**割り当て法案（くじ引き審査）**：興味のある法案だけに投票する人を、可否の判定から外すための仕組み。

- 会期ごとに、各参加者へくじで法案を割り当てる（初期値3本）。所属している委員会以外の法案から選ぶ
- 割り当てられた法案すべてに投票（または棄権）してはじめて、その会期の自分の票がすべて有効票になる
- 割り当てを済ませていない人の票は参考票として扱う
- 割り当て分は3行要約と変更点の一覧だけで判断できるようにし、負担を抑える

**異常の検知と結果の表示**

- 新しいアカウントの急な流入、同じ回線からの集中、同じ並びの投票の連続などを検知したら、その法案を「確認中」にして結果の公開を保留し、委員長と運営が確認する。経過はモデレーションログで公開する
- 「確認中」の法案は、結果ページに「確認中」と表示し、確定するまでIF世界に反映しない。確定が次の会期にずれ込んだ場合は、確定した時点で反映する
- 結果ページと共有用の画像には、有効票と参考票の内訳と、「ゲーム内の結果であり、世論調査ではない」という表示を必ず入れる
- 有効票と参考票で可否が逆になった場合は、そのことを目立つように表示する

**限界**：本人確認をしない以上、時間をかけて作られた多重アカウントは完全には防げない。名簿の基準日と割り当て法案で、動員の手間を大きくすることを狙う。

**将来の拡張：マイナンバーカード認証（任意）**：自前で公的個人認証を使うには主務大臣の認定が要るが、認定なしで使える道が2つある。

- デジタル庁の「デジタル認証アプリ」：認証APIは無償。利用規約上の「民間事業者」には事業を行う個人も含まれる。デジタル庁との事前準備契約と接続確認が必要
- プラットフォーム事業者（認定を受けた事業者、2026年6月時点で28社）に確認業務を委託する。有償
- 導入する場合も任意の追加認証にとどめ、「カード認証済み」の票を結果に別枠で表示する。参加の条件にはしない（カードを持たない人や、政治的なサービスで使うことに抵抗がある人を締め出さないため）
- マイナンバー（個人番号）そのものは取得・保存しない。使うのはカードの電子証明書だけ

## 憲法改正・委員長・実績・統計

**憲法改正イベント**

- 憲法改正原案は、提出要件（全委員会のアクティブ参加者の15%）に達すると通常の採決には進まず、次回イベントの候補になる
- イベントは不定期に開く（初期は年1〜2回の案）。開催前に告知とカウントダウンを出す
- 流れ：憲法審査会（全委員会合同の質疑）→ 発議の採決（3分の2以上で発議）→ 国民投票（全参加者による投票、過半数で成立）→ 結果発表
- 成立した改正はIF世界の憲法に反映し、「IF世界の憲法改正の歴史」として専用ページに残す
- イベント中も通常の会期は止めずに続ける

**委員長の選び方**：運営は選任に関与せず、現実の国会と同じく選挙で選ぶ。

- 次の会期の委員長は、前の会期の4週目に、委員会の参加者による選挙で決める。立候補制。会期が始まる時点で委員長が決まっているので、選挙が審議に影響しない
- 立候補できるのは、選挙をする会期にその委員会で活動し、実績が一定以上ある人
- 初回の会期と新しく作った委員会では委員長を置かず、運営が「事務局」として最小限の議事整理と通報対応だけを行う。対応はモデレーションログで公開する
- 任期は1会期、連続して務められるのは2会期まで（固定化を防ぐ）
- 次点の2〜3人を理事とし、委員長を補佐する
- 参加者の一定割合の署名で解任動議を出せる。委員長が一定期間何もしない場合は、理事が代行する
- 委員長の仕事：質疑の整理、通報の一次対応、類似課題の統合、「確認中」法案の確認

**参加者の実績**

- 実績は「評価スコア（相手側と未定の人からの評価）」「考えが変わった」「採用された修正案」「可決法案の起草」から計算する
- 実績は委員長選挙の立候補資格に使う
- 賛否の傾向は実績に一切影響しない

**統計の公開**：統計は積極的に公開し、それ自体を楽しめるページにする。

- 法案ごとの賛否と、暫定の立場が会期中にどう動いたか。タイムラプスのように再生できる表示にする
- 「考えが変わった」が多く付いた論点
- 立場の違う層からも支持された法案（橋渡しスコア）の順位
- 委員会ごとの賛否の割れ方と、投票傾向の匿名マップ（似た投票をする人の集まりを点の雲で表示）
- 同じ課題に対して、現実の国会とIF世界がどう違う対応をしたか

**法案の橋渡しスコア（最初の版）**：法案ごとに「賛成寄り」と「反対寄り」の2グループに分け、支持率の低いほうを採る。匿名マップは会期終了後にまとめて計算する。

**匿名化の基準**

- 個人の投票は公開しない。10人未満の区分は表示しない
- 委員会×立場×登録時期のように、組み合わせると個人が絞れる切り口は提供しない
- 本人は自分の投票履歴をいつでも見られ、削除できる。削除しても、公開済みの集計値は変わらない
- 自分の投票記録を任意で公開できる（実在の議員の投票記録のような遊び方）。初期設定は非公開

**通知・検索・共有**

- 通知はアプリ内のみ（メールは送らない）：自分の法案の進捗、「考えが変わった」が付いた、採決の開始、委員長選挙
- 法令名、条文、課題、解決策、法案を全文検索できる
- 法案、採決結果、統計ごとにSNS共有用の画像を自動で作る
- 法令ビューアに「今日の条文」（長く変わっていない条文など）を出し、毎日来る理由を作る

## 法令データとブランチ

法令は条・項・号の単位で版を管理し、「現実」と「IF世界」の2つのブランチを持たせます。IF世界は1か月の会期を途切れずに回し、現実の改正は会期が終わるたびにまとめて反映します。

**取得元**：[e-Gov法令API Version2](https://laws.e-gov.go.jp/file/法令APIバージョン2リリースのお知らせ.pdf)（デジタル庁、2025年3月公開）。特定時点の条文、改正履歴、廃止法令を取得できる。時点を指定した取得は平成29年4月1日以降のデータに限られる。

**ブランチ**

- 現実ブランチ：APIから毎日同期し、現実の改正を自動で取り込む
- IF世界ブランチ：サービス開始日の現実ブランチから分岐する。可決法案と、会期終了時に取り込む現実の改正が積み重なる

**表示機能**

- 条文ごとの改正履歴と、最終改正日からの経過年数（「何年変わっていないか」）
- 任意の2時点、または現実とIF世界の間の変更点
- IF世界にしかない条文、現実にしかない改正の一覧

**条文の構造**

- 条・項・号ごとに、番号とは別の内部IDを振る。現実で条番号や号番号がずれても版を追跡できる。前後の版の対応は本文の似ている度合いで付け、似ている度合いが低い対応は「対応の確認待ち」として運営が確定する
- IF世界で条を足すときは、繰り下げをせず枝番方式（第3条の2）にする
- 削除された条は「削除」として残す。既存の法令の附則と別表は表示のみとし、編集対象にしない（新法の附則は法案で書ける）

**改正の日付**：施行日を基準にする。公布済みで未施行の改正は「施行予定」として別に表示する。

**2017年4月より前の履歴**：時点を指定した条文は2017年4月以降しか取れないため、2段階で補う。

- 法令単位：現行条文の附則には、その法令を改正した法令の番号と日付が残る。これと国立国会図書館の[日本法令索引](https://hourei.ndl.go.jp/)（1886年以降の改正経過を収録）を突き合わせ、30年以上さかのぼる改正年表を作る
- 条単位：2017年4月1日時点で効力のあった版は取得できるので、それ以降に変わっていない条は「この版（施行日）から変更なし」と表示する。それより前の変更は、後のフェーズで改正法の「改め文」を解析し、六法から順に補う（優先度は低い）
- 外部サイトから自動で集める前に、各サイトの利用条件を確認する

**現実の改正の取り込み（リベース）**

- 現実ブランチは毎日同期するが、IF世界への反映は会期終了時にまとめて行う。会期中にIF世界の条文が勝手に変わることはない
- 会期終了時の処理順：採決の締切 → 可決法案の反映 → その会期中の現実の改正を反映 → 衝突の検出 → 次の会期の開始
- IF世界で既に変えた条文と重なった場合は「衝突」とする。IF世界側の条文を残し、次の会期の委員会に調整の議題として自動で出す
- IF世界に「現実から取り込んだ改正」の一覧ページを設け、いつ・どの改正を反映したか、どれが衝突したかを見られるようにする

**対象とする法令の階層**：最初は第1委員会のテーマに関係する数本の法律から始め、最終的に憲法・六法まで広げる。条例は余力があれば扱う。

| 階層 | 取得元 | ゲーム上のルール |
| --- | --- | --- |
| 法律（六法を含む） | e-Gov法令API | 標準の発議要件、過半数で可決 |
| 憲法 | e-Gov法令API | 特別イベントとして実施。3分の2以上で発議し、全体投票で可決 |
| 条例 | 自治体ごとの例規集（e-Gov法令APIの対象外） | 優先度は低い（なくてもよい）。実施する場合は自治体ごとに「地方議会」を設ける |

条例は自治体ごとに公開形式が違い、APIのように一括では取得しにくい。余力があるときに1自治体で試す程度にとどめる。

**公開ミラー（GitHub）**：会期ごとに、確定したIF世界の法令を1条1ファイルのリポジトリとして書き出し、GitHubで公開する。Giteaなどの自前ホストは、保守の手間と攻撃対象が増えるので使わない。

- ライセンスはCC BY。法令本文は著作権の対象外（著作権法13条）なので、そのまま載せられる
- 参加者が書いた法案と解決策は、利用規約でCC BYでの公開に同意を得る
- CC BYの表示義務と匿名化がぶつからないよう、クレジットは「オープンソース立法府 投稿者一同」にまとめる（CC0にする案とあわせて弁護士に確認）
- ユーザー名など個人を特定できる情報は入れない。gitの履歴は後から消しにくいため、公開するのは法令テキストと匿名の集計だけにする
- 利用者がリポジトリを見る必要はない。画面に出す変更点は、サービス本体がDBの版から計算する

## 議員・有識者向け機能と認証

議員の負担は「見る」と「たまに反応する」だけに抑えます。最初に見せるのは、フェーズ1の法令ビューアとフェーズ2の課題一覧です。

- **議員アカウント**：事務所からの申請で認証バッジを付ける。本人確認を手作業で行うのはここだけ。できるのは閲覧・質疑・答弁で、投票と評価はできない
- **ダッシュボード**：ステータス（課題／解決策あり／法案化／発議済み／可決）ごとに分け、分野とステータスで絞り込める。各段階で、橋渡しスコアの高い解決策と立場別の分布を見られる
- **「拾った」ステータス**：課題に「検討中」「質問で取り上げた」を付けられる。議員が会議録のURLを添えて自己申告し、URLが実在するかだけを機械で確認する
- **答弁イベント**：議員が特定の課題や法案に回答する回を告知して開く
- **選挙期間中の停止**：国政選挙と、対象にしている自治体の選挙では、公示・告示日から投票日まで議員の機能（答弁、「拾った」ステータス、議員名の表示）を止める。一般参加者のゲームは続ける。選挙日程は運営が事前に登録し、自動で切り替える
- **中立性**：全政党・会派に同じ条件で提供する。特定の政党の広告や表示順の優遇はしない

**有識者アカウント**：研究者、弁護士、実務家などの専門家が、専門性を示したうえで参加できる。専門性は見せるが、権威で議論を決めない設計にする。

- 1人1票と評価の重みは一般ユーザーと同じ
- 法案に「専門家の解説」を付けられる。解説は法案ページの別欄に表示し、評価スコアの対象にしない
- 実名で出すか、肩書と専門分野だけにするかは本人が選ぶ

**認証の方法**

| 種類 | 確認の方法 | 表示 | できること |
| --- | --- | --- | --- |
| 一般 | なし（OAuthログイン） | 表示名 | すべての参加機能 |
| 有識者 | 所属機関のドメインのメールで確認する。または公開プロフィール（researchmap、所属機関の教員ページ、自分のサイトなど）に確認コードを置いてもらう。弁護士などの資格者は公的な名簿と手作業で照合する | 「有識者」バッジと専門分野 | 一般と同じ＋専門家の解説 |
| 議員 | 事務所の公式連絡先に手作業で確認する | 認証バッジと氏名 | 閲覧・質疑・答弁のみ |

- 認証バッジは、未認証のアカウントと見た目ではっきり区別する（なりすまし対策）
- 認証は1年ごとに更新し、肩書を失ったら外す
- 認証の付与と取り消しは、モデレーションログと同じく記録して公開する
- 有識者が選挙に立候補した場合は、議員と同じく選挙期間中の停止の対象にする

## 不正・荒らし対策とモデレーション

本人確認は行わず、無料か安価な対策の組み合わせで済ませます。票の動員は、票数ではなく橋渡しスコアで並べることで効果を薄めます。

| 脅威 | 対策 | 運用コスト |
| --- | --- | --- |
| botの登録・自動投票 | 登録・投稿・投票時にCloudflare Turnstile（無料） | 低 |
| 多重アカウント | OAuthログイン必須、法案提出は登録から一定日数後、IP・端末ごとの上限 | 低 |
| 連投・スパム | アカウント・IPごとのレート制限 | 低 |
| 個人攻撃・弾劾目的の投稿 | 人物名の検出で警告、通報が一定数で自動非表示、委員長が確認 | 中 |
| 組織的な票の動員 | 投票資格の基準日、割り当て法案、異常検知と「確認中」。並び順は票数でなく橋渡しスコア、票は締切まで非公開 | 低 |
| 重複・低品質の法案 | 類似提示、発議要件、定足数に届かない法案の廃案 | 低 |
| 評価の自作自演 | 評価時の立場を固定、立場変更の回数制限、同じ相手との相互評価に上限 | 低 |
| 実在の人物への誹謗中傷 | 通報・削除依頼の窓口と対応手順、発信者情報開示請求に備えたログ保存 | 中 |

**モデレーションの方針**

- ガイドラインを公開する：対象は課題と条文だけ、人物攻撃と差別は削除
- 削除や非表示には理由を記録し、本人に通知する
- 運営と委員長の対応（削除・非表示・統合）は、個人情報と通報者を伏せてモデレーションログとして公開する。運営の恣意性を疑われないための仕組み
- 異議申し立ての窓口を設ける
- 投稿は書式を限定したテキストとし、表示するときに無害化する（XSS対策）

## 技術構成

本番はCloudflareのサービス（Workers、D1、R2など）で動かし、自宅サーバー（Minisforum MS-R1）は開発・検証と重いバッチ処理に回します。政治を扱う投票サービスは攻撃やアクセスの急増に遭いやすく、停電や回線障害で会期中の投票が止まるのも避けたいためです。外部の有料APIは使わず、TypeScriptで統一します。

サービス本体はCloudflareの中で完結するので、自宅サーバーが止まってもサービスは止まりません。自宅サーバーは法令データの取り込みや公開ミラーの書き出しを担い、結果をD1・R2・GitHubに送ります。

| 層 | 採用案 | 理由 |
| --- | --- | --- |
| 画面＋サーバー | SvelteKit（TypeScript）をCloudflare Workersで動かす | 1つのリポジトリで画面とAPIを書ける。サーバーの保守が要らず、アクセスが増えても自動で広がる |
| DB | Cloudflare D1 | Workersから直接使え、無料枠が大きい。分析が重くなったらPostgreSQLの追加を検討する |
| ORM | Drizzle | D1に対応し、型が付き、マイグレーションが素直 |
| 認証 | Better Auth（OAuthのみ） | パスワードを預からない |
| bot対策 | Cloudflare Turnstile | 無料 |
| 変更点の表示 | jsdiff（文字単位） | 条文の差分を色と記号で表示 |
| 全文検索 | D1のFTS5 | 3文字以上はtrigram、2文字は文字bigramの2つの表で引く。行は項・号ごと（フェーズ0で確認） |
| 類似検索 | Cloudflare Vectorize＋多言語の埋め込みモデル | 埋め込みはWorkers AI（bge-m3かplamo-embedding-1b）で作る。無料枠で足りる見込み |
| 定期処理 | Cron Triggers＋Queues | 会期処理、通知、集計 |
| 重いバッチ | 自宅サーバー（MS-R1、Docker Compose） | 法令の取り込みと版の作成、公開ミラーの書き出し。止まってもサービスは止まらない |
| ファイル・バックアップ | Cloudflare R2 | 共有用画像、法令の生データ、DBのエクスポート |
| 公開 | Cloudflare（DNS・プロキシ・WAF） | DDoS対策が最初から効く |
| 公開ミラー | GitHub | 法令の版とIF世界の履歴をCC BYで公開 |

| テーブル | 役割 |
| --- | --- |
| users | アカウント、登録日、実績スコア、認証の種類（一般／有識者／議員）と更新期限 |
| committees | 委員会（分野）と所属 |

| bill\_relations | 関連法案と統合案 |
| cosponsors | 賛同者・共同起草者 |

| posts / post\_views | 質疑・答弁・補足と、評価スコア用の閲覧記録 |

| law\_branches / law\_versions | 法令のブランチと、条単位の版（内部ID） |
| real\_amendment\_imports | 現実の改正の取り込み履歴と衝突 |
| election\_schedules | 選挙期間（議員機能の自動停止用） |
| reports / moderation\_logs | 通報と、公開するモデレーションログ |

（図「システム構成 · Cloudflare・自宅サーバー・外部サービス」は仕様書ドキュメントにあります）

利用者からのアクセスはすべてCloudflareの中で処理します。自宅サーバーは法令の版をD1とR2に送り、公開ミラーをGitHubに書き出すだけなので、止まっても会期や投票には影響しません。

## ドメイン・URL・メール

**ドメイン**

- 看板用：オープンソース立法府.jp（Xserverドメインで取得、更新料1,298円/年）
- 正規：英数字の.jp（候補：osrippo.jp）。リンクの共有、メール、APIで使う
- .jpはCloudflare Registrarで扱えないため、取得は国内のレジストラで行い、ネームサーバーをCloudflareに向ける。レジストラのDNSやサーバーは使わない
- 「kokkai」「shugiin」など、国の公式サイトと誤認されやすい名前は避ける

**URLの設計**

- システムが出すリンクは、すべて正規ドメインと英数字のパスにする（例：osrippo.jp/kadai/123）
- 日本語ドメインは正規ドメインへ301で転送する。日本語のパス（/課題/123）が来たら、Workerで英数字に読み替えて転送する
- ページには canonical で正規URLを指定し、重複コンテンツ扱いを避ける
- 画面に出す文字は日本語にする（パンくずの「課題 › #123」など）
- パスの単語は最初に一覧で決めて固定する（ローマ字の綴りの揺れを防ぐ）

| 画面での言葉 | パス（案） |
| --- | --- |
| 課題 | kadai |
| 解決策 | kaiketsu |
| 法案 | houan |
| 会期 | kaiki |
| 委員会 | iinkai |
| 法令 | hourei |
| 統計 | toukei |

**メール**

- メールアドレスは正規ドメインで作る。日本語ドメインのアドレスは対応していない環境が多いので作らない
- 受信：Cloudflare Email Routingで、運営専用のGmailアカウントに転送する。個人のGmailと分け、運営を引き継げるようにする
- 送信：運営専用Gmailの「他のアドレスからメールを送信」にResendのSMTPを設定する
- 通知はアプリ内のみの方針なので、システムからのメール送信は当面行わない。必要になったら、送信専用のサブドメイン（例：notify.osrippo.jp）からResend APIで送る
- SPFとDKIMを設定し、DMARCは p=none で始めて、問題がなければ p=quarantine に上げる
- 日本語ドメインには、メールを使わないことを宣言するレコードを入れる（SPF「v=spf1 -all」、DMARC「p=reject」、Null MX）
- 運営メンバーが増えたり任意団体化したりしたら、Google Workspaceへの移行を検討する

## 実装手順

まずログイン不要の「法令ビューア」を作り、そこにゲームの機能を積み上げます。フェーズ1だけでも単独で公開でき、議員に見せられます。

1. **フェーズ0：検証**
   - 法令API Version2から対象の法令を取得し、条単位で保存して変更点を表示できるか確かめる
   - D1で日本語の全文検索（FTS5）が実用になるか、法令の取り込みと会期処理がWorkersの実行時間の制限に収まるかを確かめる
   - 第1委員会のテーマを決める（決定：消費者保護）
   - 完了条件：2つの時点の変更点が画面に出る（2026-11-02 完了。結果はタブ「フェーズ0 検証結果」）
2. **フェーズ1：法令ビューア**
   - 改正履歴、「何年変わっていないか」、時点比較を表示する
   - 完了条件：対象法令の履歴がすべて閲覧できる
3. **フェーズ2：課題・解決策と「わかる」**
   - 課題と解決策の投稿、ログイン、Turnstile、レート制限、類似課題の提示と統合、通報、全文検索
   - 完了条件：課題の投稿から非表示処理まで一通り動く
4. **フェーズ3：法案と会期**
   - 改正・廃止の変更点の編集、新法の制定、必須3欄、割合で決まる発議要件、1か月の会期と4週の進行
   - 完了条件：下書きから発議、廃案までの状態遷移が動く
5. **フェーズ4：審議と採決**
   - 質疑・評価スコア・「考えが変わった」、修正案の先議、関連法案の併合審査、委員長選挙、アプリ内通知、採決（投票資格、割り当て法案、異常検知と「確認中」を含む）、IF世界への反映、会期終了時の現実改正の反映と衝突表示
   - 完了条件：1本の法案が可決され、IF世界の条文が変わる
6. **フェーズ5：議員ビューと統計ページ**
   - ステータス別の議員ダッシュボード、有識者の認証と専門家の解説、答弁イベント、選挙期間中の自動停止、統計ページ、公開ミラーの書き出し
   - 完了条件：議員アカウントで課題に「検討中」を付けられる
7. **フェーズ6：クローズドβから一般公開**
   - 開始時にWorkersを有料プラン（月$5〜）に切り替える。1委員会・50〜100人で1会期まわし、発議要件や定足数の割合を調整する。負荷試験もここで行う
   - 「公開前の安全策」の必須項目と公開時項目を済ませる
   - 完了条件：1会期を通して大きな不具合が出ない
8. **フェーズ7：法令の階層を広げる**
   - 六法全体 → 憲法改正イベント → 余力があれば条例（1自治体で試す）の順に広げる
   - 完了条件：憲法改正イベントを1回開催できる

**開発の進め方**

- Claude Codeで機能単位に開発する
- 会期の長さを設定値にし、開発環境では数分で1会期を回す。シミュレーション用のbot参加者を用意し、発議から採決、反映までを自動で流せるようにする
- 主要な流れ（課題投稿 → 解決策 → 発議 → 採決 → 反映）はPlaywrightのE2Eテストで守る
- GitHub Actionsでテストを回し、wranglerでCloudflareにデプロイする。バッチ用のDockerイメージはARM64でビルドする

## 運用・費用・規模

機械的な作業はほぼ自動化できます。いちばん重い継続負担はモデレーションなので、委員長の仕組みで分散させます。

| 項目 | 内容 | 頻度 |
| --- | --- | --- |
| 法令同期 | 自宅サーバーがAPIから改正履歴を取得してD1に取り込む。失敗したら通知 | 毎日 |
| 会期処理 | Cron Triggersで、採決の締切、可決法案の反映、現実の改正の反映 | 毎日 |
| 公開ミラー | 会期終了後にIF世界の法令をGitHubに書き出す | 会期ごと |
| バックアップ | D1のタイムトラベル（過去の時点への復元）に加え、定期的にエクスポートしてR2に保存する。復元手順を実際に試す | 毎晩／月1回 |
| 監視 | 本体はCloudflareの分析とアラート。自宅サーバーのバッチは死活監視（Uptime Kumaなど）と、同期が止まったときの通知 | 常時 |
| 依存関係の更新 | Dependabotの更新PRをテストが通れば適用 | 週1回 |
| モデレーション | 通報キューの確認、ガイドラインの改訂 | 毎日〜週数回 |
| パラメータ調整 | 発議要件、会期の長さ、定足数を参加人数に合わせて見直す | 会期ごと |
| 選挙日程の登録 | 国政選挙と対象自治体の選挙の公示・告示日と投票日を登録する | 選挙ごと |
| 認証の更新 | 議員・有識者の認証を1年ごとに確認する | 年1回 |

**API仕様変更への備え**：法令APIを扱う処理を1つのモジュールに閉じ込め、取得した生データもR2に保存しておく。仕様が変わっても、そのモジュールだけを直せば済む。

**費用**：ドメインは「オープンソース立法府.jp」（更新料1,298円/年）と英数字の.jpの2つ。Workersはフェーズ6（クローズドβ）の開始時に有料プラン（月$5〜）に切り替える。大きな法令の変更点の表示や会期終了時の処理が、無料プランのCPU時間（1回10ms）に収まらないため（フェーズ0で測定）。それまでは無料プランで開発する。D1、R2、Email Routing、Workers AI、Resendは無料枠に収める想定で、超えたら有料プランに移る。

**さばける規模**：Workersはアクセスに応じて自動で広がるので、処理能力や自宅回線が上限になることはない。上限になるのはプランに含まれる量（Workersのリクエスト数、D1の読み書き量など）で、超えたら従量課金で広がる。

**見直しの基準**：D1の使用量がプランに含まれる量の8割を超える月が続く、投票データの分析が遅くなる、のどちらかが起きたら、有料プランやPostgreSQLの追加を検討する。実際の使用量はフェーズ6の負荷試験（k6など）で測る。

**アカウント削除**：本人が削除したら個人データを消す。投稿は「退会したユーザー」として残し、法案の履歴は壊さない。

**運営体制**：個人運営で始める。運営費の負担を感じた時点で任意団体化を検討する。

## 公開前の安全策

政治を扱うサービスは、なりすまし、嫌がらせ、動員の標的になりやすいので、一般公開（フェーズ6）の前に次を済ませます。

| 優先度 | 対策 | 内容 |
| --- | --- | --- |
| 必須 | WHOISの登録者名 | .jpは登録者名が公開されるのが原則。登録者名を非表示にできるか、レジストラで確認する |
| 必須 | 2段階認証 | Cloudflare、GitHub、Xserver、Resend、運営用Gmailのすべて。できればパスキーにする |
| 必須 | 非公式であることの明記 | 全ページのフッターに「国会・政府とは無関係の非公式サービスです」と表示する |
| 必須 | Turnstileとレート制限 | 登録・投稿・投票にかける |
| 必須 | バックアップの復元試験 | 実際に復元できることを一度確かめる |
| 公開時 | 連絡先 | 規約などに出す連絡先は運営用メールとバーチャルオフィスの住所にし、自宅住所は出さない |
| 公開時 | SNSのアカウント名 | X、Bluesky、Instagram、YouTubeで、なりすまし防止のために先に取得する |
| 公開時 | 認証バッジ | 議員・有識者のバッジを、未認証のアカウントと見た目で区別する |
| 公開時 | 削除依頼の窓口 | 実在の人物への誹謗中傷に備え、通報・削除依頼の窓口と対応手順を用意する |
| 公開時 | ログの保存 | 発信者情報開示請求に備えてアクセスログを保存する。期間は弁護士に確認する |
| 公開時 | 利用規約・プライバシーポリシー | 弁護士の確認を済ませて掲載する |
| 余裕があれば | 商標 | 「オープンソース立法府」の商標登録を検討する |
| 余裕があれば | 障害時の告知 | 障害やインシデントのときの告知先と手順を決める |
