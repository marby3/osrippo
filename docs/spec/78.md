# アプリ内通知（設計書）

Issue #78。マイグレーションがあり、会期の処理と多くの書き込みの経路に関わるので Careful。決定は Issue #63（通知の中身は決定にない）。仕様は [docs/spec.md](../spec.md) の「通知・検索・共有」（通知はアプリ内のみ。自分の法案の進捗、「考えが変わった」が付いた、採決の開始、委員長選挙）と「モデレーションの方針」（削除や非表示には理由を記録し、本人に通知する）。画面の案は `PcHeader`・`SpTop` のベルだけで、一覧の案はない。

次のことは仕様書に定めがないので、この Issue の受入基準で確かめる（STOP 1 で確認する）。

## 決めたこと

1. **2つの作り方**：
   - **行を書くもの**：`notifications` の行を、きっかけの操作のあとに入れる。1人か少数に届くもの
   - **時刻から求めるもの**：読むときに求め、行を書かない。全員に届くものと、時刻で進むもの（進みを書き込んでいないので、動くきっかけがない。docs/spec/50.md）。いまの会期の分だけ。全員分の行を書かないので、Cron に頼らず、短い会期でも動く

2. **表**（`drizzle/0022_*.sql`。新しい表だけ）：
   - `notifications`：`id`（自動採番）、`user_id`（外部キー）、`kind`、`target_id`（整数。法案、課題、解決策、投稿の番号。なければ 0）、`ref_id`（整数。同じ対象に何度も届くものを分ける。なければ 0）、`created_at`。UNIQUE（`user_id`, `kind`, `target_id`, `ref_id`）。索引（`user_id`, `created_at`）。`kind` に CHECK は付けない（種類を足すたびに表の作り直しになる。値は `NOTIFICATION_KINDS` の型で絞る）
   - `notification_reads`：`user_id`（主キー）、`read_at`。一覧を開いた時刻
   - 本文は持たない。読むときに `kind` と題名から作る（題名の変更に追従し、文言を変えられる）

3. **何度走っても1件**：入れる文は `INSERT ... SELECT ... ON CONFLICT DO NOTHING`。`ref_id` は次のとおり：
   - 共同提出者の申し出と抜ける：`bill_cosponsors.id`
   - 撤回の同意を求める：版（発議し直すと、また届く）
   - 直された：新しい版
   - 非表示、表示に戻す、統合：その時刻（非表示と表示に戻すを繰り返しても届く）
   - 当選と解任：任期の会期の始まりの時刻
   - 取り下げ：`chair_candidates.id`
   - 「考えが変わった」：0（付け外しを繰り返しても1回だけ）

4. **通知に失敗しても元の操作を失敗させない**：`notifications.ts` の入れる関数は失敗をログに出して受け止める。元の操作は終わっているので、これで利用者に失敗を返さない。例外は、同じ `db.batch` に入れる2か所（当選は確定と一緒に、取り下げは票を消す文と一緒に。票を消したあとでは誰に届けるか分からない）。batch の中は builder（`db.run` は本物の D1 でだけ落ちる）

5. **会期の結果**（`notifyBillOutcomes(db, sessionKey, now)`）：`bill_results` と `vote_reviews` と `bill_adjustments` の今の状態から、届けるべき行を1つの関数で入れる。結果を書く処理の中には入れない（結果を書いたあとで失敗すると、次の実行で結果の行があるので飛ばされ、通知を失う）。呼ぶのは `settleSession` の最後（反映のあと）と `decideReview` の最後。今の状態から求めるので、途中で失敗しても次の実行で届く
   - 確認の行が `open` のあいだは「結果を確認している」だけを入れ、可決か否決かを出さない（`noted` は確認の行がないのと同じ）
   - `confirmed` は結果を入れる。`voided` は「無効」を入れる
   - 法案は提出者と共同提出者（`accepted`）に。`bill_adjustments` の行があれば「直す必要がある」も入れる

6. **発議のあとのぶつかり**（`notifyConflicts(db, now)`）：`runSessionEnd` の最後（取り込みのあと）に毎日。結果の出ていない発議済みの法案について、反映のときと同じ判定（`conflictOf`。自分自身を除く）で、ぶつかる法案の提出者と共同提出者に入れる。1本につき1回。失敗しても残りを続け、`causes` に積む

7. **時刻から求めるもの**（`timedNotices(db, userId, now, minutes)`）：返す項目の時刻は次のとおり。`採決が始まった`と`選挙が始まった`は `session.voteAt`、自分の法案の`質疑が始まった`は `session.deliberationAt`、`採決が始まった`は `session.voteAt`（その会期に採決する法案だけ。`inVote`）、`代行できる`は委員長の最後の操作（なければ任期の始まり）に7日を足した時刻。`now` より前のものだけ返す。解任された任期には代行の項目を出さない（解任の通知が行で届く）

8. **既読**：`notification_reads.read_at` より後の項目が未読。行がなければすべて未読。**一覧を開くと全部既読になる**（開いたときの未読の印は、開く前の時刻で出す）。項目ごとの既読は持たない。入口のリンクは先読みしない（`data-sveltekit-preload-data="off"`。先読みで既読にならないように）

9. **画面** `/tsuchi`（`noindex`。ログインが要る）：新しい順に50件ごと（「次のページ」は `/houan` と同じ）。時刻から求める項目は1ページ目に混ぜて並べる。各項目は文、日時、未読の印（色だけで示さず「未読」の文字）、リンク。リンク先は法案のページ、結果のページ、質疑のタブ、課題のページ、解決策の一覧、委員会のページ、採決の一覧。名前と内部IDを渡さない

10. **入口**：ホームと「わたしの記録」に「通知（未読 N 件）」のリンク。**案のベルは全体のメニュー（#85）で付ける**（ヘッダーがまだなく、全部のページで未読を数えることになるため）。#85 はフェーズ5なので、それまでは2か所からだけ入れる

11. **ルール**（`src/lib/domain/notifications.ts`）：`NOTIFICATION_KINDS`、`targetOf(kind)`（`bill`・`issue`・`solution`・`post`・`none`）、`hrefOf(item)`。文言は `ja.notifications`。画面の言葉の決まりを守る（「確認中」「衝突」「要調整」「反映」を出さない）
