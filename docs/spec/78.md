# アプリ内通知（設計書）

Issue #78。マイグレーションがあり、会期の処理と多くの書き込みの経路に関わるので Careful。決定は Issue #63（通知の中身は決定にない）。仕様は [docs/spec.md](../spec.md) の「通知・検索・共有」（通知はアプリ内のみ。自分の法案の進捗、「考えが変わった」が付いた、採決の開始、委員長選挙）と「モデレーションの方針」（削除や非表示には理由を記録し、本人に通知する）。画面の案は `PcHeader`・`SpTop` のベルだけで、一覧の案はない。

届ける相手ときっかけ、既読、入口は仕様書に定めがないので、この Issue の受入基準で確かめる（STOP 1 で確認する）。

## 決めたこと

1. **2つの作り方**：
   - **行を書くもの**：`notifications` の行を、きっかけの操作のあとに入れる。1人か少数に届くもの
   - **時刻から求めるもの**：読むときに求め、行を書かない。全員に届くものと、時刻で進むもの（進みを書き込んでいないので、動くきっかけがない。docs/spec/50.md）。いまの会期の分だけ。全員分の行を書かないので、Cron に頼らず、短い会期でも動く

2. **表**（`drizzle/0022_*.sql`。新しい表だけ）：
   - `notifications`：`id`（自動採番）、`user_id`（外部キー。ユーザーの行を消すと一緒に消える。`bans` と同じ。退会の機能はまだない）、`kind`、`target_id`（整数。法案、課題、解決策、投稿、委員会の番号。`committees.id` も整数）、`ref_id`（整数。同じ対象に何度も届くものを分ける。なければ 0）、`created_at`（ミリ秒の整数。ほかの表と同じ）。列はすべて `NOT NULL`。UNIQUE（`user_id`, `kind`, `target_id`, `ref_id`）。索引（`user_id`, `created_at`, `id`）。`kind` に CHECK は付けない（種類を足すたびに表の作り直しになる。値は `NOTIFICATION_KINDS` の型で絞る）
   - `notification_reads`：`user_id`（主キー、外部キー。消えるのは同じ）、`read_at`（ミリ秒の整数）、`read_id`（そのときの `notifications.id` の最大）。一覧の1ページ目を開いた時点
   - 本文は持たない。読むときに `kind` と題名から作る（題名の変更に追従し、文言を変えられる）

3. **何度走っても1件、起きるたびに1件**：入れる文は `INSERT ... SELECT ... ON CONFLICT DO NOTHING`。**黙って捨てないよう、種類ごとに `target_id` と `ref_id` を次の表で決める**（下の「種類」）。発議のやり直しは、要調整の法案を直して発議し直すときだけで、`proposed_rev` が変わる。否決と廃案からの出し直しは別の法案（新しい行）になるので、通知もぶつからない。`bill_cosponsors.id` は自動採番で番号を使い回さない。撤回は終わりの状態で、やり直せない。申し出を断られた人と抜けた人と外された人は申し出直せず（docs/spec/76.md の決定G）、取り下げて申し出直すと `bill_cosponsors` の行は新しくなる。同じ任期に2度の確定と解任はない

4. **通知に失敗しても元の操作を失敗させない**：`notifications.ts` の入れる関数は失敗をログに出して受け止める。元の操作は終わっているので、これで利用者に失敗を返さない。**失敗するとその通知は届かない**（非表示も同じ。理由は本人が課題のページで読めるので、やり直す仕組みは足さない）。会期の処理の中の通知（決めたこと5・6）も同じで、Cron の失敗に数えない（次の日にまた通るので届く）。例外は、同じ `db.batch` に入れる2か所（当選は確定と一緒に、取り下げは票を消す文と一緒に。票を消したあとでは誰に届けるか分からない）。batch の中は builder（`db.run` は本物の D1 でだけ落ちる）

5. **会期の結果**（`notifyBillOutcomes(db, sessionKey, now)`）：`bill_results` と `vote_reviews` と `bill_adjustments` の今の状態から、届けるべき行を1つの関数で入れる。結果を書く処理の中には入れない（結果を書いたあとで失敗すると、次の実行で結果の行があるので飛ばされ、通知を失う）。呼ぶのは `settleSession` の最後（反映のあと）と `decideReview` の最後。今の状態から求めるので、途中で失敗しても次の実行で届く。`settleSession` は結果のない法案がなくても最後まで進み、Cron（毎日 JST 0時1分）は直前の会期を毎日通る。**古い会期の確認の決定のあとで通知だけ失敗すると届かない**（その会期を通る処理がないとき。失敗はログに出す。確認の決定は少なく、起きにくいので、やり直す仕組みは足さない）
   - 確認の行が `open` のあいだは「結果を確認している」だけを入れ、可決か否決かを出さない（`noted` は確認の行がないのと同じ）。確認の行は結果の行より先に入り（docs/spec/73.md 決めたこと3）、あとから `open` にする経路はないので、結果の通知のあとで確認が始まることはない
   - `confirmed` は結果を入れる。`voided` は「無効」を入れる
   - `ref_id` の `settled_at` は結果の行が入ったときの値で変わらない。確認の行だけがあって結果の行がないあいだは入れない（結果のない確認の行は、運営の画面にも記録にも出していない）
   - 受け取る人は今の提出者と共同提出者。共同提出者は下書きのあいだだけ増え（承認の文に `status = 'draft'` がある）、要調整の法案は発議済みのままなので、結果のあとに加わった人に古い結果が届くことはない
   - 法案は提出者と共同提出者（`accepted`）に。`bill_adjustments` の行があれば「直す必要がある」も入れる

6. **発議のあとのぶつかり**（`notifyConflicts(db, now)`）：`runSessionEnd` の最後（取り込みのあと。Cron は毎日走る）に。発議済みで、いまの発議の付託先の会期（`referralSession(proposed_at)`）の結果がない法案について、反映のときと同じ判定（`conflictOf`。自分自身を除く）で、ぶつかる法案の提出者と共同提出者に入れる。1本につき `proposed_rev` ごとに1回。失敗してもログに出して残りを続け、次の日にまた通る（1本あたり数回の問い合わせ。法案が増えて Cron の上限に近づいたら見直す）

7. **時刻から求めるもの**（`timedNotices(db, userId, now, minutes)`。`minutes` は開発用の短い会期）：`now` より前のものだけ返す。
   - 全員向けの2つ：`vote_open`（採決が始まった。その会期に採決する法案がなければ出さない）、`election_open`（委員長選挙が始まった）（どちらも `session.voteAt`。会期ごとに1回。運営と運営協力者に選挙は出さない。締め出された人にも出す。読むだけのお知らせで、操作の断りは操作のときに出る）。委員会は今1つなので、委員会ごとの分け方はしない
   - 自分の法案ごとの2つ：`my_bill_deliberation`（質疑が始まった。`session.deliberationAt`）、`my_bill_vote`（採決が始まった。`session.voteAt`）。対象はその会期に採決する法案（`inVote`。どれも質疑の始まりより前に発議し、共同提出者は発議の前に決まるので、発議より前の時刻にならない）。全員向けの「採決が始まった」と同じ時刻に並ぶが、法案の名前が分かるので両方出す
   - `my_bill_expired`（要調整のまま期限が過ぎた）：`bill_adjustments.due_at`。いまの会期に期限が来た、直していない法案。法令が廃止された法案は入らない
   - `acting`（代行できる）：委員長の最後の操作（なければ任期の始まり）に7日を足した時刻。解任された任期には出さない（解任の通知が行で届く）。任期は1会期で、いまの会期の任期だけを見るので、次の会期には残らない

8. **既読**：行は `id` が `read_id` より大きいものが未読（会期の処理は始まった時刻を `created_at` に入れるので、時刻で比べると、処理の途中で開いた人の未読が消える）。時刻から求める項目は時刻が `read_at` より後のものが未読。`notification_reads` の行がなければすべて未読。`read_id` は一覧を読む前に求め、大きくなるときだけ更新する（読んでいるあいだに入った行を未読に残し、別のタブで値を戻さない）。**一覧の1ページ目を開くと全部既読になる**（未読の印は開く前の時刻で出す。**印を出すのは1ページ目だけ**で、2ページ目以降と開き直したあとには出さない）。項目ごとの既読は持たない。形の違う `page` と、項目のないページでは既読にしない。入口のリンクとページを移るリンクは先読みしない（`data-sveltekit-preload-data="off"`。先読みで既読にならないように）

9. **画面** `/tsuchi`（`noindex`。ログインが要る）：行と時刻から求める項目を**合わせて新しい順に並べてから**50件ごとに分ける（「次のページ」は `/houan` と同じ。同じ時刻は時刻から求める項目を先に、その中は全員向け、法案の番号の順、代行の順。行は `id` の大きい順）。各項目は文、日時、未読の印（色だけで示さず「未読」の文字）、リンク。リンク先は法案のページ、結果のページ、質疑のタブ、課題のページ、解決策の一覧、委員会のページ、採決の一覧。名前と内部IDを渡さない。**帯と「架空の法令」の表示を付ける**（条文は出さないが、架空の法案の「可決」が並ぶので、現実と誤解されないように。`IfBand`）。`noindex` も付ける。対象の行がない項目は出さない

10. **入口**：ホームと「わたしの記録」に「通知（未読 N 件）」のリンク。**案のベルは全体のメニュー（#85）で付ける**（ヘッダーがまだなく、全部のページで未読を数えることになるため）。#85 はフェーズ5なので、それまでは2か所からだけ入れる

11. **ルール**（`src/lib/domain/notifications.ts`）：`NOTIFICATION_KINDS`、`targetOf(kind)`（`bill`・`issue`・`solution`・`post`・`committee`。投稿と解決策は番号の並びが別なので `kind` を分ける）、`hrefOf(kind, ids)`。文言は `ja.notifications`。画面の言葉の決まりを守る（「確認中」「衝突」「要調整」「反映」を出さない）
