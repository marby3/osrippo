# 似た課題を出す機能と、課題の統合（設計書）

Issue #30。マイグレーション（列とトリガーの作り直し）と、取り消せない操作（統合）を足すので Careful。仕様の正は [docs/spec.md](../spec.md) の「課題・解決策・法案」の課題の項。課題は [docs/spec/25.md](25.md)、通報と運営の画面は [docs/spec/28.md](28.md)。

仕様書にない次のことは、2026-11-03 にユーザーと決めた（仕様書のドキュメントへの反映はユーザー側）。

- 仕様の「この課題に『わかる』を付けて補足を書く」は、いまは「わかる」を付けてその課題のページへ移るだけにする（画面の案の「これに『わかる』を付ける」）。補足は解決策の Issue で考える
- 似ているかは、タイトルの2文字ずつの組の重なりで決める（費用がかからない。言い換えは拾えない）。課題が数千件を超えたら全文検索の Issue の索引に切り替える
- 似た課題は、タイトルを打っている間に出す（画面の案と同じ。似た課題があるとボタンは「どれとも違うので、次へ」）
- 統合は委員長がいないあいだ運営と運営協力者が `/kanri` で行う。「わかる」は両方に付けた人を1人と数えて合算する。元の課題の URL は統合先へ転送し、統合先のページに「この課題にまとめた課題」として題名を並べる。統合は運営の記録に残す。取り消しはできない（その前に確認の画面を挟む）

## 範囲

- 入れる：似た課題の判定、似た課題を返す `/kadai/nita`、課題を書く画面の似た課題の欄と「これに『わかる』を付ける」、統合（`/kanri` の統合の欄と確認、統合先への転送、合算、まとめた課題の一覧、運営の記録）
- 入れない：補足、言い換えを拾う判定（Workers AI など）、統合の取り消し、統合を元の課題の書いた人に知らせること

## 似ている度合い

`src/lib/domain/similar.ts` の純粋な関数。

1. **そろえる**：NFKC にそろえ、英字を小文字にし、空白・句読点・記号（`\p{P}`、`\p{S}`、空白）を除く
2. **組を作る**：そろえた文字列の、となり合う2文字の組（コードポイントで数える）の集合。2文字に満たなければ空
3. **度合い**：Dice 係数 `2 × 共通の組の数 ÷ (組の数 + 組の数)`
4. **出す条件**：共通の組が2つ以上、かつ度合いが 0.15 以上。度合いの高い順、同じなら「わかる」の多い順、さらに同じなら新しい順に3件まで
   - 画面の案の例（入力「駅前で自転車の走る場所がわからない」に対して「自転車で歩道を走っていい場所がわかりにくい」「駅前の放置自転車で歩道が通りにくい」が出る）が出ることを、単体テストで確かめる

## 決めたこと

1. **`/kadai/nita?q=…`**：似た課題を JSON で返す（`{ issues: [{ id, title, supports }] }`）。ログインなしで呼べる（返すのは一覧と同じ公開の情報だけ）
   - `q` は信頼の境界：ないとき・空のときは `{ issues: [] }`。61字以上（コードポイント。タイトルの上限は60字）は 400
   - 対象は一覧に出る課題（`status` が `visible`・`restored`）だけ。非表示・統合済みは出さない
   - 対象の課題のタイトルを全部読み、Worker の中で度合いを計算する（課題が数千件を超えたら全文検索の Issue で索引に切り替える。あとで決めること）
2. **課題を書く画面（ステップ1）**：タイトルを打つと、0.4秒打たなかったときに `/kadai/nita` を呼び、似た課題があればタイトルの欄の下（PC は右）に「似た課題があります」「同じ困りごとなら、『わかる』を付けるだけで十分です」と、似た課題のカード（題名は課題のページへのリンク、わかるの数）を出す
   - いちばん上のカードにだけ「これに『わかる』を付ける」。押すと、その課題の「わかる」の POST（`/kadai/[id]?/support`、`op=add`。docs/spec/25.md 決めたこと6の判定をそのまま通る）を送り、通ったらその課題のページへ移る。断られたら（国、締め出し、レート制限）その理由をカードの下に出す
   - 似た課題があれば、次の段へ進むボタンを「どれとも違うので、次へ」、なければ「次へ」にする
   - 入力を変えたら、前の問い合わせの答えは捨てる（遅れて届いた古い答えで上書きしない）
   - JS がないときは似た課題の欄を出さない（タイトルだけを書いて次へ進む）
3. **統合の欄（`/kanri`）**：課題のまとまりごとに「別の課題に統合する」（統合先の課題の番号を入れて「確かめる」）。送り先は `GET /kanri?issue=[id]&merge=[統合先]` で、確認の欄を出す
   - 確認の欄：「#[id]『[題名]』を #[統合先]『[題名]』に統合します。統合は取り消せません」、合算したあとの「わかる」の数（両方に付けた人は1人）、メモ（決めたこと6の判定。公開する）、「統合する」
   - 統合できないときは、確認の欄の代わりにその理由を出す（決めたこと5）
   - `merge` は信頼の境界：形が違えば（`parseIssueId` で読めない）404
4. **統合する（`?issue=[id]&/merge`、POST）**：確かめる順は docs/spec/28.md 決めたこと5と同じ（役職 404 → 国 403 → 入力 400 → 自分の課題 403 → 状態 400）。入力は `issue`・`target`・`note`
   - `issues` に `merged_into`（統合先の番号、NULL 可）を足し、`status` に `merged` を足す（`status` の列に CHECK はない。docs/spec/28.md「表」）
   - 1文の `UPDATE issues SET status = 'merged', merged_into = :target, status_actor = …, status_note = …, status_changed_at = … WHERE id = :issue AND status IN ('visible', 'restored') AND (統合先が visible か restored) AND :issue <> :target` で行う。行が返らなければ 400
   - トリガー（`issues_status_log` を作り直す。決めたこと7）が、同じ文の中で次を行う
     - 運営の記録に `merge` の行を書く（統合先の番号も残す）
     - 元の課題の「わかる」を統合先へ写す（`INSERT OR IGNORE`。両方に付けた人は1人のまま）。元の課題の行は残す（履歴）
     - 元の課題へすでに統合されていた課題の `merged_into` を、新しい統合先に付け替える（統合が続いても、転送は1回で済む）
5. **統合できないとき**（どれも 400 と理由。記録を書かない）
   - 統合先が自分自身
   - 元の課題が `visible`・`restored` でない（非表示の課題を統合すると、統合先に非表示の題名が並ぶため。非表示のまま残す）。すでに統合された課題も同じ
   - 統合先が `visible`・`restored` でない、またはない
   - 元の課題か統合先のどちらかを、操作する運営が書いた（403。docs/spec/28.md 決めたこと5と同じく、運営の恣意性を疑われないように）
6. **メモ**：docs/spec/28.md 決めたこと5と同じ判定（1〜200字、制御文字なし、改行は可）。公開する
7. **マイグレーション**（`drizzle/0005_*.sql`）：`issues` に `merged_into` を、`moderation_logs` に `merged_into` を `ADD COLUMN` で足す。トリガー `issues_status_log` を `DROP TRIGGER` して作り直す（`merged` → `merge` の記録と、「わかる」を写す・付け替える文を足す）。`schema.ts` のトリガーの注意書きも 0005 を指すように直す
8. **統合された課題のページ**：`/kadai/[元の番号]` は、だれが開いても `/kadai/[統合先]` へ 308 で転送する。元の課題への「わかる」と通報の POST は 403 と「統合された課題には操作できません」
9. **統合先のページ**：「この課題にまとめた課題」として、まとめた課題の題名を新しい順に並べる（リンクにしない。元の URL は転送されるため）。わかるの数は統合先の `issue_supports` の数（写したあとなので、そのまま合算になる）
10. **運営の記録 `/unei`**：`merge` は「統合」と出し、理由の列に「#[統合先] にまとめた」を出す（統合先へのリンク）
11. **言葉**：`ja.ts` の `similar`（似た課題）と `kanri`・`unei`・`hidden` に足す

## テストの方針

- 似ている度合いと、出す条件と並びは Vitest（画面の案の例を含む）
- 画面は Playwright の2幅で、似た課題の欄と「これに『わかる』を付ける」、統合の確認と統合、転送、合算、まとめた課題、運営の記録、統合できないときを確かめる
- 信頼の境界：`/kadai/nita` の `q`、`/kanri` の `merge`、統合の POST の `issue`・`target`・`note`

## あとで決めること

- 課題が数千件を超えたときの似た課題の探し方（全文検索の索引、言い換えを拾う判定）
- 補足（解決策の Issue）
- 統合を元の課題の書いた人に知らせること（通知の仕組み）
