# 解決策の通報と非表示（設計書）

Issue #36。マイグレーション（列・表・トリガーの追加）と、権限の境界（運営の画面）を足すので Careful。仕様の正は [docs/spec.md](../spec.md) の「不正・荒らし対策とモデレーション」。課題の通報は [docs/spec/28.md](28.md)、解決策は [docs/spec/34.md](34.md)。

ユーザーと決めたこと（#34 の STOP 1、2026-11-03）：解決策の通報と非表示は、課題と同じ決まり（別々の3人の通報で自動非表示、`/kanri` で運営と運営協力者が確認、運営の記録に残す）を使う。

課題の決まりを解決策に広げるときに、私が決めたこと（STOP 1 で確認）：

- 通報の理由は「人への攻撃・差別」「宣伝・荒らし」「その他」（任意）。「同じ課題がほかにある」は課題の統合のための理由なので、解決策には出さない
- 通報の上限（1アカウント24時間に10件）は、課題の通報と合わせて数える
- 非表示の解決策は、書いた本人と運営以外には出さない（課題のページの解決策の数・一覧の解決策の数・「解決策あり」の絞り込みからも外す）。本人と運営には本文と「非表示になっています」を出す

## 範囲

- 入れる：解決策の通報、自動非表示、非表示の解決策の見え方、`/kanri` の「通報を受けた解決策」（非表示にする・表示に戻す）、運営の記録の解決策の行
- 入れない：解決策の統合、異議申し立て、通報した人への結果の知らせ

## 決めたこと

1. **通報の画面**：各解決策（課題のページと解決策の一覧）に「この解決策を通報する」。押すとその解決策の下に通報の欄（理由のラジオ（任意）、「その他」の説明（200字まで）、非表示の基準の要約と `/unei` へのリンク、「通報する」）を開く。JS がなければ押すとその解決策の通報の欄へ移る形にはせず、課題と同じく欄を最初から開いておく
   - ログインしていない人には、ボタンは出すが欄は開かず、押すとログインの画面へ（戻り先はいまのページ）
   - ボタンを出さないとき：自分の解決策、すでに通報した（代わりに「この解決策は通報済みです」）、解決策か課題が非表示
   - 送ると、その解決策の下に「通報を受け付けました」
2. **通報の受け付け**（`?/reportSolution` の POST。課題のページと解決策の一覧の両方に置く）：課題の番号と課題があるか（404。ログインより先）→ ログイン → 国 → 締め出し → 入力（`solution` の形、`reason`・`note` は docs/spec/28.md 決めたこと2の判定から「同じ課題がほかにある」を除いたもの。形が違えば 400。解決策がその課題のものでなければ 404）→ 自分の解決策（400）→ 状態（課題か解決策が非表示・統合済みなら 403 と「非表示の解決策には操作できません」）→ 2回目か（200 と「この解決策は通報済みです」。数えない）→ レート制限（課題の通報と合わせて1アカウント24時間に10件。超えたら違反に数える）→ 保存
3. **自動非表示**：保存したあと、`UPDATE solutions SET status = 'auto_hidden', status_actor = 'auto', status_reason = 'reports', …（status_* は全部入れる）WHERE id = ? AND status = 'visible' AND (counted = 1 の通報の数) >= 3` を1文で行う。数に入るのは、登録から24時間たった人の通報（理由は問わない）
4. **非表示の解決策の見え方**（`auto_hidden`・`hidden`）
   - 書いた本人と運営以外：課題のページの解決策・解決策の一覧に出さない。「解決策 N件」、「解決策をすべて見る（N件）」、課題の一覧の解決策の数、「解決策あり」の絞り込みも、表示中（`visible`・`restored`）の解決策だけで数える
   - 書いた本人と運営：本文と「この解決策は通報により非表示になっています」（`hidden` なら「この解決策は運営の確認により非表示になっています（理由：{理由}）」）を出す。「わかる」「考えが変わった」は数だけ、通報のボタンは出さない。並びと数（「解決策 N件」）は、ほかの人と同じく表示中のものだけで数える（本人・運営に見える非表示の解決策は、表示中の解決策のあとに並べる）
   - 非表示の解決策への「わかる」「考えが変わった」の POST は 403 と「非表示の解決策には操作できません」（docs/spec/34.md 決めたこと5の「課題の状態」と同じ位置で確かめる）
5. **運営の画面 `/kanri`**：「通報を受けた課題」の下に「通報を受けた解決策」の欄。権限の確かめ（役職 → 404 を最初に）と国の確かめは課題と同じ
   - 通報を受けた解決策を、自動で非表示が先、その中は最後の通報が新しい順に100件まで。各解決策に、番号、課題（題名と課題のページへのリンク）、本文、状態、通報の数（数に入るもの／入らないもの）、理由ごとの数、「その他」の説明、`restored` なら表示に戻したあとの通報の数。通報した人と書いた人は出さない
   - `?solution=[番号]` で、その解決策（通報されていなくても）を欄の上に出す。形が違う・ないときは 404
   - 「非表示にする」（`?solution=[番号]&/hideSolution`）と「表示に戻す」（`?solution=[番号]&/restoreSolution`）：入力は `solution`・`reason`（非表示のみ）・`note`。判定と状態の表は課題と同じ（docs/spec/28.md 決めたこと5。`merged` はない）。自分が書いた解決策は 403
6. **運営の記録 `/unei`**：解決策の行は、課題の列に「#[課題] の解決策」（課題のページの、その解決策の位置 `#kaiketsu-[番号]` へのリンク）と出す。何をしたか・だれが・理由・メモは課題と同じ
7. **運営として対応する**：運営・運営協力者には、各解決策に「運営として対応する」（`/kanri?solution=[番号]`）を出す
8. **言葉**：`ja.ts` の `solution`・`kanri`・`unei` に足す。基準（`ja.unei.criteria`）の文を「課題や解決策」に直す

## テストの方針

- 画面のテストで、通報の流れ、自動非表示と見え方（本人・運営・それ以外）、`/kanri` の権限と操作、運営の記録、上限（課題の通報と合わせる）を確かめる
- 信頼の境界：通報の `solution`・`reason`・`note`、`/kanri` の `?solution=` と操作の `solution`・`reason`・`note`

## あとで決めること

- 解決策の統合
- 非表示の解決策が多い課題で、本人・運営が見る並び
