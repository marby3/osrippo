# 委員会と法案の下書きの表、変更点と正式名のルール（設計書）

Issue #45。マイグレーション（表の追加と `actions` の作り直し）を足すので Careful。仕様の正は [docs/spec.md](../spec.md) の「課題・解決策・法案」の法案の項と「法令データとブランチ」の条文の構造。法令の版は [docs/spec/8.md](8.md)、解決策は [docs/spec/34.md](34.md)。

仕様書にない次のことは、2026-11-04 にユーザーと決めた（Issue #41 の決めたこと。仕様書のドキュメントへの反映はユーザー側）。

- 発議の前に編集できるのは提出者1人だけ。共同提出者と撤回は v0.4（決めたこと4）
- 解決策の引用は1つ以上が必須で、5つまで。非表示の解決策は引用できない（決めたこと7）
- 改正・廃止の対象は委員会の対象法令（いまの3本）だけ。基にするのは現実の法律のいま施行されている版で、どの版を基にしたかを記録する（決めたこと8）
- 法案は解決策から書き始める（`/houan/kaku?kaiketsu=<番号>`。#41 レビューで決めたこと）

## 目的

法案の下書きを保存し、読み出せる形を作る。画面は #46（改正・廃止）と #47（制定）、一覧は #48、賛同と発議は #49、状態の進み方は #50。

## 範囲

- 入れる：表（委員会、委員会の対象法令、法案、法案の対象の法令、条ごとの変更点、元になった解決策）、`actions` の作り直し（v0.3 で使う種類をまとめて足す）、ドメインの決まり（入力の確かめ、変更後の条文の読み取り、変更点の確かめ、正式名）、下書きを作る・保存する・読むサーバーの関数

## 表

`drizzle/0009_*.sql`（`drizzle-kit generate`）。第1委員会の行は、マイグレーションの末尾に手で `INSERT` を足す（`topics` の最初の行と同じ。前の文との間に `--> statement-breakpoint`）。委員会の対象法令（`committee_laws`）の行は、`laws` の行と同じく取り込み（`src/lib/db/seed.ts` の `seedStatements`）で `laws` のあとに入れる。`laws` はマイグレーションでは入らないので、マイグレーションで入れると外部キーで止まるため。generate のあとに SQL を読み、既存の表（`issues`・`solutions` など、トリガーのある表）を作り直していないことを確かめる。

## 決めたこと

1. **版ごとに保存する（`rev`）**：法案の中身（対象の法令・変更点・元になった解決策）は、保存のたびに新しい版の番号の行として足し、`bills.rev` が指す版だけを読む。D1 と node:sqlite の両方で使う Drizzle の型には `batch` がなく、子の行を消して入れ直すと途中で失敗したときに中身が半分になるため。
   - 版の番号は `UPDATE bills SET next_rev = next_rev + 1 WHERE id = ? AND user_id = ? AND status = 'draft' RETURNING next_rev - 1` で取る。保存のたびに必ず違う番号になるので、同じ法案を2つのタブから同時に保存しても、子の行は混ざらない（`rev + 1` を使うと、2つの保存が同じ番号に子の行を足して混ざる）
   - 作る：`bills` を `rev = 0`・`next_rev = 2` で足す → 子の行を版 1 で足す → `UPDATE bills SET rev = 1 WHERE id = ? AND rev = 0`。作る途中で失敗した `rev = 0` の行は残る
   - **`rev = 0` の法案は、ないものとして扱う**：`bills` を引くすべての問い合わせ（法案のページ、一覧 #48、数え、賛同 #49 など）に `rev > 0` を付ける。忘れないよう、`src/lib/server/bills.ts` に `rev > 0` を入れた条件（`savedBill`）を1つ置き、法案を引くところはそれを使う。`billById` は undefined、画面では 404。`saveDraft` は `expectedRev ≥ 1` だけを受け取り（形が違えば保存しない）、版の番号を取る UPDATE にも `AND rev > 0` を付ける（作りかけの法案を乗っ取らないように）
   - `kind`（改正・廃止・制定）は作ったあとは変えない（保存の UPDATE に入れない）。変えたいときは新しく書く
   - 保存する：版の番号 r を取る（0行なら、提出者でないか下書きでないので保存しない）→ 子の行を版 r で足す → `UPDATE bills SET rev = r, title = ?, … , updated_at = ? WHERE id = ? AND user_id = ? AND status = 'draft' AND rev = ?`（フォームを開いたときの `rev`）を1文で行う。0行なら保存しない（ほかの画面で先に保存された、発議した、のどれか）
   - 途中で失敗したり負けたりした保存の子の行は、どの `bills.rev` からも指されないので読まれない。消すと、まだ途中のほかの保存の行を消すおそれがあるので、消さない
   - 前の版の行も消さない（下書きの変更の記録になる。画面に出すかは後で決める）
2. **条の変更点の形**：変更点は条を単位に持ち、変更後の条をまるごと（見出しと、項と号の木）入れる。項・号の単位の「書きかえ」「新しく追加」は、基にした版の条と比べて画面で出す（`compareArticles` と同じ考え）。項・号の内部IDは持たない。可決した法案を IF世界の版にするとき（フェーズ4）に、現実の改正の取り込みと同じ対応付け（`alignArticles`・`buildHistory`）で振る。現実の改正も変更後の条文しか取れないので、同じ扱いになる。`body` の JSON は `[{ "num": "1", "text": "…", "items": [{ "num": "1", "text": "…" }] }]`（`parse.ts` の `Paragraph[]` と同じ形）
3. **変更後の条文の読み取り**（`parseArticleBody`）：書く画面の「変更後の条文」の欄の文字列を、項と号の木にする。形は `articleText`（`display.ts`）から見出しの行を除いたものと同じで、読み取りはその逆にする
   - 1行目は必ず第1項の本文として読む（号の形をしていても）。1行目が空なら誤り。1行目から、次の項の行までが第1項。行頭が「半角の算用数字＋全角空白」（`2　`。全角の数字は項の行にしない）の行から次の項。行頭が「漢数字（の漢数字…）＋全角空白」（`一　`、`十二の二　`）の行から、その項の号
   - それ以外の行は、前の項か号の本文の続き（改行 `\n` でつなぐ）。項や号の本文は改行を含みうる（`parse.ts` の `textOf` は、号の細分（イ、ロ…）の前に改行を入れる）。空の行は無視する
   - 項の番号は 2 から1つずつ増える。号の番号は項ごとに、前の号より後ろ（`compareNum` で大きい）
   - 形が違えば、何行目がどう違うかを返す
   - 対象3法の現在の版のすべての条で、`parseArticleBody(articleText から見出しを除いたもの)` が元の項と号に戻る（単体テストで確かめる）
4. **変更点の確かめ**（`checkChanges`。基にした版の条と変更点の列を受け取る純粋な関数）
   - `amend`：基にした版にその内部IDの条があり、`num` がその条の番号と同じで、見出しか本文が変わっている
   - `delete`：基にした版にその内部IDの条がある。削除した条は「削除」として残す（仕様「条文の構造」）ので、`body` は持たない
   - `add`：番号は枝番（`3_2` の形。仕様「IF世界で条を足すときは、繰り下げをせず枝番方式」）。同じ番号の条が基にした版にも、ほかの変更点にもない。枝番の元（`3_2` なら `3`、`3_2_2` なら `3_2`）が、基にした版か、ほかの `add` にある
   - `amend`・`delete` の対象は、基にした版のその法令の条（`kind = 'article'`）。`checkChanges` は基にした版の条の列を受け取り、その中の内部IDだけを通す（DB では守られないので、ここで確かめる）
   - 基にした版ですでに「削除」の条（本文が「削除」だけの条。いまの対象3法にはない）は、`amend` で中身を書けるが、`delete` はできない
   - 同じ条に2つの変更点はない。附則と別表は基にした版の条に入っていない（`parseLaw` は本則だけ）ので、変更点にできない
   - 制定（`enact`）の新法：すべて `add` で、番号は `1` から1つずつ増える（枝番は使わない）。第1条があり、見出しが「（目的）」で本文がある（仕様「法令名と第1条（目的）を必須にし」）
   - 改正（`amend` の法令）は変更点が1つ以上。廃止（`repeal` の法令）は変更点を持たない（法令をまるごと廃止する）
5. **法案の確かめ**（`validateBill`）：`checkText`（`issues.ts`）を使う
   - 題名：1〜60字、改行なし。誰が困っているか：1〜200字、改行可。副作用：1〜400字、改行可
   - 3行要約：任意。空の行を除いて3行まで、各行60字まで
   - 附則：任意。1000字まで、改行可
   - 任意の欄（3行要約・附則・見出し）は、空なら誤りにせず NULL にする（`checkText` の `required` を使わない）
   - 制定の法令名：1〜60字、改行なし。末尾は「法」か「法律」
   - 見出し：任意。100字まで、改行なし。条ごとの値なので `checkChanges` で確かめる（取り込みデータで測ると、対象3法では景品表示法の第6条の40字が最長、ほかの法令も含めると49字）。条の本文：1条あたり10000字まで。欄の文字列なので `parseArticleBody` で確かめる（取り込みデータで `articleText` の字数を測ると、対象3法では特定商取引法の第26条（2027-07-22 の版）の3602字が最長、ほかの法令も含めると5931字。v1.0 で六法へ広げても書きかえられる長さにする）
   - 対象の法令：1〜5本。改正・廃止の法令は委員会の対象法令（`committee_laws`）のどれか。種類ごとの形は次のとおり
     - `amend`：すべて `amend`
     - `repeal`：主（`seq` 0）が `repeal`。ほかは `repeal` か `amend`（附則で関連法を改正する形）
     - `enact`：主が `enact`、ほかは `amend`（新法の附則で関連法を改正する形。仕様「新法の附則で関連法を改正する形」）
   - 変更点は法案全体で50条まで
   - 元になった解決策：1〜5つ。保存のときに表示中（`visible`・`restored`）の解決策だけ。引用したあとで解決策が非表示になっても、引用の行は残す（法案のページでほかの人に見せるかは #46 で決める）。課題の統合で解決策が統合先へ移っても、解決策の番号は変わらないので引用はそのまま
6. **正式名**（`formalName`）：画面の題名とは別に、種類と主の法令から作る
   - 改正：対象が1本なら「{法令名}の一部を改正する法律案」、2本以上なら「{主の法令名}等の一部を改正する法律案」
   - 廃止：`repeal` の法令が1本なら「{法令名}を廃止する法律案」、2本以上なら「{主の法令名}等を廃止する法律案」（附則で改正する法令は数えない）
   - 制定：「{新法の法令名}案」
   - 法令名は `laws.title`（基にした版ではなく、いまの題名）
7. **基にした版**：改正・廃止の法令ごとに、書く画面を開いたときの現在の版（`currentRevision`）をフォームが送り、それを `base_revision_id` に入れる。変更点は、利用者が見て書いたその版に対するものだから。保存の前に、呼ぶ側（#46）がその版と今の現在の版を比べ、違えば保存しない（「条文が新しくなりました。開き直してください」）。比べてから保存するまでの間に版が変わっても、入るのは利用者が見た版なので、中身と食い違わない。内部IDは版をまたいで同じなので、`provision_id` はそのまま使える
   - ただし、内部IDと版のIDが同じなのは1回の取り込みの中だけ（docs/spec/8.md：取り込みは毎回すべて作り直し、作り直すと内部IDが変わりうる）。法案の行は `provisions`・`law_revisions` に外部キーで結び付くので、法案のある DB で取り込みだけをやり直すことはできない。追記だけで行う同期を決めるまで（フェーズ4までに別の Issue。docs/spec/8.md）は、取り込み直しは開発のときだけ、法案も含めて DB ごと作り直す（`scripts/db-reset.ts`。下書きも消える）。追記だけの同期の Issue では、内部IDと版のIDを変えないことを条件にする
8. **サーバーの関数**（`src/lib/server/bills.ts`）
   - `createDraft(db, userId, input, now)`：法案の番号を返す
   - `saveDraft(db, billId, userId, expectedRev, input, now)`：保存したかを返す
   - `billById(db, billId)`：`bills.rev` の版の中身を返す。`rev = 0` か、ない番号なら undefined
   - `input` には、法令ごとの `baseRevisionId` を含む。どの関数も `validateBill` と `checkChanges` と基にした版の比べを通ったものだけを受け取る（確かめるのは呼ぶ側の #46。関数は受け取った値を信じて書く）
9. **画面の言葉**：この Issue では画面を作らないので、`ja.ts` には `validateBill`・`parseArticleBody`・`checkChanges` の誤りの文言だけを足す

## テストの方針

- 単体テスト（node:sqlite にマイグレーションを流し、取り込みも流す）：委員会の行と対象3法、`actions` の新しい種類、既存のトリガー（`issues_status_log`・`solutions_status_log`）と全文検索の表（`search_trigram`・`search_bigram`）が残っていること、CHECK（制定の新法の列、`op` と列の組み合わせ）、`createDraft`→`billById`、`saveDraft` の `rev` の確かめ（古い `rev`・ほかの人・発議したもの・`rev = 0` の作りかけ）と、負けた保存の子の行が読まれないこと
- ドメインの単体テスト：`parseArticleBody` の往復（対象3法の現在の版の全部の条）と形の誤り、`checkChanges`、`validateBill`、`formalName`
- 信頼の境界：この Issue はフォームを受け付けない。`parseArticleBody` と `validateBill` は #46 でフォームの値を受けるので、形の誤りの単体テストをここで書く。`checkChanges` もフォームから来た `num`・`op`・内部IDを受けるが、それ自体が確かめる関数なので、基準4のテストに誤りを返す入力（ない内部ID、ほかの法令の条、枝番でない追加の番号など）を入れれば足りる
- 往復の基準の前提：対象3法の取り込みデータでは、どの条も項の番号が 1, 2, 3… と続き、第1項の本文が空の条はない（設計書のレビューのときに確かめた）
