# ログイン（設計書）

Issue #23。認証なので Careful。仕様の正は [docs/spec.md](../spec.md) の「議員・有識者向け機能と認証」「不正・荒らし対策とモデレーション」「技術構成」。ここではフェーズ2の一般アカウントのログインだけを決める。

## 目的

課題の投稿・「わかる」・通報（フェーズ2）に、ログインした利用者だけが参加できるようにする。パスワードは預からない（OAuth のみ）。閲覧はログインなしでできるまま。

## 範囲

- 入れる：Better Auth、Google と LINE のログイン、ログアウト、ログインが要るページからログインへの誘導、テスト用のログイン、`users` などの表
- 入れない：有識者・議員の認証（フェーズ5）、表示名の変更画面、退会、Turnstile とレート制限（課題の投稿の Issue でかける）、本番とステージングの OAuth の設定（デプロイの Issue）

## 部品

| 部品 | 使い方 |
| --- | --- |
| Better Auth 1.7 | `better-auth/svelte-kit` で `hooks.server.ts` に組み込む。DB は Drizzle アダプター（`provider: 'sqlite'`）で D1 |
| Google | `socialProviders.google` |
| LINE | `genericOAuth` プラグインの `line()`（`providerId: 'line'`）。日本のチャネル1つ |
| テスト用のログイン | Better Auth の `testUtils` プラグインを入れた、テスト専用の auth インスタンス |

## 表

Better Auth の4つの表を、`src/lib/db/schema.ts` に Drizzle で書き、`drizzle-kit generate` でマイグレーションを作る（`drizzle/0002_*.sql`）。仕様書の `users` に当たる。

| 表 | 主な列 | 備考 |
| --- | --- | --- |
| `user` | `id`、`name`（表示名）、`email`、`email_verified`、`image`、`created_at`、`updated_at` | 実績スコアや認証の種類は、使うフェーズで列を足す |
| `session` | `id`、`user_id`、`token`、`expires_at`、`ip_address`、`user_agent` | |
| `account` | `id`、`user_id`、`provider_id`（`google`／`line`）、`account_id`（提供元の利用者ID）、トークン類 | 同じ人が Google と LINE の両方で入ると、別のアカウントになる（自動で結び付けない） |
| `verification` | Better Auth が OAuth の state などに使う | |

## 決めたこと

1. **表示名**：提供元のプロフィールの名前（Google の氏名、LINE の表示名）は使わない。登録時に「参加者」＋数字（例：参加者4821）を振る。実名が画面に出るのを避けるため（仕様「個人を特定できる統計を作らない」「実在の人物への誹謗中傷」の趣旨）。表示名を変える画面は別の Issue
2. **メールアドレス**：Better Auth の `user.email` は必須だが、LINE はメールの取得に別の申請が要り、返さないことがある。提供元が返さないときは `{provider}-{accountId}@users.invalid` を入れる。メールは画面に出さず、連絡にも使わない
3. **アカウントの結び付け**：同じメールでも、Google と LINE のアカウントを自動では結び付けない（Better Auth の `accountLinking` を切る）。乗っ取りの経路を作らないため
4. **セッション**：Better Auth の既定（HttpOnly・SameSite=Lax の Cookie、7日、期限が近づいたら延ばす）。本番は Secure
5. **ログインが要るページ**：`hooks.server.ts` でセッションを `locals.user` に入れる。ログインが要るページは、ログインしていなければ `/login?next=<元のパス>` へ送る。`next` は同じサイトのパス（`/` で始まり `//` で始まらない）だけを受け付け、それ以外は `/` にする（オープンリダイレクト対策）
6. **ログインの画面**：`/login` に「Googleでログイン」「LINEでログイン」。押すと POST で自前のエンドポイントに送り、Better Auth の `signInSocial`／`signInWithOAuth2` で提供元へリダイレクトする。戻り先は `next`
7. **テスト用のログイン**：`/test-login?name=<名前>`。環境変数 `TEST_LOGIN` が `1` のときだけ動き、それ以外は 404。
   - `TEST_LOGIN` は wrangler.jsonc にも `.dev.vars` にも書かない。画面のテストの webServer が `wrangler dev --var TEST_LOGIN:1` で起動するときだけ立てる
   - 名前ごとに `{name}@test.invalid` の利用者を作り（あれば使い回す）、`testUtils` の `login` でセッションを作って Cookie を返す。表示名は名前そのまま
   - 画面には「テスト用のログイン：{名前}」と出す
   - `testUtils` は本番の auth インスタンスには入れず、テスト用のログインのエンドポイントの中だけで作る
8. **秘密の値**：`BETTER_AUTH_SECRET`、`GOOGLE_CLIENT_ID`、`GOOGLE_CLIENT_SECRET`、`LINE_CLIENT_ID`、`LINE_CLIENT_SECRET`。本番とステージングは `wrangler secret`、手元は `.dev.vars`（git に入れない。`.dev.vars.example` に名前だけ置く）。画面のテストはダミーの値を `--var` で渡す
9. **わたしの記録**：ログインできたことを確かめる最小のページ `/watashi`（PcLaw の右上「わたしの記録」）。表示名とログアウトを出す。ログインが要るページの最初の例にもなる

## 画面のテストの起動

- いまの webServer（`pnpm db:reset && pnpm build && pnpm preview`）の `preview` に、`--var TEST_LOGIN:1` とダミーの OAuth の値を足したスクリプト `preview:test` を作り、Playwright はそれを使う
- テスト用のログインが無効のときに 404 になることは、`TEST_LOGIN` を立てない2つ目の webServer（別のポート、別の `--persist-to`）で確かめる。同じ D1 のファイルを2つのサーバーで開かない（Issue #17）

## テストの方針

- 「Googleでログイン」「LINEでログイン」を押すと、提供元の認可の URL（`accounts.google.com`／`access.line.me`）へ、ダミーの client_id と自分の戻り先を付けてリダイレクトされる（提供元までは行かない）
- テスト用のログインで入ると `/watashi` に表示名が出て、ログアウトすると `/watashi` が `/login?next=/watashi` へ送られる
- `TEST_LOGIN` がないサーバーでは `/test-login` が 404
- `next` に外のサイト（`//evil.example`、`https://evil.example`）を渡しても、外へは送らない（信頼の境界の入力）

## あとで決めること

- 本番とステージングの OAuth の設定（Google Cloud と LINE Developers での登録、戻り先の URL）：デプロイの Issue
- 表示名の変更、退会とデータの扱い
- 多重アカウント対策（IP・端末ごとの上限）：課題の投稿の Issue でレート制限と合わせて決める
