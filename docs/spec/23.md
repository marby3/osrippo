# ログイン（設計書）

Issue #23。認証なので Careful。仕様の正は [docs/spec.md](../spec.md) の「議員・有識者向け機能と認証」「不正・荒らし対策とモデレーション」「技術構成」。ここではフェーズ2の一般アカウントのログインだけを決める。

## 目的

課題の投稿・「わかる」・通報（フェーズ2）に、ログインした利用者だけが参加できるようにする。パスワードは預からない（OAuth のみ）。閲覧はログインなしでできるまま。

## 範囲

- 入れる：Better Auth、Google と LINE のログイン、ログアウト、ログインが要るページからログインへの誘導、テスト用のログイン、`users` などの表
- 入れない：有識者・議員の認証（フェーズ5）、表示名の変更画面、退会、Turnstile とレート制限（課題の投稿の Issue でかける）、本番とステージングの OAuth の設定（デプロイの Issue）

## 部品

| 部品 | 使い方 |
| --- | --- |
| Better Auth 1.7 | `better-auth/svelte-kit` で `hooks.server.ts` に組み込む。DB は Drizzle アダプター（`provider: 'sqlite'`）で D1。Workers では D1 が要求ごとに渡されるので、auth のインスタンスも要求ごとに作る |
| Google | `socialProviders.google` |
| LINE | `socialProviders.line`（Better Auth 1.7 の標準。日本のチャネル1つ） |
| テスト用のログイン | Better Auth の `testUtils` プラグインを入れた、テスト専用の auth インスタンス |

## 表

Better Auth の4つの表を、`src/lib/db/schema.ts` に Drizzle で書き、`drizzle-kit generate` でマイグレーションを作る（`drizzle/0002_*.sql`）。仕様書の `users` に当たる。

| 表 | 主な列 | 備考 |
| --- | --- | --- |
| `user` | `id`、`name`（表示名）、`email`、`email_verified`、`image`、`created_at`、`updated_at` | 実績スコアや認証の種類は、使うフェーズで列を足す |
| `session` | `id`、`user_id`、`token`、`expires_at`、`ip_address`、`user_agent` | |
| `account` | `id`、`user_id`、`provider_id`（`google`／`line`）、`account_id`（提供元の利用者ID）、トークン類 | 同じ人が Google と LINE の両方で入ると、別のアカウントになる（決めたこと2・3）。提供元の API は呼ばないので、アクセストークンなどは保存しない |
| `verification` | Better Auth が OAuth の state などに使う | |

## 決めたこと

1. **表示名**：提供元のプロフィールの名前（Google の氏名、LINE の表示名）は使わない。登録時に「参加者」＋6桁の乱数（例：参加者482193）を振る。既にある表示名と重なったら振り直す（連番にすると登録の順番と人数が外から読めるため乱数にする）。実名が画面に出るのを避けるため（仕様「個人を特定できる統計を作らない」「実在の人物への誹謗中傷」の趣旨）。表示名を変える画面は別の Issue
2. **メールアドレス**：提供元が何を返しても、`user.email` には常に `{provider}-{accountId}@users.invalid` を入れる（Better Auth の `mapProfileToUser`）。Better Auth の `user.email` は一意で、OAuth ではまずメールで既存の利用者を探すため、本物のメールを入れると、同じメールの Google と LINE がぶつかってログインに失敗する。メールは画面に出さず、連絡にも使わない
3. **アカウントの結び付け**：Google と LINE のアカウントを自動では結び付けない（`accountLinking` を切る）。2 によりメールが提供元ごとに分かれるので、同じ人が両方で入ると別の利用者になる。乗っ取りの経路を構造で作らない
4. **プロフィール画像**：提供元の画像（Google は本人の顔写真のことが多い）は保存しない（`mapProfileToUser` で `image` を入れない）
5. **セッション**：Better Auth の既定（HttpOnly・SameSite=Lax の Cookie、7日、期限が近づいたら延ばす）。本番は Secure。ログアウトは POST だけで受け付ける（GET では切らない）
6. **戻り先の判定**：`next`（ログインのあとに戻るパス）は、`src/lib/domain/` の純粋な関数 `safeNext(next, origin)` で判定する。`new URL(next, origin)` で解決し、`origin` が自サイトと同じときだけ `pathname + search + hash` を返し、それ以外（`//evil.example`、`/\evil.example`、`https://evil.example`、タブや改行を含むものなど）は `/` を返す。`next` を使う場所（`/login` の表示、ログインの POST、提供元からの戻り先の組み立て、`/test-login`）では、どこでもサーバー側でこの関数を通す。Better Auth の `trustedOrigins` の確認には頼らない
7. **ログインが要るページ**：`hooks.server.ts` でセッションを `locals.user` に入れる。ログインが要るページは、ログインしていなければ `/login?next=<元のパス>` へ送る
8. **ログインの画面**：`/login` に「Googleでログイン」「LINEでログイン」。押すと POST で自前のエンドポイントに送り、Better Auth の `signInSocial` で提供元へリダイレクトする（戻り先は `safeNext` を通した `next`）。すでにログインしている人が `/login` を開いたら、`next` へ送る
9. **baseURL**：Better Auth の `baseURL` は環境変数 `BETTER_AUTH_URL` で決める。手元は `http://localhost:5173`（`pnpm dev`）、画面のテストは `http://localhost:4173`、本番とステージングはデプロイの Issue で決める。`trustedOrigins` は `baseURL` だけ。提供元に渡す戻り先は `{BETTER_AUTH_URL}/api/auth/callback/{google|line}`
10. **テスト用のログイン**：`/test-login?name=<名前>`。次の2つがどちらも満たされるときだけ動き、それ以外は 404。
    - 環境変数 `TEST_LOGIN` が `1`（wrangler.jsonc にも `.dev.vars` にも書かない。画面のテストの webServer が `--var TEST_LOGIN:1` で起動するときだけ立てる）
    - 要求のホストが `localhost` か `127.0.0.1`（本番で変数を誤って立てても、公開された URL では動かない）
    - `name` は英数字とハイフンだけ（1〜32文字）。それ以外は 400
    - 名前ごとに `test-{name}@test.invalid` の利用者を作り（あれば使い回す）、`testUtils` の `login` でセッションを作って Cookie を返す。表示名は名前そのまま
    - `/test-login` の応答のページに「テスト用のログイン：{名前}」と出す。`next` があれば、そのリンクも出す
    - `testUtils` は本番の auth インスタンスには入れず、テスト用のログインのエンドポイントの中だけで作る
11. **秘密の値**：`BETTER_AUTH_SECRET`、`GOOGLE_CLIENT_ID`、`GOOGLE_CLIENT_SECRET`、`LINE_CLIENT_ID`、`LINE_CLIENT_SECRET`。本番とステージングは `wrangler secret`、手元は `.dev.vars`（`.gitignore` に `.dev.vars` を足す。`.dev.vars.example` に名前だけ置く）。画面のテストはダミーの値を `--var` で渡す
12. **わたしの記録**：ログインできたことを確かめる最小のページ `/watashi`（PcLaw の右上「わたしの記録」）。表示名とログアウトを出す。ログインが要るページの最初の例にもなる

## 画面のテストの起動

- いまの webServer（`pnpm db:reset && pnpm build && pnpm preview`）の `preview` に、`--var TEST_LOGIN:1` とダミーの OAuth の値を足したスクリプト `preview:test` を作り、Playwright はそれを使う
- テスト用のログインが無効のときに 404 になることは、`TEST_LOGIN` を立てない2つ目の webServer で確かめる。2つ目は build も db:reset もせず、1つ目が作ったビルドを `wrangler dev .svelte-kit/cloudflare/_worker.js --port 4174 --persist-to .wrangler/state-nologin` で起動するだけ（Playwright は webServer を順に起動するので、1つ目のビルドが済んでから起動させる）。404 は D1 に触れる前に返すので、2つ目の D1 にマイグレーションは当てない。同じ D1 のファイルを2つのサーバーで開かない（Issue #17）

## テストの方針

- 「Googleでログイン」「LINEでログイン」を押すと、提供元の認可の URL（`accounts.google.com`／`access.line.me`）へ、ダミーの client_id と自分の戻り先を付けてリダイレクトされる（提供元までは行かない）
- テスト用のログインで入ると `/watashi` に表示名が出て、ログアウトすると `/watashi` が `/login?next=/watashi` へ送られる
- `TEST_LOGIN` がないサーバーでは `/test-login` が 404
- `next` に外のサイト（`//evil.example`、`/\evil.example`、`https://evil.example`）を渡しても、外へは送らない（信頼の境界の入力。`safeNext` の単体テストと、ログインの POST の画面のテスト）
- 表示名・メール・画像（決めたこと1・2・4）は、`mapProfileToUser` に渡す関数の単体テストで確かめる
