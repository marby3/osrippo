# 解決策（設計書）

Issue #34。マイグレーション（表の追加、`actions` の作り直し、トリガーの作り直し）を足すので Careful。仕様の正は [docs/spec.md](../spec.md) の「課題・解決策・法案」の解決策の項と「審議・評価・修正案」。課題は [docs/spec/25.md](25.md)、通報は [docs/spec/28.md](28.md)、似た課題と統合は [docs/spec/30.md](30.md)。

仕様書にない次のことは、2026-11-03 にユーザーと決めた（仕様書のドキュメントへの反映はユーザー側）。

- 解決策は本文だけ（1〜400字、改行可）。題名はない
- 「考えが変わった」は、仕様（spec.md:135）と同じく「読んだ人が、自分の理解を変えた投稿に付ける」もの。賛成・反対の立場の変化ではない。解決策は法案に結び付かないので立場を記録せず、付け外しして数を出すだけにする。書いた人の実績と通知に数えるかは、フェーズ4・5で決める
- 「わかる」と「考えが変わった」は別に付け外しでき、同じ人が両方を押せる。自分の解決策には押せない
- 課題のページには解決策を「わかる」の多い順（同じなら新しい順）に3件出し、「解決策をすべて見る（N件）」で全部の一覧へ
- 解決策の通報と非表示は、次の Issue（v0.2 の前）
- 似た課題から「これに『わかる』を付ける」で来た人には、課題のページに「解決策を書く」への案内を出す（仕様の「補足」の、いまの形。docs/spec/30.md）
- 課題を統合したら、元の課題の解決策も統合先へ移す
- 一覧に解決策の数と「解決策あり」の絞り込み（画面の案）

### レビューを受けて提案すること（STOP 1 で確認）

- 回線（IP）ごとの上限を、課題と同じ形でかける（決めたこと2・5）
- 断るときの文言を、「わかる」と「考えが変わった」を合わせた1つにそろえる（数えを合わせるため）。公開済みの課題の「わかる」と締め出しの文言も変わる（決めたこと5・9）

## 範囲

- 入れる：解決策を書く、課題のページの解決策、解決策の一覧、「わかる」と「考えが変わった」、上限と締め出し、似た課題から来た人への案内、統合で移す、一覧の解決策の数と絞り込み
- 入れない：解決策の通報と非表示（次の Issue）、解決策の編集と削除、法案からの引用（フェーズ3）、議員のダッシュボード（フェーズ5）、実績と通知（フェーズ4・5）

## 表

`drizzle/0006_*.sql`。

| 表 | 列 | 備考 |
| --- | --- | --- |
| `solutions` | `id`（整数、自動採番）、`issue_id`（`issues` への外部キー）、`user_id`（`user` への外部キー）、`body`、`created_at` | 索引（`issue_id`） |
| `solution_reactions` | `solution_id`（`solutions` への外部キー）、`user_id`（`user` への外部キー）、`kind`（`support`＝わかる／`changed`＝考えが変わった）、`created_at` | 主キー（`solution_id`, `user_id`, `kind`）。外すと行を消す |
| `actions` | `kind` に `solution_post`・`reaction_add`・`reaction_remove` を足す | 下の注意 |

- `actions.target_id` は、`solution_post` と `reaction_add`・`reaction_remove` では解決策の番号（`issue_post`・`support_*` は課題の番号。`kind` で分かれるので重ならない）
- **マイグレーションの順**：`CREATE TABLE solutions`・`solution_reactions` → `actions` の作り直し → トリガーの作り直し。作り直した `actions` に索引（`actions_user`・`actions_ip`・`actions_target`）が作り直されていることを確かめる。`schema.ts` のトリガーの注意書きを 0006 を指すように直す
- **`actions` の作り直し**：`kind` に CHECK があるので、値を足すと drizzle-kit は表を作り直す SQL（新しい表を作って写し、元を消して名前を変える）を出す。`actions` を参照する外部キーとトリガーはないので、作り直しても消える行はない（docs/spec/28.md の注意は、ほかの表から参照される `user`・`issues` のこと）。生成された SQL が `actions` 以外の表を作り直していないことを確かめてからコミットする
- `solutions` と `solution_reactions` の外部キーの `ON DELETE` は既定（退会は「あとで決めること」）

## 決めたこと

1. **解決策を書く `/kadai/[id]/kaiketsu/kaku`**：ログインが要る（`requireUser`）。本文の欄（`textarea`、400字まで）、Turnstile、「投稿する」。投稿できたら `/kadai/[id]` へ 303
   - ページ（load）：課題の番号の形が違う・ない・非表示なら 404。統合済みなら統合先の書く画面へ 308
   - 投稿（POST）の確かめる順：課題の番号と課題があるか（404。ログインより先）→ ログイン → 国 → 締め出し → Turnstile → 入力 → 課題の状態（非表示・統合済みは 403 と「この課題には解決策を書けません」）→ レート制限 → 保存
   - 保存は `INSERT INTO solutions … SELECT … WHERE EXISTS (SELECT 1 FROM issues WHERE id = ? AND status IN ('visible', 'restored'))` の1文で行い、入った行がなければ 403（このとき `actions` に `solution_post` を書かない）（画面を開いてから送るまでに統合・非表示になっても、元の課題に解決策が残って見えなくなることがないように）
   - 本文（信頼の境界）：docs/spec/25.md 決めたこと2の判定（前後の空白を除き、改行を `\n` にそろえ、1〜400字（コードポイント）、制御文字と文字の向きを変える文字なし、改行は可）
   - 誤りがあれば保存せず、欄の横に理由を出す（入力は残し、Turnstile は作り直す）
2. **レート制限**（docs/spec/25.md 決めたこと10・11と同じ数え方。`actions` の `solution_post` から数える）
   - 1アカウント24時間に10件（超えたら違反に数える）。文言「解決策は24時間に10件まで書けます。しばらくしてからお試しください」
   - 登録から24時間のアカウントは24時間に3件（違反に数えない）。文言「登録したばかりのあいだは、解決策は24時間に3件まで書けます。{M月D日 H時mm分}から次の解決策を書けます」
   - 1回線24時間に20件（違反に数えない。課題と同じ）。文言「この回線から書ける解決策の数を超えました。しばらくしてからお試しください」
3. **課題のページの解決策**：「解決策 N件」と「解決策を書く」（`/kadai/[id]/kaiketsu/kaku` へのリンク）。解決策を「わかる」の多い順、同じなら新しい順（`id` の大きい順）に3件。各解決策に本文、「わかる N」と「考えが変わった N」のボタン。4件以上なら「解決策をすべて見る（N件）」（`/kadai/[id]/kaiketsu`）
   - 課題が非表示で、見る人が書いた本人・運営でないときは、解決策も出さない（docs/spec/28.md 決めたこと4）。非表示の課題を書いた本人・運営が見るときは、解決策のボタンの代わりに数だけを出し、「解決策を書く」も出さない
4. **解決策の一覧 `/kadai/[id]/kaiketsu`**：同じ並びで50件ごと（`?page=2`。`page` の形と、2ページ目以降で解決策がないときは 404。docs/spec/25.md 決めたこと4と同じ）。課題の題名（課題のページへのリンク）を上に出す
   - 課題がないときは 404、統合済みは統合先の一覧へ 308
   - 課題が非表示で、見る人が書いた本人・運営でないときは、docs/spec/28.md 決めたこと4と同じく、`<title>` と見出しを「非表示の課題」にし、文言と `/unei` へのリンクだけを出し（200）、`noindex` を付ける。本人・運営には解決策を出し（ボタンの代わりに数だけ）、`noindex` を付ける
5. **「わかる」と「考えが変わった」**（`?/react` の POST。課題のページと解決策の一覧の両方に置く）：フォームの値は `solution`（解決策の番号）、`kind`（`support`／`changed`）、`op`（`add`／`remove`）。docs/spec/25.md 決めたこと6と同じく、いまと同じ状態への操作は何もせず数えない。JS がなくても動き、JS があればページを読み直さずに数と状態を変える
   - 確かめる順：課題の番号と課題があるか（404）→ ログイン（していなければ `/login?next=` に今のページ）→ 国 → 締め出し → 入力（形が違えば 400。解決策がその課題のものでなければ 404。統合したあとは解決策が統合先へ移っているので、元の課題への操作はここで 404 になる）→ 課題の状態（非表示・統合済みは 403）→ 自分の解決策（403 と「自分の解決策には押せません」）→ いまと同じ状態か（同じなら何もせず、数えない。レート制限より先に確かめる）→ レート制限 → 保存
   - ボタンは `aria-pressed`。自分の解決策には、ボタンの代わりに数だけを出す
   - 読み上げ名：解決策のボタンには、画面には出さない前置き「この解決策に」を付け（読み上げ名は「この解決策に わかる 48」）、`aria-describedby` で本文を結び付ける。課題そのものの「わかる」（読み上げ名「わかる 214」）と区別するため。各解決策は `<article>` で囲む
   - レート制限：課題の「わかる」と合わせて、1アカウント24時間に50回、5分に10回（`support_add`・`support_remove`・`reaction_add`・`reaction_remove` を合わせて数える）。超えたら違反に数える
   - 同じ解決策への `reaction_add`（「わかる」「考えが変わった」のどちらでも）：同じ回線から24時間に3アカウントまで（docs/spec/25.md 決めたこと10の「同じ課題への『わかる』」と同じ数え方。違反に数えない）。文言「この回線からは、この解決策にこれ以上押せません」
   - 数えを合わせるので、断るときの文言も、課題の「わかる」と解決策で同じものにそろえる：「『わかる』と『考えが変わった』は、合わせて24時間に50回まで押せます。しばらくしてからお試しください」「短いあいだに『わかる』や『考えが変わった』を何度も押しました。しばらくしてからお試しください」（docs/spec/25.md の文言を直す。既存のテストの文言も直す）
6. **似た課題から来た人への案内**：課題を書く画面の「これに『わかる』を付ける」で移るとき、`/kadai/[id]?from=nita` に移る。課題のページは、`from=nita` で、見る人がログインしていてその課題に「わかる」を付けていて、課題が一覧に出る状態のときだけ、上に「『わかる』を付けました。考えがあれば、解決策として書いてください」と「解決策を書く」を出す（URL を共有された人などに、事実と違う案内を出さないように）。案内を出したら、URL から `from` を消す（`replaceState`。読み直しで何度も出さないように）。`from` がほかの値なら無視する
7. **統合で移す**：トリガー `issues_status_log` を作り直す。0005 の3つの文（記録を書く、「わかる」を写す、`merged_into` を付け替える）はそのまま残し、統合（`merged`）のとき `UPDATE solutions SET issue_id = NEW.merged_into WHERE issue_id = NEW.id` を足して、同じ文の中で行う（docs/spec/30.md 決めたこと4と同じ仕組み。`NEW.merged_into IS NOT NULL` のときだけ）
8. **一覧（`/kadai`）**：行に解決策の数を出す（PC は「解決策」の列、スマホは「わかる N ・ 解決策 N」）。解決策の数は相関サブクエリ（`(SELECT count(*) FROM solutions WHERE issue_id = issues.id)`）で取り、「解決策あり」は `EXISTS` で絞る（`issue_supports` と同じ JOIN に足すと行が掛け算で増え、「わかる」の数と並びが狂うため）。`kaiketsu` は `sort`・`page` と組み合わせられ、絞り込みを変えたら1ページ目に戻る（docs/spec/25.md 決めたこと4と同じ）。絞り込みに「解決策あり」（`?kaiketsu=ari`）を足す。0件のときの文言は「解決策のある課題はまだありません」。絞り込みは「すべて」「今回のお題」「解決策あり」から1つを選ぶ（`topic` と `kaiketsu` を一緒には受け付けず、両方あれば 404）。`kaiketsu` は `ari` だけを受け付け、それ以外は 404（信頼の境界）
9. **言葉**：`ja.ts` の `solution` に置く。締め出しの文言（`guard.banned`）を全文「制限を何度も超えたため、{M月D日 H時mm分}まで、課題や解決策の投稿、『わかる』『考えが変わった』、通報ができません。」に直す（既存のテストの文言も直す）

## テストの方針

- 本文の判定は docs/spec/25.md の判定をそのまま使う（Vitest で、解決策の上限の400字と改行を確かめる）
- 上限と締め出し、並び、統合で移すことは、画面のテストで確かめる（テスト用のログインの `days` で登録した日を変える）
- 既存のテストのうち、課題の「わかる」を `/^わかる/` で探すものは、解決策のボタンの読み上げ名が「この解決策に」で始まるので、そのまま通る。似た課題のテストの `toHaveURL(/kadai/[id])` は、`from=nita` を `replaceState` で消したあとに一致する（`toHaveURL` は待つ）
- 信頼の境界：本文、解決策の投稿の課題の番号（形の違う番号、非表示・統合済みの課題への POST）、`?/react` の `solution`・`kind`・`op`、解決策の一覧の `page`、一覧の `kaiketsu`
