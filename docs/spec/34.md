# 解決策（設計書）

Issue #34。マイグレーション（表の追加、`actions` の作り直し、トリガーの作り直し）を足すので Careful。仕様の正は [docs/spec.md](../spec.md) の「課題・解決策・法案」の解決策の項と「審議・評価・修正案」。課題は [docs/spec/25.md](25.md)、通報は [docs/spec/28.md](28.md)、似た課題と統合は [docs/spec/30.md](30.md)。

仕様書にない次のことは、2026-11-03 にユーザーと決めた（仕様書のドキュメントへの反映はユーザー側）。

- 解決策は本文だけ（1〜400字、改行可）。題名はない
- 「考えが変わった」は、仕様（spec.md:135）と同じく「読んだ人が、自分の理解を変えた投稿に付ける」もの。賛成・反対の立場の変化ではない。解決策は法案に結び付かないので立場を記録せず、付け外しして数を出すだけにする。書いた人の実績と通知に数えるかは、フェーズ4・5で決める
- 「わかる」と「考えが変わった」は別に付け外しでき、同じ人が両方を押せる。自分の解決策には押せない
- 課題のページには解決策を「わかる」の多い順（同じなら新しい順）に3件出し、「解決策をすべて見る（N件）」で全部の一覧へ
- 解決策の通報と非表示は、次の Issue（v0.2 の前）
- 似た課題から「これに『わかる』を付ける」で来た人には、課題のページに「解決策を書く」への案内を出す（仕様の「補足」の、いまの形。docs/spec/30.md）
- 課題を統合したら、元の課題の解決策も統合先へ移す
- 一覧に解決策の数と「解決策あり」の絞り込み（画面の案）

## 範囲

- 入れる：解決策を書く、課題のページの解決策、解決策の一覧、「わかる」と「考えが変わった」、上限と締め出し、似た課題から来た人への案内、統合で移す、一覧の解決策の数と絞り込み
- 入れない：解決策の通報と非表示（次の Issue）、解決策の編集と削除、法案からの引用（フェーズ3）、議員のダッシュボード（フェーズ5）、実績と通知（フェーズ4・5）

## 表

`drizzle/0006_*.sql`。

| 表 | 列 | 備考 |
| --- | --- | --- |
| `solutions` | `id`（整数、自動採番）、`issue_id`（`issues` への外部キー）、`user_id`（`user` への外部キー）、`body`、`created_at` | 索引（`issue_id`） |
| `solution_reactions` | `solution_id`（`solutions` への外部キー）、`user_id`（`user` への外部キー）、`kind`（`support`＝わかる／`changed`＝考えが変わった）、`created_at` | 主キー（`solution_id`, `user_id`, `kind`）。外すと行を消す |
| `actions` | `kind` に `solution_post`・`reaction_add`・`reaction_remove` を足す | 下の注意 |

- **`actions` の作り直し**：`kind` に CHECK があるので、値を足すと drizzle-kit は表を作り直す SQL（新しい表を作って写し、元を消して名前を変える）を出す。`actions` を参照する外部キーとトリガーはないので、作り直しても消える行はない（docs/spec/28.md の注意は、ほかの表から参照される `user`・`issues` のこと）。生成された SQL が `actions` 以外の表を作り直していないことを確かめてからコミットする
- `solutions` と `solution_reactions` の外部キーの `ON DELETE` は既定（退会は「あとで決めること」）

## 決めたこと

1. **解決策を書く `/kadai/[id]/kaiketsu/kaku`**：ログインが要る（`requireUser`）。課題が一覧に出る状態（`visible`・`restored`）でなければ 404。本文の欄（`textarea`、400字まで）、Turnstile、「投稿する」。投稿できたら `/kadai/[id]` へ 303
   - 確かめる順：ログイン → 国 → 締め出し → Turnstile → 入力 → レート制限 → 保存（docs/spec/25.md 決めたこと12と同じ）
   - 本文（信頼の境界）：docs/spec/25.md 決めたこと2の判定（前後の空白を除き、改行を `\n` にそろえ、1〜400字（コードポイント）、制御文字と文字の向きを変える文字なし、改行は可）
   - 誤りがあれば保存せず、欄の横に理由を出す（入力は残し、Turnstile は作り直す）
2. **レート制限**（docs/spec/25.md 決めたこと10・11と同じ数え方。`actions` の `solution_post` から数える）
   - 1アカウント24時間に10件（超えたら違反に数える）
   - 登録から24時間のアカウントは24時間に3件（違反に数えない。次に書ける時刻を出す）
   - 回線ごとの上限はかけない
3. **課題のページの解決策**：「解決策 N件」と「解決策を書く」（`/kadai/[id]/kaiketsu/kaku` へのリンク）。解決策を「わかる」の多い順、同じなら新しい順（`id` の大きい順）に3件。各解決策に本文、「わかる N」と「考えが変わった N」のボタン。4件以上なら「解決策をすべて見る（N件）」（`/kadai/[id]/kaiketsu`）
   - 課題が非表示で、見る人が書いた本人・運営でないときは、解決策も出さない（docs/spec/28.md 決めたこと4）。非表示・統合済みの課題には「解決策を書く」を出さない
4. **解決策の一覧 `/kadai/[id]/kaiketsu`**：同じ並びで50件ごと（`?page=2`。`page` の形と、2ページ目以降で解決策がないときは 404。docs/spec/25.md 決めたこと4と同じ）。課題の題名（課題のページへのリンク）を上に出す。課題が見せられないとき（非表示で本人・運営でない、統合済みは統合先の一覧へ 308、ない）は課題のページと同じ扱い
5. **「わかる」と「考えが変わった」**（`?/react` の POST。課題のページと解決策の一覧の両方に置く）：フォームの値は `solution`（解決策の番号）、`kind`（`support`／`changed`）、`op`（`add`／`remove`）。docs/spec/25.md 決めたこと6と同じく、いまと同じ状態への操作は何もせず数えない。JS がなくても動き、JS があればページを読み直さずに数と状態を変える
   - 確かめる順：課題の番号と課題があるか（404）→ ログイン（していなければ `/login?next=` に今のページ）→ 国 → 締め出し → 入力（形が違えば 400。解決策がその課題のものでなければ 404）→ 課題の状態（非表示・統合済みは 403）→ 自分の解決策（403 と「自分の解決策には押せません」）→ レート制限 → 保存
   - ボタンは `aria-pressed`。自分の解決策には、ボタンの代わりに数だけを出す
   - レート制限：課題の「わかる」と合わせて、1アカウント24時間に50回、5分に10回（`support_add`・`support_remove`・`reaction_add`・`reaction_remove` を合わせて数える）。超えたら違反に数える。文言は「『わかる』と『考えが変わった』は、合わせて24時間に50回まで押せます」と「短いあいだに何度も押しました。しばらくしてからお試しください」（課題の「わかる」の文言は変えない）
6. **似た課題から来た人への案内**：課題を書く画面の「これに『わかる』を付ける」で移るとき、`/kadai/[id]?from=nita` に移る。課題のページは `from=nita` のときだけ、上に「『わかる』を付けました。考えがあれば、解決策として書いてください」と「解決策を書く」を出す（ログインしていて、課題が一覧に出る状態のとき）。`from` がほかの値なら無視する
7. **統合で移す**：トリガー `issues_status_log` を作り直し、統合（`merged`）のとき `UPDATE solutions SET issue_id = NEW.merged_into WHERE issue_id = NEW.id` も同じ文の中で行う（docs/spec/30.md 決めたこと4と同じ仕組み。`NEW.merged_into IS NOT NULL` のときだけ）
8. **一覧（`/kadai`）**：行に解決策の数を出す（PC は「解決策」の列、スマホは「わかる N ・ 解決策 N」）。絞り込みに「解決策あり」（`?kaiketsu=ari`）を足す。絞り込みは「すべて」「今回のお題」「解決策あり」から1つを選ぶ（`topic` と `kaiketsu` を一緒には受け付けず、両方あれば 404）。`kaiketsu` は `ari` だけを受け付け、それ以外は 404（信頼の境界）
9. **言葉**：`ja.ts` の `solution` に置く

## テストの方針

- 本文の判定は docs/spec/25.md の判定をそのまま使う（Vitest で、解決策の上限の400字と改行を確かめる）
- 上限と締め出し、並び、統合で移すことは、画面のテストで確かめる（テスト用のログインの `days` で登録した日を変える）
- 信頼の境界：本文、`?/react` の `solution`・`kind`・`op`、解決策の一覧の `page`、一覧の `kaiketsu`
