# 全文検索（設計書）

Issue #38。検索用の表（FTS5）を足し、外から来る検索の言葉（信頼の境界）を受けるので Careful。仕様の正は [docs/spec.md](../spec.md) の「通知・検索・共有」（法令名、条文、課題、解決策、法案を全文検索できる）と「技術構成」（D1 の FTS5。3文字以上は trigram、2文字は文字 bigram の2つの表で引く。行は項・号ごと。フェーズ0で確認）。

2026-11-03 にユーザーと決めたこと（仕様書のドキュメントへの反映はユーザー側）：

- 探せるのは法令名・条文・課題・解決策。法案は v0.3 で法案を作るときに足す。非表示の課題・解決策と統合した課題は出さない
- 入口は2つ。課題の一覧の「課題を探す」（課題だけ。並び・絞り込みと組み合わせる）と、全体を探す `/kensaku`（条文・課題・解決策を種類ごとの欄に分けて出す。法令名も出す）。入口はトップページと法令のページ。`kensaku` は URL の単語の一覧（spec.md「URLの設計」）に足す
- 条文は、いま施行されている版だけを探す。結果に法令名・位置（「第4条第2項」）・該当部分を出し、法令のページのその条へリンクする
- 言葉は2文字以上（1文字は「2文字以上で入力してください」）。2文字は bigram、3文字以上は trigram の表で引く。空白で区切るとすべての言葉を含むもの（AND）。言葉は5つまで、全体で60字まで
- 並び：条文は法令の順・条の順、課題と解決策は「わかる」の多い順。種類ごとに20件ずつ出し、「もっと見る」で続き

## 範囲

- 入れる：検索用の表と、その行の作り方（法令の取り込み、課題・解決策の投稿）、`/kensaku`、課題の一覧の「課題を探す」、トップページと法令のページの入口
- 入れない：法案の検索（v0.3）、IF世界の条文の検索（IF世界を作るとき）、過去の版の検索、並びの当てはまり具合（bm25）、検索の回数の制限（公開のときに Cloudflare の WAF。デプロイの Issue）、本番の取り込みの仕組み（MS-R1 のバッチ。取り込みの Issue）

## 表

`drizzle/0008_*.sql`。drizzle-kit は FTS5 の仮想表を扱わないので、仮想表はマイグレーションに手で書く（`schema.ts` には書かない。読み書きは `sql` で行う）。

```sql
CREATE VIRTUAL TABLE search_trigram USING fts5 (kind UNINDEXED, ref_id UNINDEXED, text, tokenize = 'trigram');
CREATE VIRTUAL TABLE search_bigram USING fts5 (kind UNINDEXED, ref_id UNINDEXED, text, tokenize = 'unicode61 remove_diacritics 0');
```

- `kind`：`provision`（`ref_id` は `provision_versions.id`。条・項・号の行）、`issue`（`issues.id`）、`solution`（`solutions.id`）
- `text`：探す文字列を、検索の言葉と同じ規則でそろえたもの（決めたこと1の `normalizeText`）。`search_bigram` には、そろえた文字列を2文字ずつの組に分け、空白でつないだものを入れる（`unicode61` が空白で区切るので、組がそのまま1つの言葉になる）
  - 条：見出し（見出しのない条は行を作らない）。条の見出しは条の版の行にあるので、項・号とは別の行にする（版の切り替わりがずれても、引くときに「いまの版で有効な行」で絞れるように）
  - 項・号：本文
  - 課題：題名・困っている人・具体例を、それぞれ別の行にする（同じ `ref_id`。欄の境目をまたいで当たらないように。言葉どうしの AND は `ref_id` で結ぶので、別の欄にある言葉でも当たる）
  - 解決策：本文
- MATCH に渡す言葉は、`sql` テンプレートのバインド変数で渡す（文字列をつないで SQL を作らない）
- 表示中かどうか（非表示・統合）は、検索の表には持たず、引くときに元の表と結んで絞る（状態が変わるたびに検索の表を直さなくてよいように）

### 行の作り方

- **法令**：`seedStatements`（取り込み）で、`provision_versions` のすべての行（項・号）の検索の行も作る。どの版の行かは引くときに決める（いま施行されている版で有効な行だけを結んで出す。施行予定の版が施行されても、検索の表を作り直さずに済む）。1文 100KB 未満の約束は今の分け方に乗る
- **課題・解決策**：投稿を保存したあとに、同じ処理の中で検索の行を足す（`createIssue`・`createSolution`）。課題の保存と検索の行の追加は別の文なので、間で失敗すると検索に出ない課題ができる（一覧には出る）。ゆるしてよい（D1 の `batch` ならひとまとめにできるが、テストで使う node:sqlite の Drizzle と共通の型に `batch` がないため。docs/spec/28.md の実装のときと同じ事情）
- 本番にはまだ課題・解決策がないので、マイグレーションで既存の行を埋め直さない（埋め直しが要るときはスクリプトを作る。あとで決めること）

## 決めたこと

1. **そろえ方**（`src/lib/domain/search.ts`、純粋な関数）：本文と検索の言葉で同じ規則を使う
   - `normalizeText(s)`：NFKC にそろえ、英字を小文字にし、句読点・記号（`\p{P}`、`\p{S}`）と空白（改行を含む）を除く。本文（検索の行の `text`）はこれで作る（例：「クーリング・オフ」は「クーリングオフ」になり、言葉の側と同じになる）
   - 検索の言葉：`q` を空白（全角を含む）で言葉に分け、言葉ごとに `normalizeText`
   - bigram の組：`normalizeText` したものを、となり合う2文字ずつに分ける
2. **検索の言葉の判定**（信頼の境界）：形が違うときは結果を出さず、理由を出す（状態コードは 200。検索の欄に打った言葉なので、404 にしない）
   - `q` は前後の空白を除いて0〜60字（コードポイント。そろえる前に数える）。制御文字は、課題の入力と同じ判定（`src/lib/domain/issues.ts` の `CONTROL`。文字の向きを変える書式文字を含む）
   - 言葉の数は、空白で分けた数（そろえる前）で1〜5つ。そろえたあとの言葉は、どれも2文字以上・30字以下（NFKC で長くなる文字があるので、そろえたあとにも上限をかける）
   - 空：何も探さない（`/kensaku` は欄だけ、課題の一覧はふつうの一覧）
   - そろえたあと1文字以下の言葉がある（記号だけの言葉を含む）：「2文字以上で入力してください」
   - 61字以上、言葉が6つ以上、そろえたあと31字以上の言葉がある：「60字まで、言葉は5つまでで入力してください」
   - 制御文字：「使えない文字が入っています」
3. **引き方**：言葉ごとに、2文字なら `search_bigram`、3文字以上なら `search_trigram` を `MATCH` で引く（言葉は `"` で囲み、中の `"` は2つ重ねる）。言葉どうしは `INTERSECT` で AND にする
4. **`/kensaku?q=…`**：だれでも見られる。`noindex`。検索の欄（「探す」）と、次の欄を上から出す
   - **法令**：題名にすべての言葉を含む法令（そろえた題名で比べる）。法令のページへのリンク
   - **条文**：いま施行されている版（`currentRevision`）で有効な条・項・号のうち、当てはまるもの。各行に法令名、位置（条の見出しで当たったら「第4条」、項・号なら「第4条第2項第1号」。`articleLabel`・`itemLabel` と同じ書き方）、該当部分（下の決めたこと6）。リンクは `/hourei/[lawId]#jo-[条の番号]`。並びは法令の順（`TARGET_LAWS` の順＝法令の番号の順）、条・項・号の番号の順（`compareNum`）
   - 条文は SQL で並べられない（番号の比べ方が `compareNum`）ので、いまの版で有効な行に絞ったあと（絞る前に切ると正しい行が落ちる）、`LIMIT 1001` で読んでアプリで並べる。件数は別に数える。1000件を超えるときは、条文の欄と `shurui=jobun` のページの上に「1000件を超えました。言葉を足してしぼりこんでください」と出し、`shurui=jobun` で見られるのは並べた1000件（20ページ）まで（21ページ目以降は 404）
   - **課題**：一覧に出る課題（`visible`・`restored`）のうち当てはまるもの。題名（課題のページへのリンク）、わかるの数、該当部分。「わかる」の多い順、同じなら新しい順
   - **解決策**：表示中の解決策で、課題も一覧に出るもの。該当部分、課題の題名、わかるの数。リンクは `/kadai/[課題]/kaiketsu#kaiketsu-[番号]`（解決策の一覧には表示中の解決策が全部並ぶので、課題のページの上位3件に入らなくても着く）。「わかる」の多い順、同じなら新しい順
   - 各欄は20件まで。見出しに件数（「条文 N件」）。20件を超えるときは「もっと見る（N件）」で `/kensaku?q=…&shurui=jobun|kadai|kaiketsu` へ。その種類だけを50件ごとに出す（`?page=2`。`page` の形は docs/spec/25.md 決めたこと4と同じ。形が違う・課題などがないページは 404）。`shurui` はこの3つだけで、それ以外は 404（信頼の境界）
   - 当てはまるものがない欄は「見つかりませんでした」
5. **課題の一覧の「課題を探す」**（`/kadai?q=…`）：課題の欄（`kind = issue`）だけを引き、今の並び・絞り込み・ページと組み合わせる（`listHref` に `q` を足す）。言葉の判定は決めたこと2と同じで、形が違えば一覧の上に理由を出し、一覧は空にする。当てはまるものがなければ「見つかりませんでした」。どちらの場合も1ページ目は 200 で、2ページ目以降は docs/spec/25.md 決めたこと4と同じく課題がなければ 404。`q` があるときは `noindex` を付ける
6. **該当部分**：元の文（そろえる前）から、最初の言葉が最初に出るところ（英字の大文字・小文字は区別しない）の前後を切り出す（前20字・後60字ほど。端は「…」）。元の文で見つからないとき（全角と半角の違い、記号をはさむ書き方など）は、文の頭から80字。切り出した中で、どの言葉でも当たる部分（大文字・小文字は区別しない）を `<mark>` で囲む（文字列を区切って並べる。`{@html}` は使わない）
7. **入口**：トップページに `/kensaku` の検索の欄（「法令や課題を探す」）。法令のページの上に `/kensaku` へのリンク（「法令や課題を探す」）
8. **言葉**：`ja.ts` の `search` に置く

## テストの方針

- 言葉のそろえ方・判定・bigram の組の作り方、該当部分の切り出しは Vitest
- 引き方（trigram と bigram、AND、表示中だけ、いまの版だけ、並び）は、マイグレーションと取り込みを当てた node:sqlite で確かめる（node:sqlite の SQLite は FTS5 の trigram を使える）
- 画面は Playwright の2幅で、`/kensaku` の各欄と「もっと見る」、課題の一覧の「課題を探す」、入口を確かめる
- 信頼の境界：`q`、`shurui`、`page`

## あとで決めること

- 本番で、取り込みのバッチ（MS-R1）が検索の行も作ること（取り込みの Issue）
- 既存の課題・解決策の検索の行を埋め直すスクリプト（要るとき）
- 当てはまり具合（bm25）の並び、検索の回数の制限
- 課題・解決策を消す仕組みを作るときに、検索の行も消す（非表示にした本文は、検索の表には残る。引くときに絞るので出ない）
- D1 は仮想表（FTS5）のある DB を `wrangler d1 export` で書き出せない。バックアップは Time Travel で足りるか（デプロイの Issue）
- D1 で trigram の表を作れることは、フェーズ0で確かめた（spec.md「技術構成」）。手元の wrangler の D1 でも、このマイグレーションを当てて確かめる
