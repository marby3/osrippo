# 修正案（出す・取り込む・先議）（設計書）

Issue #68。マイグレーション（表と列の追加）を足すので Careful。仕様の正は [docs/spec.md](../spec.md) の「修正案」。画面の案はない（Issue #63 が決めたラベルに合わせ、既存の質疑のタブと変更点のタブの見た目にそろえる）。法案の版は [docs/spec/45.md](45.md)、賛同は [docs/spec/49.md](49.md)、採決は [docs/spec/65.md](65.md)。

ユーザーと決めたこと（Issue #63 の決めたこと14。仕様書のドキュメントへの反映はユーザー側）。

- 修正案は本案の版に結び付ける。本案が変わったら、提案者が更新するまで受け入れも採決もできない
- 先議の定足数と可決の条件は本案と同じ
- 複数可決して衝突したら、先に出したほうを採る
- 割り当てを済ませる条件は本案の票だけ
- 修正案は法案のページの「修正案」のタブに出し、「修正案を出す」もそのタブに置く。ラベルは「修正案を出す」「取り込む」（Issue #63 テストの作り方）

次のことは仕様書にないので、この Issue の受入基準で確かめる（STOP 1 で確認する）。

- A. 1つの修正案は、1つの条の本文の書きかえ。条の追加と削除、見出しの変更、複数の条をまとめた修正案、本案の変更をやめて基にした版へ戻す修正案は入れない（反対なら本案に反対票を入れる）
- B. 廃止の法令の条は変えられない。変えられる条のない法案（廃止だけの法案）には修正案のタブを出さない
- C. 提案者の名前はカードに出さない（質疑と同じ）。採用されたら、共同起草者として法案の概要に名前を出す。書く画面にそのことを書いておく
- D. 理由は任意で400字まで
- E. 出せるのは登録から7日たった人で、Turnstile が要る。提出者は出せない（提出者が取り込むと、提出者だけの判断で本案を書きかえられるので）。賛同者は出せる
- F. 先議の賛同と更新は3週目だけ。4週目の採決の最中に本案を変えない。**取り込みは3週目の最後の24時間にはできない**（締切の直前に取り込むと、ほかの修正案が更新も賛同も間に合わなくなり、提出者が先議の候補をすべて止められるため）
- G. 取り込まない修正案に「断る」操作は作らない。3週目が終わると、要件に届かなければ採決されずに終わる（仕様のとおり）
- H. 先議の賛同は、提案者と提出者のほかの人ができる。登録から7日は要り、Turnstile は要らない（法案の賛同と同じ）。取り消せる。要件は発議要件の半分の切り上げ
- I. **先議の票は4週目に本案の票と同じ期間に入れ、締切で修正案 → 本案の順に数える**。仕様の「本案より先に採決」「反映したうえで本案を採決」は、数える順のことと読みかえる。票は締切まで非公開で、採決の期間は1週間しかないので、本案に投票するときに修正案の結果は分からない。投票は修正案のタブで行い、Turnstile が要る（仕様「投票のときにもbot対策を通す」。投票の画面からのリンクは #70）
- J. 修正案の票も本案と同じく、投票資格があり割り当てのすべてに投票した人の票を数える。提案者と提出者も投票できる（#65 の決めたこと11 と同じ）
- K. 更新は、本案の版が変わった修正案を、提案者が確かめて書き直す操作。本文を変えたら先議の賛同は数え直し（本案の賛同と同じ考え）。本文を変えず、その条の本案の本文も変わっていなければ賛同を保つ（別の条の取り込みで賛同を失わないように）。同じ条が取り込まれていたら、賛同者の見た変更点と変わるので数え直す
- L. レート制限：修正案は1アカウント24時間に5件、1回線24時間に20件（更新も数える）。先議の賛同は24時間に30回、5分に10回、同じ修正案に同じ回線から24時間に3アカウントまで（法案の賛同と同じ）

## 目的

3週目に修正案を出し、提出者が取り込むか、賛同を集めて先に採決できるようにする。採用された提案者を共同起草者に記録する。

## 範囲

- 入れる：表、修正案のタブ（一覧、出す、更新、取り込む、先議の賛同、先議の票）、発議した版の賛同者、締切のあとの処理の関数（`settleAmendments`）、共同起草者の表示
- 入れない：`settleAmendments` を呼ぶこと（#71）、結果のページに修正案の結果を出すこと（#71）、投票の画面から修正案へのリンクと「修正案が可決すると本文が変わることがあります」の告知（#70）、IF世界の帯と `noindex`（今の法案のページは現実の条文を基にしている。#66 と同じく、#72 で法案のページ全体を決める）、修正案の通報と非表示（#103）、通知（#78）、実績（フェーズ5）

## 決めたこと

1. **時期**（`amendmentOpen(progress)`・`amendmentVoteOpen(progress)`。純粋な関数。`src/lib/domain/amendments.ts`）

   | 操作 | `proposed` | `deliberation` | `vote` | ほか |
   | --- | --- | --- | --- | --- |
   | 読む | ○ | ○ | ○ | ○ |
   | 出す・更新・先議の賛同 | × | ○ | × | × |
   | 取り込む | × | ○（最後の24時間を除く） | × | × |
   | 先議の票 | × | × | ○ | × |

2. **変えられる条**（`amendableArticles(db, bill)`）：法案の対象の法令のうち、`action` が `amend` と `enact` の法令の条
   - `amend`：基にした版の条（`articlesOfRevision`）と、法案が足した条（`op = 'add'`）
   - `enact`：法案の条（`op = 'add'`）
   - 法案が削除した条は選べない（削除の取りやめは条の追加・削除と同じく、あとの Issue。受入基準の A）
   - 「いまの本案の本文」は、法案の変更があればその本文、なければ基にした版の本文
   - 選ぶ欄の名前は「変える条」、選択肢は `第1条（目的）` の形。法令が2本以上なら法令名の `optgroup` で分ける。値は `<law_seq>:<num>`
   - 条を選ぶと「変更後の条文」にいまの本案の本文を入れる（`/shusei/kaku` の `load` が、選べる条の本文を返す。書く画面の `draftArticles` と同じ）
3. **本文の確かめ**（`validateAmendmentBody(raw, article)`・`checkAmendedLaw`）：`parseArticleBody`（項と号の形）で確かめ、いまの本案の本文と同じなら `unchanged`、基にした版の本文と同じなら `sameAsBase`（「基にした条文と同じです。変更をやめる修正案は出せません」。本文の比べは `articleBodyText` でそろえる）。理由は `checkText` で400字まで（改行可、任意）。見出しはいまの本案のまま。修正案を当てた本案に `checkChanges` をかけ、制定の第1条のひな形などの決まりも確かめる。法案全体で変える条が50条を超えるなら `changeCount`。締切のあとに複数を当てて50条を超えるのは、数が少なく害もないので許す。基にした版へ戻す修正案がないので、当てても本案の変更はなくならない
4. **出す**（`/houan/<番号>/shusei/kaku` の action）：フォームの値は `rev`（画面を開いたときの本案の版）、`article`、`body`、`reason`、Turnstile。確かめの順は、番号と存在（ない・下書きは 404）→ ログイン → 国 → 締め出し → 登録から7日（403）→ Turnstile → 入力（形が違えば 400）→ 時期（409）→ 提出者（403）→ 版（`rev` が `bills.rev` と違えば 409。古い本文を基に書いた修正案を、新しい版のものとして残さないように。`saveDraft` の `expectedRev` と同じ）→ 本文の確かめ（決めたこと3。いまの本案に依存するので版のあと。誤りは欄に出す）→ レート制限（429）→ 保存。`base_rev` は確かめた `rev`。記録は `amendment_post`（`target_id` は法案の番号）。書けたら修正案のタブへ
5. **取り込む**（`?/accept`。`acceptAmendment`）：フォームの値は `amendment`、`revision`（提出者が読んだ本文かを確かめるため）。確かめの順は、番号と存在 → ログイン → 国 → 締め出し → 入力 → 修正案（同じ法案の見える行でなければ 404）→ 提出者（403）→ 時期（409）→ 状態（`open` で `base_rev = bills.rev`、`revision` が画面のとおりでなければ 409）→ 保存。時期は `acceptOpen(progress, now, voteAt)`（3週目で、`now < voteAt - 24時間`）。Turnstile は要らない（1人だけの操作で、回数も修正案の数まで）。レート制限も掛けない。登録から7日は、提出者なので済んでいる
   - 保存の順は `saveDraft` と同じ：`next_rev` を取る（`rev = base_rev` の条件つき）→ `bill_laws`・`bill_changes`・`bill_solutions` を新しい版へ写し、対象の条だけ置きかえる → 次の2文を D1 の `batch`（1つのトランザクション）で実行する。`bills.rev` を条件つきで進める（`rev = base_rev`）。`amendments` の `status = 'accepted'` と `applied_rev` を、本案の版が新しい版になっているときだけ書く。進まなければ 409 で、書いた版の行は読まれないので残してよい（`saveDraft` と同じ）→ 記録 `amendment_accept`（`target_id` は法案の番号。足すのに失敗しても取り込みは残る）
   - 法案の見出しや要約、副作用の欄は変えない
   - `status` はゲームの状態なので、本文だけ入って提案者の記録が失われないよう、同じトランザクションにする。テストの `openMemoryDb` にも `batch` を足す（`Db` の型には `batch` がないので、`BatchDb` を別に作る）
6. **更新**（`/houan/<番号>/shusei/kaku?koushin=<修正案の番号>`）：提案者が、`status = 'open'` で `base_rev <> bills.rev` の修正案だけを3週目に更新できる。ほかの人か条件の外は、画面は欄を出さず理由を出し、送ると 403 か 409。条は変えない。本文の確かめは決めたこと3、確かめの順は決めたこと4（提出者の代わりに提案者。`rev` の確かめも同じ）。保存は `base_rev`・`body`・`reason`・`updated_at` と、本文が変わったときか、`base_rev` の版といまの版でその条の本文が違うときだけ `revision + 1` を1文で（`WHERE status = 'open' AND base_rev <> <いまの版> AND user_id = <本人>`）。記録は `amendment_post`（`target_id` は法案の番号）
   - ほかの修正案の取り込みで本文がいまの本案と同じになると、更新は `unchanged` で断られ、3週目の終わりまで「更新が必要」のまま。画面の誤りに「いまの本案と同じ本文になっているので、更新は要りません」と出す
7. **先議の賛同**（`?/support`。`setAmendmentSupport`）：フォームの値は `amendment`、`revision`、`op`（`add`・`remove`）。確かめの順は、番号と存在 → ログイン → 国 → 締め出し → 登録から7日（403）→ 入力（400）→ 修正案（404）→ 時期（409）→ 提案者と提出者（403）→ 状態（`open` で `base_rev = bills.rev`、`revision` が画面のとおりでなければ 409。取り消しは、3週目なら状態を問わず受け付ける）→ レート制限（429）→ 保存（1文で状態を確かめる）。記録は行が変わったときだけ `amendment_support_add`・`amendment_support_remove`（`target_id` は修正案の番号）
   - **要件**（`priorVoteRequirement(participants)`）：`ceil(proposalRequirement(participants) / 2)`。`participants` はその会期に固定した今月の参加者（`sessionParticipants`）。仕様の表の「発議要件 3 なら 2人」と合う
   - カードに「賛同 N人（あと M人で本案より先に採決します）」、届いたら「賛同 N人（本案より先に採決します）」を出す
8. **発議した版の賛同者**（`supportRev(bill)`。`bills.ts`）：`bill.proposedRev ?? bill.rev`。法案のページの「賛同 N人」（`+layout.server.ts` から `billSupportState` に渡す版）、一覧の「賛同 N」（`supportCount`。`s.rev = COALESCE(bills.proposed_rev, bills.rev)`）、答弁できる人（`isSupporter`）は、この版の行を数える。下書きは `proposed_rev` が NULL なので今までどおり。#66 の Major 1 と #66 の設計書の決めたこと2 の「発議した版の賛同者を保つ」を、ここで入れる
   - 発議の版は `proposeBill` の1文で入れるので、発議と版がずれない。発議のあとは `setBillSupport` が閉じているので（`status = 'draft'` の条件）、賛同の行は増えない
9. **先議の票**（`?/vote`。`castAmendmentVote`）：フォームの値は `amendment`、`choice`（`VOTE_CHOICES`）、Turnstile。確かめの順は、番号と存在 → ログイン → 国 → 締め出し → Turnstile → 入力（400）→ 修正案（404）→ 時期（409）→ 採決の対象（409）→ 保存。登録から7日は要らない（投票資格がなければ参考の票になるだけ）。Turnstile は仕様のとおり（#70 の本案の投票と同じ形にする）
   - **採決の対象**（`inPriorVote`。票を入れる文は同じ条件を SQL で確かめる）：`status = 'open'`、`base_rev = bills.rev`、`revision` の賛同が要件以上。4週目のはじめに賛同も更新も取り込みも止まるので、対象は締切まで変わらない。発議のあとに版を進めるのは取り込みと締切のあとの処理だけ（`saveDraft` は `status = 'draft'` の条件がある）
   - 保存は1文の `INSERT … SELECT … ON CONFLICT DO UPDATE … WHERE choice <> excluded.choice RETURNING`。行が返れば記録 `vote_cast`（今月の参加者に数える。`target_id` は入れない。本案の票の記録の番号と意味が混ざらないように）
   - 入れる前に `assignedBills` で割り当てを固定する。`tallyVotes` は割り当ての行がない人を「候補が0本の人」と見なすので、固定しないと割り当てを飛ばして有効票にできる
   - 画面：カードに賛成・反対・棄権のボタン（`aria-pressed`）と「票の数は締切まで誰にも見えません」。ボタンを選んだカードにだけ Turnstile と「投票する」を出す（1ページに20個出さないように）。投票資格がなければ「参考の票として数えます」（`isEligibleVoter`）。ログインしていなければ、押すとログインへ
10. **数える**（`tallyAmendmentVotes(db, session, amendmentId)`）：`tallyVotes` と同じ条件（投票資格があり、割り当てのすべてに本案の票を入れた人が有効票）。条件の式は `votes.ts` の中で共通にする
11. **締切のあとの処理**（`settleAmendments(db, session, billId, participants, now)`。`src/lib/server/amendments.ts`）：呼ぶのは #71。何度呼んでも結果が変わらない
    1. その法案の修正案を、古い順に読む。`inPriorVote` は `bills.rev` と比べるので、**状態を全部書いてから版を進める**
    2. `status = 'open'` で `inPriorVote` のものを数え、`billOutcome`（定足数 `quorumRequirement(participants)`、可決の条件は本案と同じ）で求める
    3. **採る修正案**（`adoptedAmendments(results, taken)`。純粋な関数）：可決した修正案を古い順に見て、同じ条（`law_seq` と `num`）がまだ採られていなければ採る（`status = 'passed'` の行は採ったものとして扱う）
    4. `status` を書く（`WHERE status = 'open'`）：採ったものは `passed`、否決は `failed`、同じ条で先に可決した修正案があって採らなかったものは `superseded`、定足数に届かなかったものは `lapsed`、対象でなかったものは `unvoted`
    5. `status = 'passed'` で `applied_rev` が NULL のものを、取り込みと同じ手順で1つの新しい版に全部当てる。条件に使う版は、読み直したいまの `bills.rev`（`base_rev` ではない）。版を進める文と `applied_rev` を書く文は `batch` で1つにする。4と5のあいだで失敗しても、やり直すと5から続く
12. **共同起草者**（`coDrafters(db, billId)`）：`status` が `accepted` か `passed` の修正案の提案者の名前（重複なし）。法案の概要の「提出者」の行に「共同起草者 A、B」と足す（案のない部分）。提案の画面に「採用されると、共同起草者として名前が出ます」と出す
13. **修正案のタブ**（`/houan/<番号>/shusei`）
    - タブの名前は「修正案 N」。N は見える修正案の数。発議から出す。下書きと、変えられる条のない法案には出さない（`/shusei` も `/shusei/kaku` も URL は 404）
    - 並びは古い順（先に出したものが先に採られるので）。20件ごとに分け、「修正案をもっと見る（N件）」で次へ（`?page=`）。`?page=` の形が違うか、2ページ目以降に修正案がなければ 404
    - 0件のときは「修正案はまだありません」
    - カード：変える条（法令が2本以上なら法令名も）、変更点（「もとの本案」「修正案」。`changeDiff`。比べるのは `base_rev` の版の本文で、提案者が書いたときの差だけを出す。取り込まれたあとも変更点が消えない。ページの予算は `DIFF_PAGE_BUDGET`）、理由、状態。名前と `user_id` を返さない。自分の修正案かは `mine`、見ている人の賛同と票は `supported`・`myVote` で返す（ほかの人の票は返さない）
    - 状態の表示：`open` で3週目は「賛同 N人（…）」、`base_rev` が古ければ「更新が必要です」（提案者には「更新する」のリンク）、`accepted` は「取り込まれました」、`passed`「可決」、`failed`「否決」、`superseded`「可決しましたが、同じ条の修正案が先に可決しました」、`lapsed`「定足数に届きませんでした」、`unvoted`「採決されませんでした」、`open` で4週目は対象なら「本案より先に採決します」、対象でなければ「採決されません」、`open` で会期が終わったあと（#71 の処理の前）は「結果を待っています」
    - 「修正案を出す」は3週目のときだけ。登録から7日たっていない人にはいつからかを出す（質疑のタブと同じ）。ログインしていなければログインへ。提出者には出さない
    - 「取り込む」は提出者が取り込める時期（決めたこと5）に見るときだけ（更新が必要なものには出さない）。最後の24時間は「取り込めるのは採決の24時間前までです」と出す。押して確かめの画面は出さない（案のない画面なので質疑のボタンと同じ）
14. **レート制限**（`checkAmendment`・`checkAmendmentSupport`。`limits.ts`）：受入基準9の数。アカウントの上限は違反に数え、回線の上限は数えない
15. **画面の言葉**：すべて `src/lib/copy/ja.ts`。「先議」は使わず「本案より先に採決」と書く（画面に実装用語を出さない）

## テストの方針

受入基準ごとに1本。信頼の境界は、出すフォームに1本、取り込む・賛同・票のフォームに1本。

| 3 | 取り込む、変更点、共同起草者、賛同 N人、提出者のほかは断る | 画面 |

## あとで決めること

- 条の追加と削除、見出しの変更、複数の条をまとめた修正案（使われ方を見て Issue にする）
- 修正案の通報と非表示（#103）。非表示の修正案を「修正案 N」でどう数えるかも一緒に。非表示は `status` と別に持つ（共同起草者を `status` から求めているので）
- 修正案が多い法案では、`settleAmendments` の数える問い合わせが修正案の数だけ走る（#71 で Cron の時間に収まるかを見る）
- 本案の投票の確かめ（#70）に合わせて、先議の票のレート制限を見直す（票を変えるたびに `vote_cast` の行が増える）
- 退会を入れるときの `amendments`・`amendment_supports`・`amendment_votes` の扱い
- 要調整で次の会期に審議するとき（#72）の、前の会期の修正案の扱い
