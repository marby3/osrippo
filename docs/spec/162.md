# 読める法律の取り込み（設計書）

Issue #162。受入基準と決めたことは Issue #198 の「#162」の節と、ユーザーの決定のコメントの4（2026-11-13）。法令の表と全文検索に表を足し、取り込みのバッチを足すので Careful（ROADMAP「モード」の、条文の内部IDと版のまわり）。ただし、いまある `laws`・`law_revisions`・`provisions`・`provision_versions` と全文検索の表は変えない。

## 受入基準（#198 から写す）

1. バッチが e-Gov の一覧から、読める法律の法令名・読み・略称・分類・法令番号・最後の改正日と、最新の版の条文を取り込む（DB のテスト。テストデータを使い、e-Gov は呼ばない）
2. 2回目は、改正日（e-Gov の `updated`）が変わった法律だけを入れ直す（DB のテスト）
3. 読める法律の法令のページ `/hourei/[lawId]` が開き、最新の条文と「読める法律（最新の版だけ）」の表示が出る。改正の記録と比較へのリンクは出ない（画面のテスト）
4. 遊べる法律のページ、IF世界、毎日の同期は、いまのまま変わらない（いまある画面のテストが通る）
5. 全件を取り込んだときの DB の大きさと書き込んだ行数を測り、`docs/readable-laws.md` に書く（文書）

読める法律の全文検索は、本文の写しを持たない3文字ずつの索引1つに、条の見出しと本文を入れる（ユーザーの決定4）。

## 目的

委員会の対象（遊べる法律）だけでなく、残りの法律も最新の版だけ読めるようにする。法律Wiki（#163〜#166）の土台にする。

## 範囲

- 入れる
  - 表：`readable_laws`、`readable_articles`、全文検索の `readable_search`
  - バッチ：`pnpm sync:readable`
  - 法令のページ `/hourei/[lawId]` で読める法律を出すこと
  - 画面のテストの D1 に、テストデータの読める法律を入れること
  - `docs/readable-laws.md`
- 入れない
  - 法律の一覧と検索の画面（#163）
  - 別名と条だけのページ（#164）
  - 自動リンク（#165）とリンク元（#166）
  - 本番の D1 につなぐ引数（本番の公開 #203）

## 表

マイグレーションは足すだけで、いまある表と行は変えない。

| 表 | 列 | 備考 |
| --- | --- | --- |
| `readable_laws` | `id`（e-Gov の law_id、主キー）、`title`、`title_kana`、`law_num`、`law_type`（`Act`・`Constitution`）、`category`、`abbrevs`（JSON の配列。SQL の既定 `'[]'`。e-Gov が null なら `[]`）、`promulgation_date`、`last_amended`（NULL 可）、`revision_id`、`updated`、`headings`（JSON、NULL 可）、`article_count`（整数、NULL 可）、`synced_updated`（NULL 可） | 遊べる法律の行も入れる（#163 の一覧と検索で、法令名・分類・略称を使う）。遊べる法律の条文と見出しは、いまの表から読むので、この表の `headings` と条は入れない |
| `readable_articles` | `id`（整数。索引の rowid。取り込みのときに、表の最大値 + 1 から順に、バッチの側で決める。`law-sync.ts` の内部IDと同じ振り方で、入れる前に索引の行の rowid も分かる）、`law_id`（外部キー）、`seq`（本則の中の順）、`num`（e-Gov の形の条の番号）、`label`、`caption`、`paragraphs`（JSON、`Paragraph[]`） | 一意：（`law_id`, `num`）。`parseLaw` は本則の条だけを返し（附則と別表は含めない。`src/lib/domain/law/parse.ts:41`）、本則の条の番号は重ならない。`parseLaw` の結果に内部IDはない（内部IDは版の履歴を作るときに振る） |
| `readable_search` | FTS5、`tokenize='trigram'`、`content=''`（contentless）。列は `text` 1つ。rowid は `readable_articles.id` | 本文も見出しも写しを持たない。引いた rowid を `readable_articles` と結んで条を出す。消すときは、FTS5 の `'delete'` の命令に、消す行の `text` を渡す（`text` は `paragraphs` と見出しから同じ関数で作り直せる） |

`text` は、その条の見出し（`readable_articles.caption`）と本文（`paragraphs`）だけから、いまの全文検索と同じ規則（`src/lib/domain/search.ts` の `searchTexts` の trigram の側）でそろえた文字列。同じ行から必ず作り直せるので、消すときの `'delete'` に同じ文字列を渡せる。法令の見出しの木（`readable_laws.headings`）は入れない。

FTS5 の表は、`law-sync.ts` の `search_trigram` と同じく、スキーマの外で形だけ宣言し、Drizzle の builder で書く（D1 の batch は値つきの `db.run` を受け付けない）。contentless の FTS5 と `'delete'` の命令が手元の D1（wrangler）で動くことは、実装の最初に確かめて PR に書く。

## 決めたこと

1. **対象**（基準1）
   - e-Gov 法令API v2 の `GET /laws?law_type=Act&repeal_status=None` の全件（`limit=500` で `offset` を進めて全部読む）と、`law_type=Constitution` の全件
   - `revision_info.current_revision_status` が `CurrentEnforced` でないもの（未施行の版しかない法律）は入れない
   - 政令と府省令は入れない
2. **一覧の形**（`src/lib/egov/` に `readLawList` を足す。応答は信頼の境界）
   - 使う値：`law_info.law_id`・`law_num`・`law_type`・`promulgation_date` と、`revision_info.law_revision_id`・`law_title`・`law_title_kana`・`abbrev`（カンマ区切りか null）・`category`・`updated`・`amendment_law_id`・`amendment_enforcement_date`・`current_revision_status`
   - 応答の形：`{ total_count: number, count: number, laws: [...] }`。`offset` を `count` ずつ進め、`offset >= total_count` で終わる。途中で `count` が0なら形が違うとみなす
   - 行の値：`law_id`・`law_num`・`law_type`・`law_revision_id`・`law_title`・`updated`・`current_revision_status` は空でない文字列。`law_title_kana`・`category`・`abbrev`・`amendment_law_id`・`amendment_enforcement_date` は文字列か null。日付は `YYYY-MM-DD`
   - `abbrev` は、カンマで分け、前後の空白を落とし、空のものを捨てる（null と空文字は `[]`）
   - 1行でも形が違えば、一覧全体を断る。そのときは何も書かず、終了コード1で終わる
   - `last_amended` は `amendment_enforcement_date`（`amendment_law_id` があるときだけ）。`amendment_law_id` がなければ制定から改正なしで、ページは「制定から改正なし」と公布日を出す。`amendment_law_id` があって日付が null なら、ページは改正日を出さない
3. **取り込みの流れ**（基準1・2）
   1. 一覧を全部読む（全ページと2つの種類が、そろって形を通ったときだけ次へ進む）
   2. 保存している行を読み、法令ごとに次の3つを決める
      - 法令名などの欄を書く（入れるか、変える）
      - 本文を読み直す。遊べる法律（`laws` にある法令）でなく、次のどれかのとき
        - 行がない
        - `synced_updated` が一覧の `updated` と違う
        - `article_count` が NULL
      - 消す（一覧にない）
   3. 法令名などの欄（`synced_updated` と `article_count` と `headings` 以外）を書く。遊べる法律の行は、ここで `synced_updated` も一覧の `updated` にする（本文は読まないので、欄がそろった時点で済み）
   4. 読み直す法令ごとに、`/law_data/{revision_id}` を読み、`parseLaw` と `parseHeadings` で条と見出しを作る
      - 本文の形は正しいが本則の条がない法律：失敗にせず、`article_count = 0`・`synced_updated = updated` を書き、`docs/readable-laws.md` の一覧に載せる（`updated` が変わるまで読み直さない。ページは出さない）
      - 別の版の本文、根が違う本文など、形の違う本文：その法令の失敗にする（何も書かない）
   5. 入れ替えは、法令ごとに次の順にする
      - 最初の `batch`：`synced_updated` と `article_count` を NULL にする、古い索引を消す（`'delete'`）、古い条を消す
      - 次の `batch`：条と索引を入れる。D1 の上限（1回の呼び出しに1000文、1文100KB。https://developers.cloudflare.com/d1/platform/limits/ ）を超えないよう、条を分けて入れる
      - 最後の `batch`：`synced_updated`・`article_count`・`headings`・`revision_id` を書く
      - 途中で失敗すると `synced_updated` は NULL のままなので、次の回に読み直す。ページは `synced_updated` のある法令だけを出す（決めたこと4）
      - 1条の `paragraphs` が100KB を超える法令は、失敗として記録する（いまの3法の最大の条は数KB。全件の取り込みで有無を確かめ、`docs/readable-laws.md` に書く）
   6. 消すのは、一覧が全部そろったときだけ。順は、索引を消す（`'delete'`）→ 条を消す → `readable_laws` の行を消す
   7. 1つの法令で失敗しても、ほかは続け、最後に終了コード1で終わる（`sync:laws` と同じ）
   8. e-Gov への負荷：一覧のページも本文も1件ずつ、1秒あけて読む。429・5xx・タイムアウト（30秒）は、5秒あけて1回だけやり直す。2回目からは変わった法令だけを読むので、ふつうは週に数十件
   9. 待つ関数と、JSON を読む関数は引数で受け取る（テストは待たず、読んだ回数を数える）
4. **法令のページ**（基準3）
   - 読める法律のページは、`synced_updated` が NULL でなく、`article_count` が1以上の法令だけ出す（途中まで入った法令と、条のない法令は出さない）
   - `/hourei/[lawId]` は、`laws` にあれば、いまのとおり遊べる法律のページを出す
   - なく、`readable_laws` にあって条があれば、読める法律のページを出す
   - 読める法律のページに出すもの
     - 題名、法令番号、「読める法律（最新の版だけ）」の表示
     - 最後の改正日。`last_amended` が NULL なら「制定から改正なし」と公布日
     - 見出しの帯と目次
     - 条文（ふりがなと法令用語の説明は、遊べる法律と同じ部品）
   - 読める法律のページに出さないもの
     - 改正の記録、比較へのリンク、条ごとの「N年変わっていない」（版の履歴がないため）
     - IF世界へのリンク
   - `/if/hourei/[読める法律の id]` は 404 のまま
5. **全文検索**：いまの `/kensaku` には、この Issue では読める法律を足さない（#163 で、法律の一覧の検索と一緒に足す）。この Issue では、索引が引けることだけを DB のテストで確かめる
6. **テストデータと画面のテストの D1**
   - 一覧の応答は、e-Gov の形で小さく作る（テストデータなので、版は本文のテストデータがある版にし、状態は `CurrentEnforced` と書く）
     - `tests/fixtures/egov/laws_list_act.json`：民法（版 `129AC0000000089_20200401_501AC0000000034`）、景品表示法、消費者契約法、未施行だけの法律1件
     - `tests/fixtures/egov/laws_list_constitution.json`：日本国憲法（版 `321CONSTITUTION_19470503_000000000000000`。本文のテストデータを e-Gov から1回取って置く）
   - DB のテストでは、遊べる法律（`laws`）を消費者契約法だけにする。民法・景品表示法・憲法が読める法律になり、2回目のテストで「1件だけ読む」と「全部読む」を見分けられる
   - `pnpm db:reset` は、遊べる3法に加えて、この一覧で読める法律を取り込む。`seedStatements` と同じく、取り込みの関数にテストデータを返す読み込みの関数を渡して SQL を作り、e-Gov は呼ばない（画面のテストで民法と憲法が開く）
7. **バッチの入口**：`scripts/sync-readable.ts`（`pnpm sync:readable`）。`--persist-to` は `sync:laws` と同じ。本番の D1 につなぐ引数は #203 で足す
8. **大きさの記録**（基準5）：手元の D1 に全件を取り込み、次を `docs/readable-laws.md` に書く。2GB を超えたら、索引を見出しだけにする前に止めて相談する（ユーザーの決定4の条件を変えることになるため）
   - DB の大きさ
   - 表ごとの行数
   - 書き込んだ行数
   - 取り込みにかかった時間

## テストの方針

テストは受入基準ごとに1本と、信頼の境界（一覧の応答）の形の違う入力の1本。e-Gov は呼ばない（`tests/fixtures/egov/`）。

- 基準1（DB のテスト）：テストデータの一覧と本文で取り込むと、次のようになる
  - 法令名・読み・略称・分類・法令番号・最後の改正日が入る
  - 民法の条が入り、`readable_search` で本文の3文字の言葉を引くと、その条が返る
  - 遊べる法律の条は入らない
  - 未施行だけの法律は入らない
- 基準2（DB のテスト）：同じ一覧で2回目を流すと、本文は1件も読まない。1件の `updated` を変えると、その1件だけ読む
- 一覧の形（DB のテスト）：1行の `law_info.law_id` がない一覧を渡すと、何も書かずに失敗を返す
- 基準3（画面のテスト、390px と 1280px）：`/hourei/129AC0000000089` に、題名、「読める法律（最新の版だけ）」、第1条の本文が出る。比較へのリンクは出ない
- 基準4：法令のページ・IF世界・同期のいまある画面のテストと DB のテストを流す（新しいテストは書かない）
