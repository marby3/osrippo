# 本番の公開（設計書）

Issue #203。受入基準は Issue #198 の「本番の公開」の節、ユーザー側でやることは #190、デプロイのときにやることの一覧は覚え書き（deploy-checklist）。票・会期の終わりの処理・認証が動く本番の D1 を作り、マイグレーションと取り込みを当てるので Careful（ROADMAP「モード」の、会期終了時の処理と認証のまわり。あとから直すと票や法令の版が壊れる）。マイグレーションは足さない。

## 受入基準（#198 から写す）

1. `wrangler.jsonc` に本番の環境（D1、カスタムドメイン、秘密の値の一覧）がある。`pnpm check` が通る（#116 を直す）
2. 本番のデプロイの手順がスクリプトになっている（マイグレーション → 取り込み → ビルド → デプロイ）
3. 公開後の確かめのテスト（読むだけ）を本番の URL に向けて流せる。主な画面が200、`X-Robots-Tag` がない、IF世界に `noindex` と帯がある、`/test-login` と `/test-import` が404、フッターに非公式の表示がある
4. `docs/launch.md` に、ユーザーの手作業の一覧（D1 を作る、秘密の値、ログインのクライアント、Turnstile、ドメイン、WAF、最初の運営、自宅サーバーのタイマー、通知先、2段階認証）を順番どおりに書く（文書）

## 決めたこと

### 1. 本番の環境の名前と、top-level の扱い（基準1）

- 本番は `env.production` に置く。top-level は、いまのまま手元とテストのための設定にする
- 理由
  - wrangler は `vars`・`d1_databases`・`secrets` を名前付きの環境に引き継がない（`node_modules/wrangler/config-schema.json` の説明。2026-11-14 に 4.156.0 で確かめた）。本番を top-level にしても、ステージングの値は環境の側に全部書くことになり、まとめられるものはない
  - top-level は、手元のサーバー（`preview:test`・`preview:nologin`）、`db:reset`、`getPlatformProxy` の手元の D1 が使う。ここにある Turnstile のテスト用の鍵や `database_id: "local"` を本番の値に変えると、手元の動きが変わる
  - `npx wrangler deploy` を `--env` なしで流しても、top-level の `database_id` は `"local"` なので、本番に出ない（D1 が見つからず止まる）
- 引き継がれるもの（`name`・`main`・`compatibility_date`・`compatibility_flags`・`assets`・`workers_dev`・`preview_urls`）のうち、`workers_dev` と `preview_urls` は本番で `false` に上書きする。本番の Worker は、カスタムドメインの1つのホストだけで開く（`workers.dev` の別のホストがあると、ログインの戻り先（`BETTER_AUTH_URL`）と合わず、検索にも別の URL で載る）
- `triggers` は、ステージングと同じく本番にも書く（`1 15 * * *`、日本時間 0時1分）。引き継ぎに頼らない
- Worker の名前は wrangler の決まりのまま `osrippo-production`（ステージングは `osrippo-staging`）。D1 の名前も `osrippo-production`

本番の環境の形（仮の値の置き方は2）：

```jsonc
"production": {
	"d1_databases": [
		{
			"binding": "DB",
			"database_name": "osrippo-production",
			// 本番の D1 を作ったら入れる（docs/launch.md）。それまでは仮の値で、デプロイのスクリプトが止める
			"database_id": "00000000-0000-0000-0000-000000000000",
			"migrations_dir": "drizzle"
		}
	],
	// ドメインが決まったら入れる。それまでは .invalid で、デプロイのスクリプトが止める
	"routes": [{ "pattern": "domain-undecided.invalid", "custom_domain": true }],
	"workers_dev": false,
	"preview_urls": false,
	"secrets": { "required": [ /* 4 を参照 */ ] },
	"vars": {
		// 本番のウィジェットを作ったら入れる。NOINDEX は置かない（Issue #156）
		"TURNSTILE_SITE_KEY": "undecided"
	},
	"triggers": { "crons": ["1 15 * * *"] }
}
```

### 2. 本番の D1 の ID、ドメイン、サイトキーの置き場所（基準1）

- 3つとも `wrangler.jsonc` に直接書き、リポジトリに入れる。どれも秘密ではない（D1 の ID は、API トークンがなければ使えない。ステージングの ID もすでに書いてある。ドメインとサイトキーは、公開した画面から見える）
- ユーザーが作るまでは、上の仮の値を置く。仮の値は、`wrangler types` にも `pnpm check` にも影響しない（5）
- 値が決まったら、1つの PR（Normal）で3つを入れる。ユーザーが値を渡し、Claude が PR を作る（`main` に直接書かない）。`docs/launch.md` の順では、D1・Turnstile・ドメインを作ったあと、初めてのデプロイの前
- デプロイのスクリプトは、仮の値が1つでも残っていれば、何もせずに止める（7 の「前の確かめ」）
- ドメインは1つだけ（例：`example.jp`）。`www.` を付けた名前の扱いは決めていない（「あとで決めること」）

### 3. D1 を作るときの場所

`npx wrangler d1 create osrippo-production --location apac`。利用者は日本からだけ書き込める（`allowedCountry`）ので、主な置き場所をアジア太平洋にする。場所はあとから変えられないので、`docs/launch.md` にこの命令をそのまま書く。

### 4. 秘密の値の一覧（基準1）

- `secrets.required` は環境ごとに書く（引き継がれない）。いま top-level にある8つを、`env.staging` と `env.production` にも書く
  - `BETTER_AUTH_URL`、`BETTER_AUTH_SECRET`、`GOOGLE_CLIENT_ID`、`GOOGLE_CLIENT_SECRET`、`LINE_CLIENT_ID`、`LINE_CLIENT_SECRET`、`TURNSTILE_SECRET_KEY`、`IP_HASH_SECRET`
- **`MIRROR_TOKEN` は本番の一覧にだけ足す**。ステージングと top-level には足さない
  - #155 で「書き出しを使わない環境では入れなくてよい」として、どこにも入れていなかった（`src/app.d.ts`）。本番では公開ミラーを使うので、入れ忘れると会期が確定しても書き出せない
  - wrangler 4.156.0 は、環境の `secrets.required` にある名前がその Worker に入っていないと、`wrangler deploy` を止める（`wrangler-dist/cli.js` の `addRequiredSecretsInheritBindings`）。本番の一覧に入れておけば、入れ忘れたままデプロイできない
  - ステージングに足すと、いまのステージングに入っていなければデプロイが止まるので足さない。型は、どれかの環境にない名前として省略可能（`?:`）になり、いまの宣言（ないときは入口が 401）と同じ
- **初めてのデプロイ**は、Worker がまだないので `wrangler secret put` で先に入れられない（wrangler が「This Worker does not exist yet」で止める）。初回だけ `wrangler deploy --secrets-file <ファイル>` で、コードと一緒に入れる
  - ファイルは JSON にする（`.env` の形は `$VAR` を展開し、手元の環境変数を読んで送ってしまうことがある。`wrangler deploy --help`）
  - ファイルはリポジトリの外に置き、本人だけが読めるようにし、デプロイのあとで消す（手順は `docs/launch.md`）
  - 2回目からは `wrangler secret put <名前> --env production`
- `BETTER_AUTH_URL` は秘密ではないが、いままでどおり秘密の値として入れる（docs/spec/23.md）。値は `https://<ドメイン>`
- 本番の `vars` に `NOINDEX` を置かない（#156）。デプロイのスクリプトの前の確かめで、本番の `vars` に `NOINDEX` があれば止める

### 5. `pnpm check` の直し方（#116。基準1）

原因は2つあった（2026-11-14、`wrangler types` を一時フォルダに書き出して確かめた）。

- 秘密の値が `env.staging` に引き継がれず、ステージングにない名前として、型が省略可能（`?:`）になる → 4 のとおり、環境ごとに `secrets.required` を書くと、もとの必須の型に戻る
- `vars` の値が文字の型そのもの（`"0x4AAAAAAF4cryiiv6FIHZHg" | "1x00000000000000000000AA"`）になり、値を変えるたびに型が変わる。`NOINDEX?: "1"` も、`src/app.d.ts` の `NOINDEX?: string` とぶつかる

直し方：

- `pnpm gen` を `wrangler types --strict-vars=false`、`pnpm check` の最初を `wrangler types --check --strict-vars=false` にする。`vars` の型は `string` になる。仮の値をあとで本物に変えても型は変わらず、`pnpm gen` をやり直さなくてよい（同じ手で、値だけ変えて `--check` が通ることを確かめた）
- `worker-configuration.d.ts` を作り直してコミットする
- 環境ごとの型の差（`ProductionEnv`・`StagingEnv` が別に作られる）は使わない。コードは、いままでどおり全部の環境を合わせた `Env` を使う
- `src/app.d.ts` の宣言のうち、作り直した型と同じになったもの（`NOINDEX`、`MIRROR_TOKEN`）は消す。`TEST_LOGIN`・`SESSION_MINUTES` はどの環境の設定にもないので残す
- 作り直したあと `svelte-check` で型の誤りが出たら、その箇所を直す（`!` や型の付け替えで黙らせない）

### 6. 取り込みのスクリプトを本番の D1 につなぐ引数

- `sync:laws`・`sync:readable`・`backfill:law-refs` に、`--env <環境>` と `--remote` を足す。`docs/backup.md` の `pnpm backup --env staging` と、`docs/load-test.md` の `pnpm beta:data -- --check ... --env staging --remote` にそろえる

  ```sh
  pnpm sync:readable --env production --remote
  pnpm sync:laws --env production --remote
  pnpm backfill:law-refs --env production --remote
  ```

  - `--remote` には `--env` が要る（top-level の D1 は手元にしかない）。`--remote` と `--persist-to` は一緒に使えない。どちらも終了コード2で使い方を出す
  - `--remote` がないときは、いまのまま手元の D1（`--persist-to` も今のまま）
- つなぎ方は、wrangler の remote bindings（`getPlatformProxy` の `remoteBindings`）にする。いまの3つのスクリプトは、Drizzle と `db.batch` で D1 を読んで比べながら書くので、SQL のファイルにして `wrangler d1 execute --remote --file` で流す形にはできない（`sync:readable` と `sync:laws` は、DB にある行と e-Gov を比べて、変わったものだけを書く）
  - `wrangler.jsonc` には `remote: true` を書かない（書くと `wrangler dev` が本番の D1 を開く）。スクリプトの共通の部分（`scripts/d1.ts`）が、`--env` の D1 の行だけを写した一時の設定ファイル（その D1 に `remote: true` を付けたもの）を OS の一時フォルダに書き、`getPlatformProxy` の `configPath` に渡す。終わったら消す
  - 資格情報は `CLOUDFLARE_API_TOKEN`・`CLOUDFLARE_ACCOUNT_ID` の環境変数（`docs/backup.md` と同じ。引数にしない）。remote bindings は Cloudflare の上に一時の Worker を立ててつなぐので、D1 の権限のほかに要る権限を、実装のときに確かめて `docs/launch.md` に書く
  - **実装の最初に、ステージングで `pnpm sync:laws --env staging --remote` を流し、`db.batch` が remote bindings を通ることを確かめる**（覚え書きの宿題）。通らなければ、そこで止めて相談する（代わりの形は「あとで決めること」）
- 対象3法の最初の取り込み（seed）は、いまのステージングと同じく、`seedStatements(TARGET_LAWS, <テストデータ>)` を SQL のファイルにして `wrangler d1 execute DB --env <環境> --remote --file` で流す。`db:reset` と違い、読める法律のテストデータ（`readableSeedStatements`）は入れない（本番の読める法律は e-Gov から `sync:readable` で入れる）
- `restore:index` と `backup` は変えない（4 の「入れない」）

### 7. デプロイのスクリプト（基準2）

入口は `scripts/deploy.ts` の1つ。`package.json` に2つの名前で置く（`pnpm deploy` は pnpm に同じ名前の命令があるので使わない）。

```sh
pnpm deploy:production                         # tsx scripts/deploy.ts --env production
pnpm deploy:production -- --secrets-file <JSON>  # 初めてのデプロイだけ
pnpm deploy:staging                            # tsx scripts/deploy.ts --env staging --base https://osrippo-staging.marbyxmax10.workers.dev --expect-noindex
```

段の順と止まる条件は、純粋な部分 `src/lib/deploy/plan.ts` で決める。wrangler・git・e-Gov を呼ぶのは入口で、外から渡す（`src/lib/backup/batch.ts` と同じ形）。段ごとに、何をしたかと、かかった時間を出す。

| 段 | すること | 止まる条件 |
| --- | --- | --- |
| 0. 前の確かめ | 設定を読む（`unstable_readConfig`）。本番では git の状態を見る。秘密の値の名前を見る（`wrangler secret list --env <環境>`。値は見ない） | 次のどれか（終了コード2。何も変えていない）：仮の値（D1 の ID、`.invalid` のドメイン、`undecided` のサイトキー）が残っている／本番の `vars` に `NOINDEX` がある／本番で、作業ツリーに変更があるか、`HEAD` が `origin/main` と違う（`git fetch` のあと）／`secrets.required` の名前が Worker に入っていない（Worker がまだないときは、`--secrets-file` の JSON に全部の名前があるか）／日本時間の 23時45分〜0時30分（会期の終わりの処理 0時1分と重ねない） |
| 1. マイグレーション | タイムトラベルの戻し先を出して控える（`wrangler d1 time-travel info DB --env <環境> --json`）。`wrangler d1 migrations apply DB --env <環境> --remote`。当てたあと、トリガーを数える | 当てるのに失敗した。トリガーが6つ（`amendments_moderation_log`・`issues_status_log`・`posts_status_log`・`solutions_status_log`・`stances_log_insert`・`stances_log_update`）そろっていない（終了コード1）。トリガーの名前の一覧は、`drizzle/` の `CREATE TRIGGER` と `DROP TRIGGER` を順に読んで作る（増えたときに直し忘れないように） |
| 2. 取り込み（初回だけ） | 下の「初回の見分け方」で決める。初回なら、対象3法の seed → `sync:laws` → `sync:readable` → `backfill:law-refs` の順。初回でなければ飛ばす | seed を流してよくない状態（下）。どれかのスクリプトが0以外で終わった（終了コード1。ビルドとデプロイに進まない） |
| 3. ビルド | `pnpm build`（Cron の入口を包む。`scripts/wrap-worker.ts`） | 失敗した（終了コード1） |
| 4. デプロイ | `wrangler deploy --env <環境>`（初回は `--secrets-file`） | 失敗した（終了コード1） |
| 5. 公開後の確かめ | URL が200を返すまで待つ（10秒おき、2分まで。デプロイの直後は 404 が返ることがある）。そのあと `pnpm test:launch -- --base <URL>`（ステージングは `--expect-noindex` を付ける） | 2分待っても200にならない。確かめのテストが落ちた（終了コード1）。コードはもう出ているので、戻す命令（`wrangler rollback --env <環境>`）と、1で控えたタイムトラベルの戻し先を出す。自動では戻さない（マイグレーションは足すだけなので、コードを戻しても DB はそのまま使える） |

- 確かめの URL は、本番は `routes` のドメインから `https://<ドメイン>`、ステージングは `--base`
- `--skip-import` で2を飛ばせる（読める法律の1本が e-Gov の都合で読めず、取り込みが終わらないまま急いで出すとき）。ふだんは使わない

**初回の見分け方**（2）：D1 を1回の問い合わせで数えて、次の3つに分ける。

| 状態 | 条件 | 2 ですること |
| --- | --- | --- |
| 空 | `laws` が0行で、`bills` も0行 | seed → `sync:laws` → `sync:readable` → `backfill:law-refs` |
| 取り込みの途中 | `laws` が対象3法とちょうど同じで、読める法律が済んでいない（`readable_laws` が0行か、遊べる法律でない行に `article_count` が NULL のものがある） | seed を飛ばし、`sync:laws` → `sync:readable` → `backfill:law-refs` |
| 済み | `laws` が対象3法とちょうど同じで、読める法律が済んでいる | 何もしない |
| それ以外 | `laws` が0行なのに `bills` がある、`laws` が対象3法と違う（足りない・多い） | 止める（終了コード1）。人が D1 を見て決める |

- seed は、内部IDを1から振る固定の行を入れるので、行のある D1 には流せない。法案（`bills`）は条の内部IDを指しているので、法案のある D1 では取り込みをやり直せない。上の「それ以外」で止めるのはそのため
- `sync:readable` は、本文を読み終えていない法令（`article_count` が NULL）だけを読み直すので、途中で落ちても、もう一度流すと続きから進む。読める法律が済んだことを「初回の取り込みが済んだ」印にする
- `sync:readable` は、遊べる法律（`laws` の行）の本文を読まない作りなので、seed のあとに流す（`src/lib/server/readable-sync.ts` の `playable`）
- `sync:laws` は、テストデータの時点から今日までの現実の改正を進める（seed のテストデータは取り込んだ日のもの）。初回の段で流しておき、公開した日から最新の条文を出す
- `backfill:law-refs` は、新しい D1 では本文が1件もないので何も足さない。ステージングのように前からある D1 のために、同じ段で流す（何度流しても同じ行になる）
- 初回の取り込みは、`sync:readable` だけで約50分かかる（`docs/readable-laws.md`）。デプロイのスクリプトはそのあいだ待つ

**ステージング**にも同じスクリプトを使う。違うのは、`--base` で URL を渡すこと、git の状態を見ないこと、確かめで `X-Robots-Tag` が「ある」ことを確かめること（`--expect-noindex`）。いまのステージングは seed が済んでいて、読める法律がまだないので、初めて流すと「取り込みの途中」になり、`sync:readable` を流す（負荷試験の法律の一覧に2,100本が要るので、それでよい）。`.review/config` の `deploy=` は `pnpm deploy:staging` に替える。初回は約50分かかるので、替える前に1回、手で流しておく。

### 8. 公開後の確かめのテスト（基準3）

- 置き場所：`launch/launch.spec.ts`。設定は `playwright.launch.config.ts`。`e2e/` に置かない（いつもの画面のテストに混ぜない。`load/` と同じく別のフォルダ）
- 流し方：`pnpm test:launch -- --base <URL> [--expect-noindex]`。入口 `scripts/launch-check.ts` が引数を読み、環境変数で設定に渡して `playwright test -c playwright.launch.config.ts` を流す（Playwright の命令は自分の引数を受け取らないため。`test:load` と同じ書き方）
  - `--base` がないときは、手元のサーバーを立てて流す（下の「手元で確かめる」）
  - 終了コードは Playwright のまま（0 合格、1 不合格）。引数の誤りは2
- 幅は、ほかの画面のテストと同じ 390px と 1280px の2つ
- 読むだけ。ログインしない。Cookie を入れない。GET だけで読む。例外は `/test-import` で、この入口は POST しかないので、空の POST を1回送る（入口がいちばん最初に、テストのサーバーでなければ 404 を返すので、何も書かない。`src/routes/test-import/+server.ts`）
- 確かめること（1本のテストの中の手順）
  - 主な画面が200で、フッター（`contentinfo`）に「国会・政府とは無関係の非公式サービスです」が出て、応答に `X-Robots-Tag` がない：`/`、`/kadai`、`/houan`、`/hourei`、`/hourei/412AC0000000061`（遊べる法律）、`/hourei/129AC0000000089`（読める法律。民法）、`/if/hourei/412AC0000000061`、`/toukei`、`/kensaku?q=消費者`、`/iinkai`、`/asobikata`、`/login`。#200 が先にマージされていれば `/yakusoku` も
  - 見つからないページ（`/kadai/999999999`）は404で、フッターがあり、`X-Robots-Tag` がない
  - IF世界の法令ページに、帯、「架空の法令」、`<meta name="robots" content="noindex">` がある
  - `/test-login?name=launch` が404、`/test-import` への POST が404
  - `--expect-noindex` のときは、`X-Robots-Tag` が `noindex, nofollow` で「ある」ことを確かめる（ステージング。#156）
- 本番のデータを前提にしない（課題や法案の数を数えない）。公開した日の本番には、対象3法と読める法律しかない
- **手元で確かめる**：`--base` なしで流すと、設定の `webServer` が `pnpm build` のあと、テスト用のログインのないサーバーを、取り込み済みの D1 で立てる
  - `preview:nologin` の D1 は表だけで法令がない（毎回空から作る。課題のないサーバーとして使うテストがある）ので、そのままでは法令のページが404になる。`scripts/preview-test.ts` に `--seed`（マイグレーションのあとで `db:reset` と同じ取り込みの SQL を流す）を足し、`pnpm preview:launch`（`--port 4175 --persist-to .wrangler/state-launch --seed`）を作る。テスト用のログインを渡さない点は `preview:nologin` と同じ
  - ポートと D1 を分けるのは、いつもの画面のテスト（4173・4174）と同時に流しても混ざらないようにするため
- Cloudflare の「Bot Fight Mode」などのボット対策を入れると、確かめのテストのブラウザーが止められることがある。`docs/launch.md` に書く

## テストの方針

テストは受入基準ごとに1本まで（文書だけの基準4は除く）。e-Gov と Cloudflare は呼ばない。

- 基準1：新しいテストは書かない。`pnpm check` が通ること（いまは `wrangler types --check` で落ちる。直す前に落ちることを確かめる）
- 基準2（単体のテスト `src/lib/deploy/plan.test.ts`、1本）：段を偽の関数にして、呼ばれた順を記録する。次の場合を1本の中で順に確かめる
  - 空の D1：前の確かめ → マイグレーション → seed → `sync:laws` → `sync:readable` → `backfill:law-refs` → ビルド → デプロイ → 確かめ
  - 取り込みの途中：seed だけを飛ばす
  - 済み：取り込みの段を全部飛ばす
  - `laws` が0行で `bills` がある、`laws` が対象3法と違う：取り込みの段で止まり、ビルドとデプロイを呼ばない
  - 仮の値が残っている、本番の `vars` に `NOINDEX` がある、秘密の値の名前が足りない、日本時間 0時10分：何も呼ばずに終了コード2
  - トリガーが足りない、`sync:readable` が1で終わる：そこで止まり、あとの段を呼ばない（終了コード1）
  - 確かめが落ちる：戻す命令と戻し先を出して終了コード1
- 基準3：公開後の確かめのテストそのもの（`launch/launch.spec.ts`、1本、2幅）。`--base` なしで手元の `preview:launch` に向けて流し、通ることで確かめる。直す前は `--seed` がなく法令のページが404になるので、落ちることを確かめる。ステージングに `--expect-noindex` で流すのは、実装のあとの手作業（PR に結果を書く）
- 基準4：文書（`docs/launch.md`）

## あとで決めること

- **最初の招待コードの `created_by`**（要確認）：`invites.created_by` は `user` への外部キーで NULL にできない（docs/spec/199.md の表）。本番の D1 にはまだ1人もいないので、最初のコードを入れる SQL に書く作り手がいない。案は次の3つ
  - A（勧める）：ログインの口（`account`）のない「事務局」の `user` の行を SQL で1行入れ、その行を作り手にする。ログインできず、画面にも出ない（招待コードの一覧は作り手を出さない）。行が1つ残るだけ
  - B：マイグレーションで `created_by` を NULL 可にする（表を作り直すので Careful。認証の表に触れる）
  - C：最初の運営を、招待を通さずに SQL で作る（Better Auth の行を手で書くことになり、勧めない）
- **WAF のレート制限の上限の数**と、ログインに今かけるか（`docs/safety.md` では v0.7 の前に決める）
- **通知先**：Worker の Cron の失敗と、自宅サーバーのバッチの失敗の受け取り方。案は、自宅サーバーで終了コードを見て、Resend から運営用 Gmail にメールを送る小さな入口を足すこと（コードが要るので別の Issue）。Cron の失敗は Workers のログ（`observability`）を本番で有効にするかと合わせて決める。結果が入らない法案の復旧の手順（docs/spec/71.md）も、ここで一緒に書く
- **`www.` の扱い**：ドメインが決まったときに、`www.` を付けた名前を本来の名前へ送るか
- **remote bindings で `db.batch` が通らなかったとき**の代わり：初回の取り込みは、`readableSeedStatements` と同じく手元の SQLite で取り込んで SQL にし、`wrangler d1 execute --remote --file` で流す。毎日・毎週の同期は別の形を考える
