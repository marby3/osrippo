# 異常の検知と「結果を確認しています」（設計書）

Issue #73。マイグレーションがあり、会期終了時の処理と有効票の結果に関わるので Careful。仕様の正は [docs/spec.md](../spec.md) の「異常の検知と結果の表示」。結果は [docs/spec/71.md](71.md)、IF世界への反映は [docs/spec/72.md](72.md)。画面の案はない（結果のページ `SpResult`・`PcResult` と運営の画面にそろえる）。画面の言葉は `CLAUDE.md` のとおり「確認中」でなく「結果を確認しています」。

仕様で決まっていること：新しいアカウントの急な流入、同じ回線からの集中、同じ並びの投票の連続を検知したら、その法案の結果の公開を保留し、委員長と運営が確認する。経過はモデレーションログで公開する。確定するまで IF世界に反映しない。確定が次の会期にずれ込んだら、確定した時点で反映する。

次のことは仕様書にないので、この Issue の受入基準で確かめる（STOP 1 で確認する。閾値は Issue #63 で「実装の Issue で聞く」としたもの）。

- A. **閾値**（`src/lib/domain/anomalies.ts` の定数。数えた票だけを見る。参考の票は可否に使わないので見ない）
  1. **新しいアカウントの急な流入**：会期が始まる前30日以内に登録した人の票が、その法案で10票以上あり、その割合が、**前の会期**のすべての法案を合わせた割合より30ポイント以上高い。前の会期の数えた票が30票未満なら判定しない（サービスを始めた直後は全員が新しいアカウントになるためと、票が少ないと基準が振れるため）。前の会期の基準からは、確認中と無効の法案の票を除く（攻撃が次の会期の基準を押し上げないように）。同じ会期と比べないのは、攻撃者の票も割り当てでほかの法案に広がり、比べる基準が一緒に上がって、攻撃が大きいほど見逃すため。基準が70%を超える会期（サービスの初期に起きる）では、この種類は働かない
  2. **同じ回線からの集中**：1つの回線から5アカウント以上が投票し、その回線の票がその法案の数えた票の20%以上
  3. **同じ並びの投票の連続**：同じ票が20票以上続き、どの票の間も2分以内（票を最後に入れた時刻の順）。割り当てはくじで人ごとに違うので、複数の法案にまたがる「並び」は比べない
- B. **検知する法案**：可決と否決だけ。廃案は結果を保留する意味が薄いので見ない。修正案の票は見ない（本案が確認中でも修正案の処理は進める。無効にすれば本案ごと廃案になる）。**残るリスク**：多数のアカウントが修正案を通し、本案には棄権すれば、本案の可否は変わらないので保留されず、修正後の条文が IF世界に入る。数えた票になるには割り当てをすべて投票する手間が要り、公開の記録に残るので、v0.4 では受け入れ、β の結果で判断する
- B2. **保留するのは可決が絡むときだけ**：検知した票をすべて除いて数え直し（定足数を含む）、可決から否決か廃案へ、否決から可決へ変わるときだけ保留する。否決から廃案への変化と、変わらないときは保留せず、記録だけ公開する（どちらも IF世界に入らないので、保留しても守るものがない）。誤検知を減らすためと、**少数のアカウントで対立する法案の結果を無期限に止める妨害を防ぐため**。それでも、結果を左右するだけの票を動かせば止められる。後の法案は待たないので、止めた法案を要調整に追い込むこともできる。この残りは人の確認と β の結果で判断する
- C. **保留の中身**：可否も票の数も出さない（「結果を確認しています」だけ）。法案のページと一覧も同じ言葉を出す
- D. **確認する人**：この Issue では運営と運営協力者。委員長は #77 で足す。**提出者と賛同者は確認できず、賛否の数も見えない**（自分の課題を扱えない今の決まりと同じ考え）。投票した人と修正案の提案者・賛同者は除かない（運営の人数が少ない初期に、誰も確認できなくなるため）
- E. **確認の結果**：「結果を確定する」か「この採決を無効にする」の2つで、取り消せない。無効は廃案と同じ扱いで、理由が必須（400字まで。公開する）。票を一部だけ除く操作は作らない（誰の票かを運営が判断することになるため）
- F. **公開する記録**：`/unei` に、見つかった時刻・法案・偏りの種類（3つのどれか）、確定か無効か・対応した人の役職・理由。回線や人数やアカウントは出さない（個人を特定できる情報を出さない）
- G. **期限は設けない**：確認されない法案は確認中のまま。v0.4 に自動で確定する処理は入れない（自動で確定すると、検知の意味がなくなる）

## 目的

票の異常を機械で見つけて結果の公開を止め、人が確かめてから確定する。経過を公開する。

## 範囲

- 入れる：閾値の判定、確認の表、`settleSession` での検知、結果のページ・法案のページ・一覧の表示、反映の保留、運営の画面での確定と無効、公開の記録
- 入れない：委員長の権限（#77）、通知（#78）、共有用の画像（#88）、`stance_log` の立場の切り替えの検知（数えた票の結果に影響しないので入れない。使われ方を見て決める）

## 決めたこと

1. **判定**（`voteAnomalies(votes, previous, sessionStart, quorum)`。純粋な関数）：入力は数えた票の行（`userId`、`registeredAt`、`line`（なければ null）、`choice`、`at`）と、前の会期の新しいアカウントの票数と全票数の2つの整数。戻り値は検知の種類、検知した票、除いたときの可否、運営の画面の集計。割合は小数を使わず整数で比べる。連続は `at` と `userId` の順で見る（同じ時刻でも順が決まる）

2. **材料を読む**（`countedVoteRows(db, session, billId)`。`src/lib/server/results.ts`）：`countedVote` の条件で数えた票の行を読む。回線は、その人のその法案の、**その会期の採決の期間の** `vote_cast` の記録の最後の `ip_hash`（要調整で採決し直した法案が別の会期の記録を拾わないように）。記録のない票は回線なしとして分母に残す。票の材料は締切のあとに変わらないので（docs/spec/71.md 決めたこと1）、何度計算しても同じ。前の会期の2つの数は集計の SQL で1回だけ求める

3. **検知の順**（`settleBill`）：修正案の処理 → 数える → 可決か否決なら判定し、検知があれば `vote_reviews` を `ON CONFLICT DO NOTHING` で入れる（可否が変わるなら `open`、変わらなければ `noted`）→ 結果の行を入れる。結果の行が最後なので、結果の行があれば検知も済んでいる。運営の画面と操作は結果の行がある確認の行だけを扱う

4. **反映の保留**（`applySession`）：未反映の判定に「`vote_reviews` が `open` か `voided` でない」を足す。確定すると `confirmed` になる。確定した操作の中で **`settleSession` を呼ぶ**（`applySession` を直接呼ばない。「すべての結果が入ってから」の確かめは `settleSession` にあるため）ので、次の Cron を待たない。失敗しても確定は取り消さない。**Cron は、直前の会期のほかに、`confirmed` で未反映の法案の会期も処理する**（ずれ込んだ法案は直前の会期でないため）。**後の法案は待たない**（確定が遅れた法案は、新しい変更と衝突すれば要調整になる）
   - `resultOnRead`：確認の行が `open` か `voided` ならすぐ返す（読むたびに処理を走らせない）
   - 読む順は「確定の処理 → 確認の行を読む → 確認中なら結果を返さない」。最初の読者に結果が漏れないように、`resultOnRead` が確認の状態も一緒に返す

5. **段階**（`billStage`）：`reviewing`（結果を確認しています）を足す。順は、確認中 → 無効（`lapsed`）→ 要調整 → 結果。時刻を先に見るのは今までどおり。`noted` と `confirmed` は結果のとおり

6. **結果のページ**：確認中は帯と `noindex` と「結果を確認しています」だけで、可否と票の数を返さない（`__data.json` にも入らない）。無効はサーバーで別の段階にし、「廃案」「確認の結果、この採決は無効になりました」と理由と票の数を出す。**可否の文字、参考の票との比べ、反映先、要調整は出さない**（行の `outcome` は `passed` のままなので、そのまま使わない）。確定は今までどおり

7. **運営の画面**（`/kanri`）：「結果を確認している法案」の欄に、題名、検知の種類、賛成・反対・棄権、`detail` の集計（検知した票の数、回線ごとの最大の票数、最長の連続、除いたときの可否）、確定と無効のボタン、理由の欄（公開されるので個人の情報を書かない注意書きを付ける。空白だけは断る）。確認できない人（決めたことD）には、賛否の数と `detail` を `__data.json` にも入れず、題名と確認できないことだけを出す。`?/confirmReview`・`?/voidReview` の確かめの順は、役職 → 国 → 入力 → 自分の関わり → 状態（`status = 'open'` を条件に入れた1文）

8. **公開の記録**（`/unei`）：今の記録の表と別に「採決の確認の記録」を新しい順に50件ごと。2つの表は別々にページを送る（`?page=` と `?kakunin=`。どちらも `parsePage` を通し、形が違えば 404）。法案へのリンクを付ける。`noted` は「票の偏りが見つかりましたが、結果を左右しないので保留していません」と出す。**確認中の法案の可否が推測されないよう、`detail` は公開しない**

9. **文言**：`ja.review`。画面に「異常」「検知」「確認中」を出さない。公開の記録の種類は「新しいアカウントの票の集中」「同じ回線からの票の集中」「同じ票の連続」
