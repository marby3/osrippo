# 異常の検知と「結果を確認しています」（設計書）

Issue #73。マイグレーションがあり、会期終了時の処理と有効票の結果に関わるので Careful。仕様の正は [docs/spec.md](../spec.md) の「異常の検知と結果の表示」。結果は [docs/spec/71.md](71.md)、IF世界への反映は [docs/spec/72.md](72.md)。画面の案はない（結果のページ `SpResult`・`PcResult` と運営の画面にそろえる）。画面の言葉は `CLAUDE.md` のとおり「確認中」でなく「結果を確認しています」。

仕様で決まっていること：新しいアカウントの急な流入、同じ回線からの集中、同じ並びの投票の連続を検知したら、その法案の結果の公開を保留し、委員長と運営が確認する。経過はモデレーションログで公開する。確定するまで IF世界に反映しない。確定が次の会期にずれ込んだら、確定した時点で反映する。

次のことは仕様書にないので、この Issue の受入基準で確かめる（STOP 1 で確認する。閾値は Issue #63 で「実装の Issue で聞く」としたもの）。

- A. **閾値**（`src/lib/domain/anomalies.ts` の定数。数えた票だけを見る。参考の票は可否に使わないので見ない）
  1. **新しいアカウントの急な流入**：会期が始まる前30日以内に登録した人の票が、その法案で10票以上あり、その割合が、その会期のすべての法案を合わせた割合より30ポイント以上高い。会期全体と比べるのは、サービスを始めた直後は全員が新しいアカウントになるため
  2. **同じ回線からの集中**：1つの回線から5アカウント以上が投票し、その回線の票がその法案の数えた票の20%以上
  3. **同じ並びの投票の連続**：同じ票が20票以上続き、どの票の間も2分以内（票を最後に入れた時刻の順）。割り当てはくじで人ごとに違うので、複数の法案にまたがる「並び」は比べない
- B. **検知する法案**：可決と否決だけ。廃案は結果を保留する意味が薄いので見ない。修正案の票は見ない（本案が確認中でも修正案の処理は進める。無効にすれば本案ごと廃案になる）
- C. **保留の中身**：可否も票の数も出さない（「結果を確認しています」だけ）。法案のページと一覧も同じ言葉を出す
- D. **確認する人**：v0.4 は運営と運営協力者。委員長は #77 で足す。**提出者、賛同者、その法案に投票した人は確認できない**（自分の課題を扱えない今の決まりと同じ考え）
- E. **確認の結果**：「結果を確定する」か「この採決を無効にする」の2つで、取り消せない。無効は廃案と同じ扱いで、理由が必須（400字まで。公開する）。票を一部だけ除く操作は作らない（誰の票かを運営が判断することになるため）
- F. **公開する記録**：`/unei` に、検知した時刻・法案・検知の種類（3つのどれか）、確定か無効か・対応した人の役職・理由。回線や人数やアカウントは出さない（個人を特定できる情報を出さない）
- G. **期限は設けない**：確認されない法案は確認中のまま。v0.4 に自動で確定する処理は入れない（自動で確定すると、検知の意味がなくなる）

## 目的

票の異常を機械で見つけて結果の公開を止め、人が確かめてから確定する。経過を公開する。

## 範囲

- 入れる：閾値の判定、確認の表、`settleSession` での検知、結果のページ・法案のページ・一覧の表示、反映の保留、運営の画面での確定と無効、公開の記録
- 入れない：委員長の権限（#77）、通知（#78）、共有用の画像（#88）、`stance_log` の立場の切り替えの検知（数えた票の結果に影響しないので入れない。使われ方を見て決める）

## 表

`drizzle/0017_*.sql`。新しい表だけで、既存の表は変えない。

| 表 | 列 | 決まり |
| --- | --- | --- |
| `bill_reviews` | `session_key`、`bill_id`（`bills` への外部キー）、`signals`（検知の種類の JSON 配列。`new_accounts`・`same_line`・`same_run`）、`status`（`open`・`confirmed`・`voided`。CHECK）、`note`、`decided_role`（`moderator`・`operator`）、`decided_by`（`user` への外部キー。公開しない）、`decided_at`、`created_at` | 主キー（`session_key`, `bill_id`）。索引：`status` |

判定に使った人数は保存しない（画面で必要なら運営の画面で数え直す）。`bill_results` は変えない。可否の行はそのまま残り、無効は `bill_reviews` で表す。

## 決めたこと

1. **判定**（`voteAnomalies(votes, sessionNewShare, sessionStart)`。純粋な関数）：入力は数えた票の行（`registeredAt`、`ipHash`、`choice`、`at`）。戻り値は検知の種類の配列。割合は小数を使わず整数で比べる

2. **材料を読む**（`countedVoteRows(db, session, billId)`。`src/lib/server/results.ts`）：`countedVote` の条件で数えた票の行を読む。回線は、その人のその法案の `vote_cast` の記録の最後の `ip_hash`。票の材料は締切のあとに変わらないので（docs/spec/71.md 決めたこと1）、何度計算しても同じ。会期全体の割合はその会期の数えた票をまとめて1回読む

3. **検知の順**（`settleBill`）：修正案の処理 → 数える → 可決か否決なら判定し、検知があれば `bill_reviews` を `ON CONFLICT DO NOTHING` で入れる → 結果の行を入れる。結果の行が最後なので、結果の行があれば検知も済んでいる

4. **反映の保留**（`applySession`）：未反映の判定に「`bill_reviews` が `open` か `voided` でない」を足す。確定すると `confirmed` になり、次の処理で反映される。確定した操作の中で `applySession` を呼ぶので、次の Cron を待たない。失敗しても確定は取り消さず、読むときの処理か次の Cron でやり直す。**後の法案は待たない**（docs/spec/72.md の順は結果のある法案の間だけ。確定が遅れた法案は、新しい変更と衝突すれば要調整になる）

5. **段階**（`billStage`）：`reviewing`（結果を確認しています）を足す。順は、確認中 → 無効（`lapsed`）→ 要調整 → 結果。時刻を先に見るのは今までどおり

6. **結果のページ**：確認中は「結果を確認しています」だけで、`bill_results` の数を読まない（`__data.json` にも入らない）。無効は「廃案」「確認の結果、この採決は無効になりました」と理由を出し、票の数は出す。確定は今までどおり

7. **運営の画面**（`/kanri`）：「結果を確認している法案」の欄に、題名、検知の種類、賛成・反対・棄権、確定と無効のボタン、理由の欄。確認できない人（決めたことD）には理由を出してボタンを出さない。`?/confirmReview`・`?/voidReview` の確かめの順は、役職 → 国 → 入力 → 自分の関わり → 状態（`status = 'open'` を条件に入れた1文）

8. **公開の記録**（`/unei`）：今の記録の表と別に「採決の確認の記録」を新しい順に50件ごと（2つの表は別のページ送りにせず、`?kakunin=` で分ける）。法案へのリンクを付ける

9. **文言**：`ja.review`。画面に「異常」「検知」「確認中」を出さない。公開の記録の種類は「新しいアカウントの票の集中」「同じ回線からの票の集中」「同じ票の連続」
