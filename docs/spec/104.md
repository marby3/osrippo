# 似た質疑をまとめる（質疑の整理）（設計書）

Issue #104。取り消せない操作なので Careful。仕様は [docs/spec.md](../spec.md) の「委員長の仕事：質疑の整理」。[docs/spec/77.md](77.md) の決定G で #80 と一緒に作るとしたもので、#80 を分けたのでこの Issue にする。質疑の通報と非表示（[docs/spec/80.md](80.md)）の記録の仕組みの上に作る。決定の記号は分ける前のものを保つ。

## 決定

- R. **まとめる**（`mergeQuestion`）：元の質疑を統合先へまとめる。同じ法案、同じ会期の質疑どうしで、両方が `POST_SHOWN`、元と統合先が別のとき。メモは必須で公開。**扱えない人**：元か統合先が自分の質疑、関わった法案（`involvedInBill`）
- S. **答弁と補足は統合先に移る**（`parent_id` を付け替える。非表示のものもそのまま移る）。元の質疑は `merged` になり、一覧に出ず、「質疑 N」と「答弁待ち N」に入らない。統合先のカードには「同じ内容の質疑を N 件まとめました」とだけ出し、**元の本文は公開しない**（本文を個別に隠す手段が要らないように）。元にまとめられていた質疑も統合先へ移す（1段だけになるように。記録の `merged_into` は当時の統合先のまま）
  - **答弁が自分の質疑の下に移ることは許す**（書くときは断っているが、まとめた結果であり、書いた人の操作ではない）。自分の投稿なので評価はできない
- 元の本文は、書いた本人にだけ、質疑のタブの「すべて」の1ページ目の最後の欄に、統合先へのリンクと一緒に出す。**統合先があとで非表示になったら**、リンクの代わりに「まとめた先の質疑は今は非表示です」と出す（理由と本文は出さない）。運営にも出さない
- T. **元に戻せない**（課題の統合と同じ）。都合の悪い質疑を無関係の質疑へまとめる使い方は、公開の記録とメモ、書いた本人への通知と統合先へのリンクで分かるようにするが、外から本文は確かめられない（STOP 1 で確認する）
- U. **評価**：元の質疑の評価はスコアに残し、立候補の資格にも数える（書いた人の質疑が無くなったわけではない）。新しくは押せない
- V. **操作の場所**：`/kanri?post=<番号>` で指した質疑が `POST_SHOWN` のとき、その行に、同じ法案と会期のほかの質疑（`POST_SHOWN`。見ている人の質疑は除く）を本文つきで新しい順に50件並べ、1つ選んでメモを書いてまとめる（`?/mergeQuestion`。フォームの `post`、`target`、`note`。元に戻せないことを出す）。投稿の番号は画面に出さない
- **確かめの順**：役職（404）→ 国（403）→ 入力（400）→ 元の存在（404）→ 元が自分のもの（403）→ 関わり（403）→ 統合先が自分のもの（403）→ 状態（元と統合先の条件。400）
- **`merged` の扱い**：どこにも移らない。`?post=` と通報は 404（行がないのと同じ。通報のある質疑をまとめたあとも `/kanri` の一覧に出さない）。答弁と補足は 403 と「この質疑は別の質疑にまとめられました」（開いたあとにまとめられたとき。一覧の上に出る）。運営の非表示と表示に戻すは 404
- **通知**：元の質疑を書いた人に `question_merged`（`target_id` は元の投稿、`ref_id` は `status_changed_at`。文は法案の題名、リンク先は質疑のタブ）。**2段目で統合先が変わった人には届けない**（本文もリンクも今の統合先を指していて、起きたことは最初の通知と同じ）。下の答弁と補足を書いた人にも届けない（読む場所は変わるが、投稿はそのまま）
- **公開の記録**：`/unei` の行に、何か「質疑」、何をしたか「統合」、だれが、メモ。統合先の番号と本文は出さない。委員長の役職の操作は「最後の操作」に数える（`bill_moderation_logs` を見ているので足すものはない）

## 決めたこと

1. **表**（`drizzle/0025_*.sql`）：`posts` に `merged_into`（外部キーなし）と索引、`bill_moderation_logs` に `merged_into`。トリガー `posts_status_log` は `DROP` して作り直す（`merged` を `merge` にし、`merged_into` も書く）。`schema.ts` の `action` に `merge`、`posts.status` に `merged` を足す（型だけ）。既存の行は変えない
2. **ルール**（`src/lib/domain/reports.ts`）：`POST_SCORED = [...POST_SHOWN, 'merged']`（スコア）、`POST_CANDIDACY` に `merged` を足す
3. **読むところを直す**：`sessionPostScores` は `POST_SCORED`（今の `scored` を評価の対象と分ける）。`reportPost`、`postStaffAccess` は `merged` を行がないものとして扱う。`reportedPosts` は `merged` を除く。`questionOf` の受け付けは表示中でなければ断る。`createPost` の INSERT に列を1つ足す。`listQuestions` はカードに `mergedCount` を返す（`merged_into` を数える副問い合わせ）。`hrefOf`、`targetOf` に `question_merged` を足す
4. **操作**（`src/lib/server/post-moderation.ts`）：`mergeQuestion`、`mergeCandidates`、`mergedPostsFor`。`mergeQuestion` は `db.batch` で、(a) 元の行を `merged` に（元が今 `POST_SHOWN` で、統合先が今 `POST_SHOWN` の同じ法案と会期の質疑である条件を同じ文に入れる。A→B と B→A が同時でも循環しない）、(b) 元にまとめられていた行の `merged_into` を統合先に、(c) 答弁と補足の `parent_id` を統合先に。(b)(c) の条件に「元が今 `merged` で統合先がこれ」を入れる。batch の中は builder だけ。(a) が当たらなければ `false`。通知は batch のあと
5. **画面**：質疑のタブのカードに「同じ内容の質疑を N 件まとめました」、最後の欄に「まとめられた質疑」。`/kanri` の行にまとめる欄。文言は `ja.ts`

## 範囲

- 入れない：統合の取り消し、関連法案や別の会期をまたぐ統合、修正案の統合、元の本文の公開
