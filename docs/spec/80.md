# 質疑・答弁・補足と修正案の通報と非表示、質疑の整理（設計書）

Issue #80。マイグレーション（列、表、トリガーの追加）と、運営の画面の権限に関わるので Careful。仕様は [docs/spec.md](../spec.md) の「モデレーションの方針」と「委員長の仕事：質疑の整理、通報の一次対応」。課題の通報は [docs/spec/28.md](28.md)、解決策は [docs/spec/36.md](36.md)。あとで決めるとしていたこと：docs/spec/66.md（非表示の答弁の数え方、1枚のカードの件数の上限）、docs/spec/67.md（非表示の投稿の評価）、docs/spec/68.md（修正案の通報と非表示）、docs/spec/77.md の決定G（似た質疑をまとめる）、docs/spec/78.md（通知）。

解決策（docs/spec/36.md）と同じ決まりを投稿と修正案に広げる。仕様書に定めがないところは次のとおりで、この Issue の受入基準で確かめる（STOP 1 で確認する）。

## 決定

### 通報

- A. **対象**：質疑、答弁、補足、修正案。理由は解決策と同じ「人への攻撃・差別」「宣伝・荒らし」「その他」（任意）。「その他」の説明は200字まで
- B. **自動非表示**：解決策と同じく、登録から24時間たった別々の3人の通報（`countsTowardHide`）で自動で非表示。表示に戻したあとは自動では消えない。**その法案に関わった人（提出者、賛同者、共同提出者）の通報は数に入れない**（当事者が組んで、自分たちの法案への質疑や修正案を消せないように）。修正案は、同じ法案に修正案を出した人の通報も数に入れない。記録の理由は「通報が3件」
- C. **上限**：1アカウント24時間に10件。課題と解決策の通報と合わせて数える。超えると違反に数える。1人1件で、2回目は何もしない。自分の投稿と修正案は通報できない
- D. **受け付けの順**：番号と存在（404）→ ログイン → 国 → 締め出し → 入力 → 自分のもの → 状態 → 2回目 → 上限 → 保存。Turnstile は使わない（課題と解決策と同じ）

### 見え方

- E. **質疑を非表示にすると、カードごと出さない**（答弁と補足も一緒に）。「質疑 N」に入れない。答弁と補足の行は残り、表示に戻すと戻る。下の答弁と補足には評価も読んだ記録も付けられない（親の質疑の状態も条件に入れる）。下の答弁は、書いた人の責任ではないので、スコアと立候補の資格には数える。書いた人には質疑のタブに「質疑が非表示のため出ていません」と出す（質疑の中身と理由は出さない）
- F. **答弁を非表示にすると、答弁に数えない**。ほかに答弁がなければ、その質疑は「答弁待ち」に戻る。補足は数に関わらない
- G. **1枚のカードの件数に上限は設けない**（今のレート制限のまま。全部読む。使われ方を見て決める）
- H. **本人と運営にだけ見せる**：書いた本人と、運営の画面の権限のある人には、質疑のタブの1ページ目の最後に、自分の（運営はその法案の）非表示の投稿の本文、理由、「非表示になっています」を出す。ほかの人には何も出さない。修正案も同じ（修正案のタブ）。**関わった法案（決定O）では、運営の権限があっても自分のものしか出さない**。「運営として対応する」のリンクも出さない
- I. **非表示のあいだは何もできない**：答弁、補足、評価、読んだ記録の対象にしない。評価の行は残し、スコアに数えない。表示に戻すと数える（docs/spec/67.md）
- J. **立候補の資格**：表示中と、表示に戻した投稿と、まとめられた質疑を数える。非表示は数えない

### 修正案

- K. **非表示は `status` と別の列**（共同起草者を `status` から求めているので。docs/spec/68.md。値は `visible`・`auto_hidden`・`hidden`・`restored`）。非表示のあいだは「修正案 N」に入れず、賛同、投票、取り込み、更新ができない。先議の数にも入らない。`status` が何でも非表示にできる（理由の文に攻撃があれば、結果のあとでも隠せるように）
- L. **会期の処理のときに、委員長か運営が非表示にした修正案（`hidden`）は採決しない**（`status` を `unvoted` にする）。入っていた票は数えない。**自動の非表示（`auto_hidden`）は採決から外さない**（3人の通報で、採決の直前に対抗案を外せないように。票を入れられないだけで、入っていた票は数える。STOP 1 で確認する）。結果が書かれたあとは、表示に戻しても採決はやり直さない
- M. **結果のあとの非表示**：取り込みや可決で本文に当たった変更と共同起草者は変えない（書き手の名前は法案の共同起草者に出たまま。内容はすでに法案の本文）

### 運営の画面

- N. **`/kanri` に2つの区画を足す**：「通報を受けた質疑・答弁・補足」「通報を受けた修正案」。自動で非表示が先、最後の通報が新しい順に100件。`?post=<番号>`・`?amendment=<番号>` でそれを上に出す（通報されていないものも扱える。法案のタブの「運営として対応する」のリンクから）。**自分のものと関わった法案の行は一覧に出さない**（本文も通報の文面も渡さない。`?post=` で指しても 404）
- O. **扱えない人**：自分の投稿と修正案。**関わった法案**（`involvedInBill`。提出者、賛同者、共同提出者。委員長と理事は投票した法案も）の投稿と修正案は、全部の役職で扱えない（質疑は提出者と賛同者に向けたものなので、当事者が消せないように）。修正案はさらに、同じ法案に修正案を出した人、その修正案に賛同した人、委員長と理事はその修正案に投票した人も扱えない（対抗案を消せないように）。受け付けでも 403
- P. **操作**：非表示にする（理由とメモ）、表示に戻す（メモ）。課題と解決策と同じ確かめ（`validateSolutionAction`）。確かめの順は、役職 → 国 → 入力 → 自分のもの → 関わり → 状態
- Q. **権限**：委員長と代行の理事は運営と同じ（docs/spec/77.md）。委員長の役職で行った操作は「委員長の最後の操作」に数える。代行の理事の操作は数えない

### 質疑の整理

- R. **似た質疑をまとめる**（`mergeQuestion`）：元の質疑を統合先へまとめる。同じ法案、同じ会期の質疑どうしで、両方が表示中か表示に戻した状態、元と統合先が別のとき。自分の質疑（元でも統合先でも）と関わった法案は扱えない。メモは必須で公開
- S. **答弁と補足は統合先に移る**（`parent_id` を付け替える。同じ人の答弁が2つになっても、1人1答弁の決まりはないので問題ない）。元の質疑は `merged` になり一覧に出ず、「質疑 N」に入らない。統合先のカードには「同じ内容の質疑を N 件まとめました」とだけ出し、**元の本文は公開しない**（本文を個別に隠す手段が要らないように。文面が要るのは書いた本人と運営だけ）。元の本文は書いた本人にだけ質疑のタブの1ページ目の最後に出す。元にまとめられていた質疑も統合先へ移す（1段だけになるように。記録の `merged_into` は当時の統合先のまま）
- T. **元に戻せない**（課題の統合と同じ）
- U. **評価**：元の質疑の評価はスコアに残し、立候補の資格にも数える（書いた人の質疑が無くなったわけではない）。新しくは押せない
- V. **操作の場所**：`/kanri?post=<番号>` の質疑の欄に、同じ法案と会期の表示中のほかの質疑を本文つきで並べ（新しい順に50件）、1つ選んでメモを書いてまとめる（フォームの `target`。元に戻せないことを出す）。投稿の番号は画面に出さない

### 記録と通知

- W. **公開の記録**：`/unei` に「法案の質疑と修正案への対応」の区画を足す（日時、法案、何か（質疑、答弁、補足、修正案）、何をしたか、だれが、理由、メモ）。本文、書いた人、通報した人は出さない。新しい順に50件ごと
- X. **通知**：書いた人に、非表示、表示に戻した、まとめられた、を届ける（`post_hidden`、`post_restored`、`question_merged`、`amendment_hidden`、`amendment_restored`）。`ref_id` は状態を変えた時刻。リンク先は質疑のタブと修正案のタブ

## 決めたこと

1. **表**（`drizzle/0023_*.sql`。既存の表には `ADD COLUMN` だけ。生成された SQL に表の作り直しがないことを確かめる）：
   - `posts` に `status_actor`、`status_actor_user_id`、`status_reason`、`status_note`、`status_changed_at`、`merged_into`（外部キーは付けない）を足す。`status` は今の列をそのまま使い（CHECK はない。確かめた）、値は `visible`・`auto_hidden`・`hidden`・`restored`・`merged`。索引（`merged_into`）
   - `amendments` に `moderation_status`（既定 `visible`）、`moderation_actor`、`moderation_actor_user_id`、`moderation_reason`、`moderation_note`、`moderation_changed_at` を足す
   - `post_reports`、`amendment_reports`（`id`、対象の番号、`user_id`、`reason`（CHECK）、`note`、`counted`、`created_at`。一意（対象、`user_id`）。索引（`user_id`, `created_at`））
   - `bill_moderation_logs`（`id`、`bill_id`、`post_id`、`amendment_id`、`action`、`actor`、`actor_user_id`、`reason`、`note`、`merged_into`、`created_at`。索引（`actor_user_id`, `created_at`））。`moderation_logs` は `issue_id` が NOT NULL で、変えると表の作り直しになるので別の表にする
   - トリガー `posts_status_log`（`status` を見る）、`amendments_moderation_log`（`moderation_status` を見る）（手で書く。`solutions_status_log` と同じ）。変わったら同じ文の中で記録を書く。更新の文は `status_*` か `moderation_*` を全部書く（前の理由やメモが記録に残らないように）。表を作り直すとトリガーが消えるので、`schema.ts` に注意書きを足す

2. **ルール**（`src/lib/domain/reports.ts`）：`POST_SHOWN = ['visible', 'restored']`、`POST_WRITTEN = [...POST_SHOWN, 'merged']`。理由の判定は `validateSolutionReport` を使う

3. **読むところを直す**（`posts` と `amendments` を読むところを表で洗い出した。下にないのは、`evaluations.ts` の押した評価の読み出し（自分の押した印だけ）と、通知の題名（書いた本人に届くもの）、`results.ts` の修正案の結果（条の番号と結果だけで本文を出さない）、`coDrafters`（決定M））：
   - `posts.ts` の `questions`、`unanswered`、答弁と補足の読み込みは `POST_SHOWN`。`questionOf`（答弁と補足の親）も `POST_SHOWN`（今は状態を見ていない）。カードの「まとめた数」は `merged_into` で数える
   - `evaluations.ts`：`evaluationTarget`、`recordViews` は `POST_SHOWN` で、答弁と補足は親の質疑も `POST_SHOWN`。`sessionPostScores` は `POST_WRITTEN`（親の状態は見ない。決定E）
   - `chairs.ts` の `standBlock` は `POST_WRITTEN`
   - `amendments.ts`：`amendmentCount`、`listAmendments`、`priorVoteCount`、`setAmendmentSupport`、`castAmendmentVote`、`acceptAmendment`、`updateAmendment` に非表示の条件を足す（書く文の条件にも入れる）。`settleAmendments` は `hidden` だけを `unvoted` にする。`auto_hidden` は採決の対象のまま（賛同の数も数える）

4. **操作**（`src/lib/server/post-moderation.ts`）：`reportPost`、`reportAmendment`、`changePostStatus`、`changeAmendmentModeration`、`mergeQuestion`、`reportedPosts`、`reportedAmendments`、`hiddenPostsFor`、`hiddenAmendmentsFor`、`billModerationLogPage`。状態の変更は条件を入れた1文で、変わったときだけ通知する。`mergeQuestion` は `db.batch`（元の行、元にまとめられていた行、答弁と補足の付け替え）。最初の文に、元が今 `POST_SHOWN` で、統合先が今 `POST_SHOWN` の同じ法案と会期の質疑であることを入れ（同時に A→B と B→A が走っても循環しない）、あとの2つの文に「元が今 merged で統合先がこれ」を入れる。`reportsInDay` は4つの表を数える

5. **委員長の最後の操作**：`lastChairAction` に `bill_moderation_logs`（`actor = 'chair'`）を足す

6. **画面**：`QuestionCard` の質疑、答弁、補足と `AmendmentCard` に「通報する」（`SolutionCard` と同じ開き方。出さないとき：自分のもの、通報済み（「通報済みです」）、非表示）。受け付けは質疑のタブの `?/reportPost`、修正案のタブの `?/reportAmendment`。運営の権限のある人には「運営として対応する」のリンクと質疑の番号

7. **文言**：`ja.report`、`ja.kanri`、`ja.unei`、`ja.notifications` に足す。`ja.unei.criteria` に質疑と修正案を足す。自動の非表示の理由は `reports`（「通報が3件」）

## 範囲

- 入れる：上の決定のすべて
- 入れない：異議申し立て、通報した人への結果の知らせ（課題と解決策と同じ）、修正案の統合、質疑の統合の取り消し、関連法案をまたぐ統合、カードの件数の上限、まとめた質疑の本文の公開
