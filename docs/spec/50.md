# 法案の状態の進み方（設計書）

Issue #50。会期の終わりの処理に当たるので Careful（ROADMAP.md の「モード」）。マイグレーションはない。仕様の正は [docs/spec.md](../spec.md) の「状態：下書き → 発議 → 委員会付託 → 質疑 → 採決 → …」と「会期」の項。法案の表は [docs/spec/45.md](45.md)、賛同と発議は [docs/spec/49.md](49.md)、会期の区切りは `src/lib/domain/session.ts`（#44）。

仕様書にない次のことは、ユーザーと決めた（Issue #41 の決めたこと。仕様書のドキュメントへの反映はユーザー側）。

- 14日の終わり（発議の締切）に、その会期に発議した法案を委員会に付託し、15日から質疑、22日から採決の状態にする（決めたこと5）
- 会期の終わりに、定足数に届かない法案を廃案にする。v0.3 には採決がないので、付託した法案はすべて廃案になる
- 15日以降に発議した法案は、次の会期に付託する
- 画面の状態は「下書き・発議・質疑・採決・廃案」。付託は質疑の始まりと同じ時刻なので、別の状態としては出さない
- 下書きは会期をまたいで残る（仕様「廃案になるのは発議した法案だけ」）
- 会期と法案の状態は時刻から求め、「最後に処理した時刻」に頼らない（Issue #41 レビュー）

## 目的

発議した法案が時刻とともに質疑・採決・廃案へ進み、一覧の「終わった」のタブに移るようにする。あわせて、大きく書きかえた条の変更点を読める形にする（締めのテストが、ここで止まっていた）。これで `e2e/phase3.spec.ts` が通り、v0.3 を出せる。

## 範囲

- 入れる：法案の進みを求める純粋な関数、法案のページと一覧の出し方、一覧のタブの分け方、変更点のまとめ方
- 入れない：質疑・採決・定足数の計算（v0.4）、廃案から出し直すこと（v0.4）、共同提出者と撤回（v0.4）、状態が変わったときの通知（v0.4）、締切のあとに発議した人への別の案内（次の段の日付で分かるので足さない）

## 表

変えない。マイグレーションはない。

- `bills.status` は `draft` と `proposed` のままで、質疑・採決・廃案は書き込まない。`bills.proposed_at`（#49）と時刻から求める
- `bills_status_created` のほかに索引を足さない。審議中と終わったのタブは、発議した法案の行をすべて読んで `proposed_at` で分ける。発議した法案は会期ごとに多くても数十本で、一覧の1回の読みで数百行を超えるのは先の話なので、v0.4 で状態の列の持ち方を決めるときに一緒に見直す

## 決めたこと

1. **書き込まない**：進みは読むときに求める。cron も、「その会期の処理を済ませた」という印も持たない。時刻が戻っても進みが正しく戻る。賛同・発議・保存の確かめは今の `status` のままで、`proposed` の法案は編集も賛同もできない（#49 のまま）
   - 持ち越した下書きの発議も #49 のまま：賛同は会期をまたいで数え、発議要件は「発議する」を押した会期の人数と比べる（docs/spec/49.md の「この Issue で決めたこと」と決めたこと5）。15日以降の発議も、押した会期の要件で判定し、付託だけ次の会期になる
2. **付託先の会期**（`referralSession(proposedAt, minutes)`。`src/lib/domain/bills.ts`）：`proposedAt` を含む会期を S とする
   - `proposedAt < S.deliberationAt` なら S
   - それ以外は S の次の会期（`sessionAt(S.endsAt, minutes)`）
   - 14日 23:59:59.999 の発議は S、15日 0:00:00.000 の発議は次の会期
3. **進み**（`billProgress(bill, now, minutes)`。純粋な関数）：`bill` は `{ status, proposedAt }`。付託先の会期を R とする

   | 条件 | 進み | 画面の名前 |
   | --- | --- | --- |
   | `status = 'draft'` | `draft` | 下書き |
   | `now < R.deliberationAt` | `proposed` | 発議 |
   | `R.deliberationAt ≤ now < R.voteAt` | `deliberation` | 質疑 |
   | `R.voteAt ≤ now < R.endsAt` | `vote` | 採決 |
   | `R.endsAt ≤ now` | `lapsed` | 廃案 |

   - `proposedAt` のない `proposed` の法案は起きない（`proposeBill` が1文で両方を入れる）。型のために `billProgress` では `proposed` として扱うが、一覧の SQL ではどちらのタブにも入らない。起きないので、これ以上の扱いは足さない
   - 次の段の始まり（`nextStageAt(bill, now, minutes)`）：`proposed` なら `R.deliberationAt`、`deliberation` なら `R.voteAt`、それ以外は `null`
   - 発議より前の時刻（`x-test-now` を戻したとき）は `now < R.deliberationAt` なので `proposed`。下書きには戻らない。`status` は書きかわっているので、これでよい
4. **一覧の分け方**（`lapsedBefore(previous)`。`previous` は `sessionsAt(now)` の一つ前の会期。戻り値は `proposed_at` と同じミリ秒の整数）：発議した法案のうち、`proposed_at < previous.deliberationAt` のものが廃案、それ以外が審議中
   - **`billProgress` と同じ結果になる理由**：`now` を含む会期を C とする。廃案は `R.endsAt ≤ now`、つまり R が C より前の会期のとき。R が C の一つ前の会期（previous）以前になるのは、`proposed_at` が previous の締切より前のときだけ（previous の締切からあとの発議は C か、その先に付託される）
   - 暦の計算を SQL に持ち込まずに、1つの値との比べで絞れる。単体テストで、`lapsedBefore` の値のちょうどとその1ミリ秒前の発議について `billProgress` と結果が同じことを確かめる
   - `listBills(db, tab, page, lapsedBefore)` と `billTabCounts(db, lapsedBefore)` が受け取る。呼ぶ側は `sessionsAt(nowOf(event))`
   - `billTabCounts`：`shingi` は `status = 'proposed' AND proposed_at >= ?` の数。1文で下書きと一緒に数える
5. **一覧の並び**
   - 審議中：今のまま（作ったのが新しい順。#48 決めたこと1）
   - 終わった：発議が新しい順（`proposed_at` の降順、同じなら `id` の降順）。作ったのが古くても、最近終わった法案が上に来るように
6. **画面の名前**（`src/lib/copy/ja.ts`。`ja.bill.statuses` を置きかえる）
   - スマホの法案のページ（SpBillSummary）：「いま：」のあとに、発議・下書き・廃案はその名前、質疑は「**質疑**（3週目）」、採決は「**採決**（4週目）」。分の会期でも同じ言葉
     - 発議と質疑のときは、次の行に「質疑は5月15日から」「採決は5月22日から」と出す。案にはないが、PC の段階の日付と同じことがスマホでも分かるように足す（締切のあとに発議すると、約1か月「発議」のままになるため）
   - PC の法案のページ（PcBillSummary）：いまの段階の並び「下書き・発議・委員会へ・質疑・採決・結果」
     - いまの段：下書き 0、発議 1、質疑 3、採決 4、廃案 5。「委員会へ」は過ぎた印が付くだけで、いまの段にならない（Issue #41 レビュー）
     - いまの段が発議なら質疑の段に、質疑なら採決の段に、案のとおり「質疑（5月15日から）」「採決（5月22日から）」と日付を出す。締切のあとに発議した法案は次の月の日付になるので、いつ始まるかが分かる。分の会期は時刻まで出す（`sessionPoint` と同じ）
     - 廃案のときは最後の段「結果」を「廃案」と出す
   - 一覧（SpBills・PcBills）：下書き・発議・質疑中・採決中・廃案（案の「質疑中」に合わせる。法案のページは案の「質疑」に合わせる）
7. **画面に出すもの**：`+layout.server.ts` が `progress`（進みの名前）と `nextStageAt` を求めて渡す。一覧は `src/routes/houan/+page.server.ts` が行ごとに `billProgress` を求める（`listBills` が `proposedAt` を返す）。質疑・採決・廃案のときも「賛同 N人」は出す。編集・賛同・発議のボタンは今の条件（`status = 'draft'`）のままなので出ない
8. **会期の分数**：`sessionsAt(now)` の戻り値に `minutes` を足す。`billProgress` と `nextStageAt` を呼ぶときに使う
9. **変更点のまとめ方**（`changeDiff`）：文字ごとに比べると、大きく書きかえた条では「契約」「を」「め」のような偶然同じ文字が残り、文がばらばらになる。比べたあとで、前後の変更より短い共通部分を変更に含める
   - 共通部分の字数が、前の変更（消す字数と足す字数の多いほう）以下で、かつ後ろの変更についても同じときにまとめる。まとめると変更が長くなるので、前へさかのぼって同じ確かめを続ける
   - 「。」か改行を含む共通部分はまとめない。変わっていない文や項が、変わったように読めないようにする
   - 比べの結果を1回なめるだけで終わる（積み上げ式）。比べの手間の上限（`DIFF_MAX_EDIT`・`DIFF_PAGE_BUDGET`）と `cost` の数え方は変えない。`cost` はまとめる前の字数で数える
   - 例：消費者契約法第1条を「この法律は、消費者がいつでも契約をやめられるようにすることを目的とする。」にすると、「＋がいつでも契約をやめられるように」が1つにまとまる（手元で確かめた）。「十日以内に書面で」→「二十日以内に電子メールで」は「＋二」と「−書面」「＋電子メール」のまま分かれる
   - 法令の時点比較（`src/lib/domain/law/compare.ts`）は変えない。項と号の単位に揃えて比べていて、この問題が報告されていない

## テストの方針

- 単体テスト：`referralSession` と `billProgress` の境界（基準1・2）、`lapsedBefore` と `billProgress` の結果が同じこと、`listBills` と `billTabCounts` のタブ分けと並び（基準4）、`changeDiff` のまとめ方（基準7）
- 画面のテスト（2幅）：法案のページの状態と段階の日付、締切のあとに発議した法案、一覧の段階の名前、質疑・採決・廃案でボタンが出ず、POST が断られること、下書きが次の会期でも賛同を保ったまま発議できること
- 締めのテスト：`e2e/phase3.spec.ts` をそのまま通す
- 新しい入力は受け付けない（`?tab=` と `?page=` は今のまま）ので、信頼の境界のテストは足さない

## あとで決めること（v0.4）

- 採決の結果を DB に書くときの形。定足数と可決・否決が入ると、`lapsed` は「結果がなく、会期が終わった」だけを指すことになる。結果を確定する処理も、時刻から求める形を保てるかを決める
- 廃案から出し直すこと（仕様「課題に戻り、再提出できる」）
- 状態が変わったときの通知。進みを書き込まないので、状態が変わる瞬間に動くきっかけがない。通知を入れるときに決める
- 法案の数が増えたときの索引（`status`, `proposed_at`）
