# 立場を超えた支持順（課題の橋渡しスコア）（設計書）

Issue #126。票を読んで課題の並びを決め、統計の匿名化の基準（10人）に触るので Careful。仕様は [docs/spec.md](../spec.md) の「課題の橋渡しスコア」：「わかる」を付けた人を、その人の直近の採決での立場（賛成が多い法案の傾向）でグループに分け、グループごとの「わかる」率の低いほうを採る。グループ分けに使う投票履歴が10人分未満なら、「わかる」の数で並べる。画面の案は `SpIssues`・`PcIssues` の並び「立場を超えた支持順」（案の既定）。docs/spec/25.md 決めたこと4 で後回しにしていた。

受入基準と決めること A〜D は Issue #126（2026-11-10 ユーザーと決定）。この設計書は、その中身を実装の形にする。マイグレーションはない。

## 決めたこと

### 1. グループ（決めること A・B）

- 会期は **直近に締め切った会期**（`sessionsAt(now).previous`）。その会期の票（`votes.session_key = previous.key`）だけを読む。締め切ったあとは票そのものは変わらない
- 使うのは **数えた票** だけ。条件は採決の結果と同じ `countedCondition(previous, votes)`（会期の始まりより前に登録して参加の行動があり、割り当てのすべてに票を入れた人の票）。参考の票は使わない（作ったばかりのアカウントで並びを動かせないように）
- **確認中（`vote_reviews.status = 'open'`）と無効にした（`'voided'`）法案の票は使わない**。異常を検知した票で並びが動かないように。`noted`（記録だけ）と `confirmed` は使う。会期の締めの処理（`settleOnRead`・Cron）の前は確認の行がまだないので、締めの処理が走るまではその会期の票をそのまま使う（一覧を読むたびに締めの処理を走らせるのは重いのでしない）。**そのためグループは、会期の締めのあと、締めの処理のあと、確認中の法案を運営が判断したあと（`open` → `confirmed` で票が戻る、`voided` で外れる）に変わりうる**。それ以外のときは変わらない
- 人ごとに、その会期の数えた票の賛成と反対を数え、**賛成が多い人は「賛成寄り」、反対が多い人は「反対寄り」**。同じ数の人と棄権だけの人は、どちらにも入れない
- グループに入らない人の「わかる」は、この並びに効かない（分子にも分母にも入れない）。「わかる」の数（表の「わかる」の列、「わかる」の多い順）には今までどおり入る
- 課題そのものには立場がない。分けるのは「わかる」を付けた人の側（決めること B）

### 2. スコアと並び

- 課題ごとに、賛成寄りのうちその課題に「わかる」を付けた人の割合 `a / A` と、反対寄りの割合 `b / B` を出し（`A`・`B` はグループの人数）、**低いほう `min(a / A, b / B)`** をスコアにする
- **課題ごとの10人の基準（決めること E、2026-11-10 ユーザーと決定。設計レビューの指摘から）**：その課題に「わかる」を付けた人が、賛成寄り（`a`）と反対寄り（`b`）の**どちらも10人以上のときだけスコアを使う**。どちらかが10人未満の課題はスコアを使わない。グループ全体が10人以上でも課題ごとの区分が1人だと、並びと「わかる」の数から、その1人がどちらのグループかを推定できるため（仕様書「10人未満の区分は表示しない」を課題ごとにも当てはめる）
- 並びは、スコアを使う課題を先に スコアの高い順、そのあとにスコアを使わない課題。どちらの中でも 同じなら「わかる」の数の多い順 → 新しい順（id の大きい順）
- 「わかる」を取り消すと、その人は分子から外れる（今の「わかる」の行だけを数える）

### 3. 人数が足りないとき（10人の基準）

- `A < 10` か `B < 10` なら、**「わかる」の多い順で並べる**（今の `support` と同じ順）。画面には一覧の上に「人数が足りないので、いまは「わかる」の多い順に並べています」と出す（基準3）
- 10人は仕様書の「匿名化の基準：10人未満の区分は表示しない」と同じ数。グループごとに見る（片方でも足りなければ使わない）
- 判定は一覧を読むたびに行う。注記と真偽は並びが `bridge` のときだけ出す

### 4. 出さないもの（基準5）

- スコア、`a`・`b`・`A`・`B`、だれがどちらのグループかは、画面にもページのデータ（`+page.server.ts` の戻り値）にも入れない。`listIssues` は並べるためにだけスコアを使い、行の値に入れない
- ページのデータに入れるのは「人数が足りないので「わかる」の多い順にした」かどうかの真偽だけ（グループの人数そのものは出さない）

### 5. 並びの選択肢と URL（基準1・4、決めること D）

- `SORTS` に `bridge` を足し、**既定にする**。`parseListQuery` は `sort` がなければ `bridge`。**今は 404 にしている `sort=support` を受け付けるように変え**、`sort=support`・`new`・`rising` を受け付ける。`sort=bridge` は形が違う（404。既定は `sort` なしの1つの URL だけにする。`page=1` を受け付けないのと同じ考え）
- `listHref` は `bridge` のとき `sort` を付けず、`support` のときは `sort=support` を付ける。今までの `sort` なしの URL は「立場を超えた支持順」になる
- 文言：`ja.issue.sorts.bridge = '立場を超えた支持順'`。並びの選択欄の最初に置く

### 6. 計算のしかた（決めること C）

読むときに計算し、新しい表は作らない。**並びが `bridge` のときだけ計算する**（`support`・`new`・`rising` を選んだときはグループを作らず、注記も真偽も出さない）。

- グループの CTE は **1つの文の中で1回だけ** 作り、人数（`A`・`B`）と課題ごとの集計の両方に使う。`votes` を直近の会期・数えた票・確認中と無効を除いて人ごとに集め、`side`（`for`・`against`）を決める
- 一覧：その CTE を `issue_supports` に LEFT JOIN し、課題ごとに `count(CASE WHEN side = 'for' THEN 1 END)` と `against` を数え、`min(a * 1.0 / A, b * 1.0 / B)` で並べる。人数が足りないかは同じ文の中で `A`・`B` から求め、足りなければ `support` と同じ順にし、足りなかったことを行と一緒に返す（並べ方が変わるだけで、絞り込み・探す言葉・ページ送りは今の `listIssues` のまま）
- 重さ：`votes` は `(session_key, bill_id, user_id)` の主キーで会期ごとに引けるが、**数えた票かの判定（`countedCondition`）は票の1行ごとに相関副問い合わせ（`actions` の EXISTS と、割り当てと票の NOT EXISTS）を持つ**。そのため一覧を開くたびに、直近の会期の票の行の数だけこの判定が走る。β の規模（1会期の票が数千）までは読むときの計算にする
- 参加者が増えて重くなったら、会期の締めの処理でグループを表に保存する形に移す（その時はテーブルを足すだけのマイグレーション）。**そのときは、確認中の法案を判断したときにも作り直す**

## テスト

- 基準ごとに1本。計算と10人の基準は DB のテスト（`src/lib/db/` の memory DB）で確かめる。画面のテストで2つのグループに10人ずつ数えた票を作るのは重いため
  - DB（基準2・3・5を1本ずつ。次は1本の中で確かめる項目）：グループの分け方（賛成が多い・反対が多い・同じ数・棄権だけ・参考の票・確認中と無効の法案の票・前の会期の票）、スコアの順（低いほうを採る、同じなら「わかる」の数、新しい順）、10人の基準（片方9人で「わかる」の多い順）、行の値にスコアが入らないこと
  - URL：`sort` なしが `bridge`、`sort=bridge` は 404、`listHref` の往復（ユニットテスト）
  - 画面：並びの選択肢に「立場を超えた支持順」があり既定で選ばれていること、人数が足りないときの注記（e2e の DB は直近の会期に数えた票が足りないので、注記が出る側を確かめる）
