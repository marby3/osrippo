# 議員・有識者の認証（設計書）

Issue #157。認証に触れるので Careful。仕様は [docs/spec.md](../spec.md) の「議員・有識者向け機能と認証」：事務所・本人の確認は運営が手作業で行い、認証は1年ごとに更新し、付与と取り消しは記録して公開する。認証バッジは未認証のアカウントと見た目ではっきり区別する。

受入基準は Issue #157、前提の決定は Issue #147 の決めること1〜3・5（2026-11-10 ユーザーと決定）。議員にできないことと今月の参加者の数え方は #158 で扱う。この設計書は、その中身を実装の形にする。

## 決めたこと

### 1. 表

マイグレーションは表を2つ足すだけ（`drizzle/0026_user_verifications.sql`。既存の列と行は変えない。`drizzle-kit generate` の出力が `CREATE TABLE` と `CREATE INDEX` だけであることを確かめる）。

仕様書の表の説明では `users` が認証の種類と期限を持つが、別の表にする。Better Auth が持つ `user` 表を変えずに済み、付与・延長・取り消しの記録も残せるため。Better Auth の `verification` 表（メールの確認用）とは別物なので、名前を `user_verifications` にする。

- **`user_verifications`**：利用者ごとに1行（`user_id` が主キー、`user.id` への外部キー。削除の扱いは既定のまま。アカウントの削除はまだなく、作るときに決める）。いまの認証か、最後の認証を持つ
  - `kind`：`'legislator'`（議員）／`'expert'`（有識者）。CHECK 制約を付ける
  - `display_name`：表示する名前（議員は氏名、有識者は実名か肩書）
  - `field`：専門分野。有識者だけ。**議員は NULL**（空文字を入れない）。CHECK 制約 `(kind = 'expert') = (field IS NOT NULL)`
  - `granted_at`・`expires_at`・`revoked_at`（NULL でなければ取り消し済み）・`updated_at`（ミリ秒）
  - `op`：最後にこの行を書いた操作の印（要求ごとに `crypto.randomUUID()`）。記録をこの印から作る（3 の書き込み）
- **`user_verification_logs`**：付与・延長・取り消しの記録。公開する
  - `id`、`user_id`、`action`（`'grant'`／`'renew'`／`'revoke'`。CHECK 制約）、`kind`・`display_name`・`field`（その時点の写し。あとで取り消しても記録の名前は変わらない）、`actor_user_id`（運営。画面には出さない）、`created_at`
  - 索引は `created_at`（公開の一覧を新しい順に読む）

### 2. 有効かどうか

- **有効**とは `revoked_at IS NULL AND expires_at > now`。`now` は要求の時刻（`nowOf(event)`。画面のテストは `x-test-now`）
- 期限切れは、読むときの時刻で判定する（Cron で行を書きかえない）。期限切れを記録に出さないのはこのため（基準4）
- **期限**（ルール。`src/lib/domain/verification.ts` の `verificationExpiry(ms)`）：操作した日（日本時間）の**1年後の同じ日付の終わりまで有効**。`expires_at` はその翌日の 0時（日本時間）。2036年4月3日に付けると 2037年4月4日 0時に切れ、画面には「2037年4月3日まで」と出す（1年より短くならない）。2月29日に付けたら、翌年の2月28日まで（3月1日 0時に切れる）
- 延長は「延ばした日から1年」なので、同じ式に延ばした時刻を入れる。付けた日と同じ日に延ばしても期限は変わらない
- 画面の「〜まで」の日付は `expires_at - 1` の日本時間の日付（`tokyoDate` と `jaDate` を組み合わせる。`ja.ts` に `jaDateOfMs` を足す）

### 3. 運営の画面の操作（基準1・2・3）

- 欄は `/kanri` に足す（`section`、見出し「議員・有識者の認証」）。**運営（`user.role = 'operator'`）にだけ**出す。運営協力者、委員長、理事は `/kanri` を開けても、この欄は出ない。一般の利用者には `/kanri` が 404 のまま
- 操作は3つのフォームの action（`verifyGrant`・`verifyRenew`・`verifyRevoke`）。どれも最初に役職を確かめ、運営でなければ **404**（`/kanri` の今の扱いと同じく、欄があることを漏らさない）。役職から付けられるかを決めるのはルールの関数 `canVerify(role)`（`'operator'` だけ真。`'moderator'`・`'chair'`・`'director'`・役職なしは偽）
- `load` も、運営でなければ一覧を返さない（委員長・理事が `__data.json` から読めないように）
- **付ける**：入力は 表示名（`user.name` と完全に一致）、種類（`fieldset`「種類」のラジオ「議員」「有識者」）、表示する名前（ラベル「表示する名前（議員は氏名、有識者は実名か肩書）」）、専門分野（有識者だけ）
  - 入力の確かめ（ルール。`parseVerification`）：種類は「議員」「有識者」のどちらか（ほかの値は断る。DB の CHECK で 500 にしない）。表示する名前は1〜40字。専門分野は有識者なら1〜40字、議員なら入力を見ずに NULL。改行と制御文字は使えない（課題の題名と同じ `checkText`）
  - 断るとき（理由を `role="alert"` で出す）：その表示名の利用者がいない、運営・運営協力者のアカウント（`user.role` が NULL でない）、いま有効な認証がある
  - 書き込みは1つの `db.batch`：`user_verifications` への insert … on conflict(user_id) do update（**有効な認証がないときだけ**更新する条件を付ける。`op` に今回の印を書く）と、`user_verification_logs` への insert … select（`op` が今回の印の行があるときだけ）。印は要求ごとに違うので、2人の運営が同じミリ秒に付けても、書けなかったほうの記録はできない。有効な認証と記録は1つずつ
  - 付けたあとで運営・運営協力者になった人の認証は、自動では外さない（役職は DB で直接付けるもので、画面がない。そのときは運営が取り消す）
  - 取り消しのあとや期限切れのあとは、同じ行を上書きして付け直せる（`revoked_at` を NULL に戻す）
- **一覧**：いま有効な認証を、期限の近い順に並べる（種類・表示する名前・専門分野・「〜まで」）。表示名（`user.name`）も添える（運営が誰か分かるように）
- **1年延ばす**・**取り消す**：対象は `user_id`（hidden。運営だけが見る欄なので出してよい。公開の画面には渡さない）。有効な認証にだけ効く（条件付きの update で `op` に今回の印を書き、記録はその印の行から作る。1つの batch）。効かなかったら「この認証はもう有効ではありません」
- **文言**：見出し「議員・有識者の認証」、ラベル「表示名」「種類」「議員」「有識者」「表示する名前（議員は氏名、有識者は実名か肩書）」「専門分野（有識者だけ）」、ボタン「認証を付ける」「1年延ばす」「取り消す」、一覧の期限「2037年4月3日まで」

### 4. 運営の記録（基準4）

- 記録を書くのは付与・延長・取り消しの3つだけ。期限切れでは記録を書かない（日付から誰でもわかるため）
- `/unei` に「認証の記録」の欄を足す（ページの送りは今の欄と同じ形で、引数は `ninsho`）
- 1行は「議員の認証を付けた・試験 太郎・2036年4月3日」の形。操作は「付けた」「1年延ばした」「取り消した」、種類は「議員」「有識者」。有識者は名前のあとに「（専門分野）」を付ける。日付は日本時間
- 運営のだれが操作したか（`actor_user_id`）は出さない（今の運営の記録と同じ）

### 5. バッジと名前（基準5・6）

- 有効な認証のある人は、**表示名の代わりに表示する名前**を出し、横にバッジを付ける
  - 議員：盾の印（`svg`、`aria-hidden`）と「認証済み議員」
  - 有識者：「有識者」と「（専門分野）」
  - 文字で区別する（色だけにしない）。色と大きさは Tokens の CSS 変数だけ
- 部品は `src/lib/components/PersonName.svelte`（`{ person }` を受ける。`person` は `{ name: 表示名, verified: { kind, name: 表示する名前, field } | null }`。`verified` があれば表示する名前とバッジ、なければ表示名）
- 今は名前を文字列で返して文言の関数で `、` でつないでいる（`billView.author`、`coDrafters`、`ja.ts` の `coDrafters(names)` など）。これを `person` の配列で返し、画面で `PersonName` を並べる形に変える。文言の関数は前置き（「共同起草者」など）だけにする
- サーバーは、名前を返す関数で、有効な認証を左結合して `verified: { kind, name, field } | null` を返す。**`user_id` は画面に渡さない**（今と同じ）。結合の条件は1か所の関数（`activeVerification(now)`）にまとめる
- 出す場所：法案の提出者（`billView`）、共同提出者（`cosponsorsOf`・`cosponsorPanel`）、共同起草者（`coDrafters`）、撤回に同意した人（`withdrawStateOf`）、委員長の候補（`electionPage`）、委員長・理事（`chairPanelOf`）
- **質疑・答弁・補足のカード**（基準6）：今は書いた人の名前を出していない。投稿の行に、書いた人の**有効な認証があるときだけ** `author: { kind, name, field }` を付け、カードの上に名前とバッジを出す。認証のない人の投稿は今のまま（`author: null`、名前を出さない）
- 認証が切れたり取り消されたりすると、次に読んだときから名前とバッジは出なくなる（過去の投稿も、読むときの状態で出す）
- 運営の画面の通報の欄は、今のまま（名前を出さない）

### 6. 文言

`src/lib/copy/ja.ts` に `verification`（欄の見出し、ラベル、断る理由、一覧、ボタン、記録の行、バッジ）を足す。画面に実装用語を出さない。

## テスト

- **ルールのテスト**（`src/lib/domain/verification.test.ts`）：期限の計算（付けた日・延ばした日の1年後の同じ日付の終わりまで、日本時間の日付で切れる、2月29日）、`canVerify` が運営だけ真（基準2の委員長・理事はここで確かめる。画面のテストで委員長・理事を作るには委員長選挙を通す必要があり重いため）
- **DB のテスト**（`src/lib/db/verifications.test.ts`）：同じ時刻に2回付けても、有効な認証と記録が1つずつ（Blocker の再現）
- **画面のテスト**（`e2e/ninsho.spec.ts`。基準ごとに1本）
  - 基準1：運営が付ける。ない表示名・運営協力者のアカウント・認証のある人には理由を出して付けない
  - 基準2：運営協力者には欄が出ず、運営協力者と一般の利用者の POST は 404
  - 基準3：一覧に期限が出る。`x-test-now` を半年進めて延ばすと、期限が延ばした日の1年後になる。取り消すと一覧から消え、付け直せる。1年と1日進めると期限切れで一覧から消える
  - 基準4：運営の記録に、付けた・延ばした・取り消したの3行
  - 基準5：有識者が提出した法案のページに、表示する名前と「有識者（専門分野）」。認証が切れるとバッジが消える
  - 基準6：議員の質疑のカードに名前と「認証済み議員」。一般の人の質疑のカードには名前が出ない
