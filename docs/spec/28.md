# 課題の通報と自動非表示、運営が確認する画面、運営の記録（設計書）

Issue #28。マイグレーションを足し、権限の境界（運営だけの画面）を作るので Careful。仕様の正は [docs/spec.md](../spec.md) の「不正・荒らし対策とモデレーション」と「委員長の選び方」。課題は [docs/spec/25.md](25.md)。

仕様書にない次のことは、2026-11-02〜03 にユーザーと決めた（仕様書のドキュメントへの反映はユーザー側）。

- 別々の3人の通報で自動的に非表示にする。委員長が決まるまでは運営が確認する
- 役職：運営（`operator`）と運営協力者（`moderator`。通報の確認だけを手伝う）を `user.role` に持つ。付けるのは `wrangler d1 execute` の手作業で、画面からは付けない。委員長（委員会ごと）はフェーズ5で委員会と結ぶ別の表に、議員・有識者は役職ではなく本人確認の印として持つ
- 通報の理由は「人への攻撃・差別」「宣伝・荒らし」「同じ課題がほかにある」「その他」。「その他」には200字までの自由記述
- 「同じ課題がほかにある」の通報は、自動非表示の数に入れない（別の課題だと思って書いた人の課題が消えないように。統合の Issue で使う）
- 登録から24時間たっていないアカウントの通報は、自動非表示の数に入れない（使い捨てのアカウントで他人の課題を消せないように）
- 運営が「表示に戻す」とした課題は、そのあと通報が集まっても自動では非表示にしない。非表示の基準は公開する
- 公開の「運営の記録」は `/unei`、運営だけの画面は `/kanri`（権限で守る。URL を隠して守るのではない）
- 書いた本人には、非表示になった課題の本文と理由を出す（「本人に通知する」の、いまの形）
- 異議申し立ての窓口、課題の統合、解決策の通報、ガイドラインのページは別の Issue

## 範囲

- 入れる：課題の通報、自動非表示、非表示の課題の見え方、`/kanri`（通報を受けた課題の一覧、非表示にする、表示に戻す）、`/unei`（非表示の基準と対応の記録）、`user.role`、テスト用のログインの `role`
- 入れない：上の「別の Issue」、役職を画面から付けること、通報者への結果の知らせ、`/watashi` での通知の一覧

## 表

`drizzle/0004_*.sql`（`drizzle-kit generate`）。

| 表 | 列 | 備考 |
| --- | --- | --- |
| `user` | `role` を足す（NULL／`moderator`／`operator`） | CHECK で値を絞る。NULL はふつうの参加者 |
| `issues` | `status` を足す（`visible`／`auto_hidden`／`hidden`／`restored`、既定 `visible`） | `restored` は運営が表示に戻した課題（表示されるが、自動では非表示にしない） |
| `reports` | `id`、`issue_id`、`user_id`、`reason`（`attack`／`spam`／`duplicate`／`other`／`none`）、`note`（NULL 可）、`counted`（自動非表示の数に入れるか）、`created_at` | 一意（`issue_id`, `user_id`）。索引（`user_id`, `created_at`） |
| `moderation_logs` | `id`、`issue_id`、`action`（`auto_hide`／`hide`／`restore`）、`actor`（`auto`／`moderator`／`operator`）、`actor_user_id`（NULL 可。公開しない）、`reason`（NULL 可）、`note`（NULL 可）、`created_at` | 索引（`created_at`） |

- `reason` の `none` は理由を選ばずに通報したとき（締めのテストは理由を選ばずに「通報する」を押す。理由は任意）
- `counted` は通報したときに決めて残す：理由が `duplicate` でなく、通報した人の登録から24時間たっているとき 1
- `actor_user_id` は内部で誰が対応したかを追うため。公開の記録には役職（運営／運営協力者／自動）だけを出す
- 外部キーの `ON DELETE` は既定（退会は「あとで決めること」）

## 決めたこと

1. **通報の画面**：課題のページの下に「この課題を通報する」（ボタン）。押すと、その場に通報の欄を開く：理由（ラジオ。任意）、「その他」の説明（`textarea`、200字まで。理由が「その他」のときだけ出す）、非表示の基準の要約と `/unei` へのリンク、「通報する」。JS がなければ欄を最初から開いておく
   - 出さないとき：ログインしていない（ボタンを押すと `/login?next=/kadai/[id]` へ）、自分の課題、すでに通報した（代わりに「この課題は通報済みです」）、課題が非表示
   - 送ると「通報を受け付けました」。もう一度開くと「この課題は通報済みです」
2. **通報の受け付け**（`?/report` の POST）：ログイン → 国 → 締め出し → 入力 → レート制限 → 保存（docs/spec/25.md 決めたこと12と同じ順。`writeGuard` を使う。Turnstile はかけない）
   - 入力（信頼の境界）：`reason` は `attack`／`spam`／`duplicate`／`other` のどれかか、空（`none` として保存）。`note` は `reason` が `other` のときだけ受け取り、前後の空白を除いて0〜200字（コードポイント）、制御文字なし（改行は可。docs/spec/25.md 決めたこと2と同じ判定）。`other` 以外で `note` が来たら捨てる。形が違えば 400
   - 自分の課題、非表示の課題は 400
   - 同じ人の2回目は、何もせず「この課題は通報済みです」を返す（一意の索引。数えない）
   - レート制限：1アカウント24時間に10件まで（`reports` から数える）。超えたら 429 と「通報は24時間に10件までできます。しばらくしてからお試しください」。違反に数える（docs/spec/25.md 決めたこと11の締め出し）
3. **自動非表示**：通報を保存したあと、その課題の `counted = 1` の通報が3件以上で、`status` が `visible` なら、`auto_hidden` にし、`moderation_logs` に `auto_hide`（`actor = auto`、`reason` は通報の理由の多い順の要約ではなく固定の「通報が3件」）を書く。`restored`・`hidden` の課題は変えない
4. **非表示の課題の見え方**（`auto_hidden` と `hidden`）
   - 一覧（`/kadai`）から外す
   - ページ：書いた本人以外には、題名も本文も出さず、`auto_hidden` なら「この課題は通報により非表示になっています」、`hidden` なら「この課題は運営の確認により非表示になっています（理由：{理由}）」と `/unei` へのリンクだけを出す。状態コードは 200。`<title>` も「非表示の課題」にする
   - 書いた本人には、本文と一緒に上の文言を出す
   - 「わかる」と通報は受け付けない（ボタンを出さない。POST は 403 と「非表示の課題には操作できません」）
5. **運営の画面 `/kanri`**：`role` が `operator` か `moderator` の人だけ。それ以外（ログインしていない人を含む）には 404（ログインへは誘導しない）。`noindex`
   - 通報を受けた課題を並べる：`auto_hidden` が先、その中は最後の通報が新しい順。各課題に、番号（課題のページへのリンク）、題名、状態、通報の数（数に入るもの／入らないもの）、理由ごとの数、「その他」の説明（新しい順。通報者は出さない）、`restored` なら表示に戻したあとの通報の数
   - 「非表示にする」：理由（「人への攻撃・差別」「宣伝・荒らし」「その他」のどれか）とメモ（1〜200字、必須。公開するので個人情報を書かないよう画面に注意書き）。`status` を `hidden` にし、`moderation_logs` に `hide`
   - 「表示に戻す」：メモ（1〜200字、必須）。`status` を `restored` にし、`moderation_logs` に `restore`
   - どちらも `actor` は対応した人の `role`、`actor_user_id` はその人
   - 運営と運営協力者は、ここでは同じことができる（違いは記録に出る役職だけ）。運営だけができることは、役職を画面から付ける機能を作るときに足す
   - 入力（信頼の境界）：`issue`（課題の番号。docs/spec/25.md の `parseIssueId`）、`reason`、`note`。形が違えば 400
   - 書き込みには国の確かめをかける（`writeGuard` の国の部分）。締め出しとレート制限はかけない
6. **運営の記録 `/unei`**：だれでも見られる
   - 上に非表示の基準（次の5つ）を出す
     - 登録から24時間たった別々の3人から通報があると、運営が確認するまで一時的に見えなくなります
     - 「同じ課題がほかにある」の通報では見えなくなりません
     - 運営が確認して問題がないとした課題は、そのあと通報があっても自動では見えなくなりません
     - 運営が見えなくするのは、人への攻撃・差別、宣伝・荒らしなど、課題として扱えないものだけです。理由はこの記録に残します
     - 通報した人や書いた人の名前は、ここには出しません
   - 下に `moderation_logs` を新しい順（`id` の大きい順）に50件ごと（`?page=2`。形の違う `page` と、2ページ目以降で記録がないときは 404。docs/spec/25.md 決めたこと4と同じ）。各行に、日時（日本時間）、課題の番号（ページへのリンク）、何をしたか（「自動で非表示」「非表示」「表示に戻した」）、だれが（「自動」「運営」「運営協力者」）、理由、メモ
   - 記録がなければ「まだ記録はありません」
7. **テスト用のログイン**：`/test-login` に `role`（`moderator`／`operator`。省略はなし）を足す。新しく作る利用者にだけ付ける。形が違えば 400（信頼の境界）
8. **言葉**：画面の文言は `src/lib/copy/ja.ts` の `report`（通報）、`kanri`、`unei` に置く。実装用語（`auto_hidden` など）は出さない
9. **締めのテストの変更**：`e2e/phase2.spec.ts` の通報する人（B・C・D）は登録から24時間たっていないので、決めたことの「新しいアカウントの通報は数えない」で、3人目でも非表示にならない。テスト用のログインに `days=2` を付ける形に直す（ユーザーの判断に合わせた変更）

## テストの方針

- 通報の入力の判定、自動非表示にするかの判定は、純粋な関数を Vitest で確かめる
- 自動非表示とレート制限は、docs/spec/25.md と同じく node:sqlite に D1 と同じ SQL を流して確かめる（`counted` の決め方、`restored` で止まること、2回目を数えないこと）
- 画面は Playwright の2幅で、通報の流れ、非表示の見え方（本人とそれ以外）、`/kanri` の権限と操作、`/unei` を確かめる
- 信頼の境界の入力（通報の `reason`・`note`、`/kanri` の `issue`・`reason`・`note`、`/unei` の `page`、`/test-login` の `role`）は、形の違う値を送って断られることを確かめる

## あとで決めること

- 役職を画面から付け外しする機能と、運営だけができること
- 通報者への結果の知らせ、`/watashi` での通知の一覧
- 異議申し立ての窓口（公開前の安全策の Issue）、ガイドラインのページ
- 「同じ課題がほかにある」の通報からの統合（似た課題と統合の Issue）
- 委員長が決まったあとの、委員長と運営の分担（フェーズ5）
