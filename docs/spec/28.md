# 課題の通報と自動非表示、運営が確認する画面、運営の記録（設計書）

Issue #28。マイグレーションを足し、権限の境界（運営だけの画面）を作るので Careful。仕様の正は [docs/spec.md](../spec.md) の「不正・荒らし対策とモデレーション」と「委員長の選び方」。課題は [docs/spec/25.md](25.md)。

仕様書にない次のことは、2026-11-02〜03 にユーザーと決めた（仕様書のドキュメントへの反映はユーザー側）。

- 別々の3人の通報で自動的に非表示にする。委員長が決まるまでは運営が確認する
- 役職：運営（`operator`）と運営協力者（`moderator`。通報の確認だけを手伝う）を `user.role` に持つ。付けるのは `wrangler d1 execute` の手作業で、画面からは付けない。委員長（委員会ごと）はフェーズ5で委員会と結ぶ別の表に、議員・有識者は役職ではなく本人確認の印として持つ
- 通報の理由は「人への攻撃・差別」「宣伝・荒らし」「同じ課題がほかにある」「その他」。「その他」には200字までの自由記述
- 「同じ課題がほかにある」の通報は、自動非表示の数に入れない（別の課題だと思って書いた人の課題が消えないように。統合の Issue で使う）
- 登録から24時間たっていないアカウントの通報は、自動非表示の数に入れない（使い捨てのアカウントで他人の課題を消せないように）
- 運営が「表示に戻す」とした課題は、そのあと通報が集まっても自動では非表示にしない。非表示の基準は公開する
- 公開の「運営の記録」は `/unei`、運営だけの画面は `/kanri`（権限で守る。URL を隠して守るのではない）
- 書いた本人には、非表示になった課題の本文と理由を出す（「本人に通知する」の、いまの形）
- 異議申し立ての窓口、課題の統合、解決策の通報、ガイドラインのページは別の Issue

## 範囲

- 入れる：課題の通報、自動非表示、非表示の課題の見え方、`/kanri`（通報を受けた課題の一覧、非表示にする、表示に戻す）、`/unei`（非表示の基準と対応の記録）、`user.role`、テスト用のログインの `role`
- 入れない：上の「別の Issue」、役職を画面から付けること、通報者への結果の知らせ、`/watashi` での通知の一覧

## 表

`drizzle/0004_*.sql`（`drizzle-kit generate`）。すでにある `user`・`issues` には `ALTER TABLE … ADD COLUMN` だけで足す。表全体の CHECK を足すと drizzle-kit が表を作り直す SQL を出し、D1 では `PRAGMA foreign_keys=OFF` が効かないので、`ON DELETE CASCADE` の行（`session`・`account`・`bans`）が消えるおそれがある。そのため足す列には CHECK を付けず、値はアプリで絞る（Drizzle の `enum` は型だけ）。生成された SQL に表の作り直しがないことを確かめてからコミットする。

| 表 | 列 | 備考 |
| --- | --- | --- |
| `user` | `role` を足す（NULL／`moderator`／`operator`） | NULL はふつうの参加者。Better Auth の `additionalFields` には登録しない（登録すると既定で参加者が `update-user` から書けてしまう）。D1 から別に読む |
| `issues` | `status` を足す（`visible`／`auto_hidden`／`hidden`／`restored`、既定 `visible`） | `restored` は運営が表示に戻した課題（表示されるが、自動では非表示にしない） |
| `reports` | `id`、`issue_id`、`user_id`、`reason`（`attack`／`spam`／`duplicate`／`other`／`none`）、`note`（NULL 可）、`counted`（自動非表示の数に入れるか）、`created_at` | 一意（`issue_id`, `user_id`）。索引（`user_id`, `created_at`） |
| `moderation_logs` | `id`、`issue_id`、`action`（`auto_hide`／`hide`／`restore`）、`actor`（`auto`／`moderator`／`operator`）、`actor_user_id`（NULL 可。公開しない）、`reason`（`reports`（自動）／`attack`／`spam`／`other`。`restore` は NULL）、`note`（NULL 可）、`created_at` | 索引（`issue_id`）。`reason` は決まった値で持ち、画面の文言は `ja.ts` の対応表で出す（基準の数を変えても過去の記録が食い違わないように） |

- `reason` の `none` は理由を選ばずに通報したとき（締めのテストは理由を選ばずに「通報する」を押す。理由は任意）
- `counted` は通報したときに決めて残す：理由が `duplicate` でなく、通報した人の登録から24時間たっているとき 1
- `actor_user_id` は内部で誰が対応したかを追うため。公開の記録には役職（運営／運営協力者／自動）だけを出す
- 外部キーの `ON DELETE` は既定（退会は「あとで決めること」）

## 決めたこと

1. **通報の画面**：課題のページの下に「この課題を通報する」（ボタン）。押すと、その場に通報の欄を開く：理由（ラジオ。任意）、「その他」の説明（`textarea`、200字まで。理由が「その他」のときだけ出す）、非表示の基準の要約と `/unei` へのリンク、「通報する」。JS がなければ欄を最初から開いておく
   - ログインしていない人には、ボタンは出すが欄は開かず、押すと `/login?next=/kadai/[id]` へ送る
   - ボタンを出さないとき：自分の課題、すでに通報した（代わりに「この課題は通報済みです」）、課題が非表示
   - 送ると「通報を受け付けました」。もう一度開くと「この課題は通報済みです」
2. **通報の受け付け**（`?/report` の POST）：課題の番号と課題があるか（なければ 404。docs/spec/25.md の「わかる」と同じくログインより先）→ ログイン → 国 → 締め出し → 入力 → 課題の状態 → 2回目か → レート制限 → 保存（docs/spec/25.md 決めたこと12の順に、課題の状態と2回目かを足す。`writeGuard` を使う。Turnstile はかけない）
   - 入力（信頼の境界）：`reason` は `attack`／`spam`／`duplicate`／`other` のどれかか、空（`none` として保存）。`note` は `reason` が `other` のときだけ受け取り、前後の空白を除いて0〜200字（コードポイント）、制御文字なし（改行は可。docs/spec/25.md 決めたこと2と同じ判定）。`other` 以外で `note` が来たら捨てる。形が違えば 400
   - 入力：自分の課題は 400（画面にボタンを出さないので、届くのは形の違う要求だけ）
   - 課題の状態：非表示（`auto_hidden`・`hidden`）の課題は 403 と「非表示の課題には操作できません」（決めたこと4）
   - 2回目か：同じ人の2回目は、何もせず「この課題は通報済みです」を返す（状態コード 200。数えない。レート制限より先に確かめるので、上限に達した人の2回目も 429 にならない）。同時に送られたときは一意の索引で2行目を入れない（`ON CONFLICT DO NOTHING`）
   - レート制限：1アカウント24時間に10件まで（`reports` から数える）。超えたら 429 と「通報は24時間に10件までできます。しばらくしてからお試しください」。違反に数える（docs/spec/25.md 決めたこと11の締め出し）
3. **自動非表示**：通報を保存したあと、`UPDATE issues SET status = 'auto_hidden', status_actor = 'auto', status_reason = 'reports', … WHERE id = ? AND status = 'visible' AND (その課題の counted = 1 の通報の数) >= 3` を1文で行う。`visible` の課題しか変えないので、同時に通報が来ても、運営の「表示に戻す」と重なっても、状態は1回しか変わらない。`restored`・`hidden` の課題は変えない
   - **記録の書き方**：`issues` に `status_actor`・`status_actor_user_id`・`status_reason`・`status_note`・`status_changed_at` を足し、状態を変える `UPDATE` がこれらも一緒に入れる。`issues.status` が変わったら、SQLite のトリガー（`issues_status_log`。マイグレーションに手で書く）が同じ文の中で `moderation_logs` に1行書く。状態だけ変わって記録が抜けることも、同時の操作で記録が重なることもない
   - 当初は D1 の `batch` と `changes()` で書く予定だったが、D1 と node:sqlite の両方で使う Drizzle の共通の型（`BaseSQLiteDatabase`）に `batch` がないため、トリガーにした（実装のときに変更。トリガーが wrangler の手元の D1 にも作られることを確かめた）
4. **非表示の課題の見え方**（`auto_hidden` と `hidden`）
   - 一覧（`/kadai`）から外す
   - ページ：書いた本人以外には、題名も本文も出さず、見出し（`h1`）「非表示の課題」と、`auto_hidden` なら「この課題は通報により非表示になっています」、`hidden` なら「この課題は運営の確認により非表示になっています（理由：{理由}）」（理由は `issues.status_reason`。いちばん新しい対応の理由と同じ。対応表で出す）と、`/unei` へのリンク「くわしくは運営の記録へ」だけを出す。状態コードは 200。`<title>` も「非表示の課題」にする
   - 非表示の課題のページには、書いた本人に見せるときも `<meta name="robots" content="noindex">` を付ける。題名や本文を入れた `<meta>`（`description` など）は出さない（いまは出していない。共有用の画像を作るときも同じ）
   - 書いた本人と、`role` が `operator`・`moderator` の人には、本文と一緒に上の文言を出す（運営は中身を読んで判断する）。運営・運営協力者には、どの状態の課題でも、ページに「運営として対応する」（`/kanri?issue=[id]`）を出す
   - 「わかる」と通報は受け付けない（ボタンを出さない。POST は 403 と「非表示の課題には操作できません」）
5. **運営の画面 `/kanri`**：`role` が `operator` か `moderator` の人だけ。それ以外（ログインしていない人を含む）には 404（ログインへは誘導しない）。ページの表示（load）だけでなく、フォームの操作（`?/hide`・`?/restore`）でも同じく確かめ、権限のない人には 404。`noindex`
   - フォームの操作で確かめる順：役職（404。ほかの確かめより先にして、権限のない人に `/kanri` があることを漏らさない）→ 国（403）→ 入力（400）→ 自分の課題（403）→ 状態（400）
   - `?issue=[id]` を付けると、その課題（通報されていなくても）を一覧の上に出す。運営が見つけた問題のある課題も扱えるように。`issue` の形が違う・課題がないときは 404
   - 通報を受けた課題を並べる：`auto_hidden` が先、その中は最後の通報が新しい順。各課題に、番号（課題のページへのリンク）、題名、状態、通報の数（数に入るもの／入らないもの）、理由ごとの数、「その他」の説明（新しい順。通報者は出さない）、`restored` なら表示に戻したあとの通報の数
   - 「非表示にする」：理由（「人への攻撃・差別」「宣伝・荒らし」「その他」のどれか）とメモ（前後の空白を除いて1〜200字（コードポイント）、制御文字なし、改行は可。docs/spec/25.md 決めたこと2と同じ判定。公開するので個人情報を書かないよう画面に注意書き）。`status` を `hidden` にし、`moderation_logs` に `hide`
   - 「表示に戻す」：メモ（「非表示にする」と同じ判定）。`status` を `restored` にし、`moderation_logs` に `restore`
   - どちらも `actor` は対応した人の `role`、`actor_user_id` はその人
   - 運営と運営協力者は、ここでは同じことができる（違いは記録に出る役職だけ）。運営だけができることは、役職を画面から付ける機能を作るときに足す
   - 自分が書いた課題には、どちらの操作もできない（403 と「自分の課題には対応できません」。画面にもボタンを出さない。通報の自分の課題が 400 なのと違い、ここは権限の問題なので 403）。運営の恣意性を疑われないように（仕様「モデレーションの方針」）
   - 状態ごとの扱い（`issue` は通報されていない課題でもよい。運営が見つけた問題のある課題も扱えるように）

     | いまの状態 | 非表示にする | 表示に戻す |
     | --- | --- | --- |
     | `visible` | `hidden` にする | 400（「表示されています」） |
     | `auto_hidden` | `hidden` にする | `restored` にする |
     | `hidden` | 400（「すでに非表示です」） | `restored` にする |
     | `restored` | `hidden` にする | 400（「表示されています」） |

     400 のときは記録を書かない。状態の変更は `UPDATE … WHERE status IN (…) RETURNING` の1文で行い、記録は決めたこと3と同じくトリガーが書く。`UPDATE` の行が返らなければ 400
   - フォームの送り先は `?issue=[id]&/hide` のように課題の番号を入れる（JS がなくても、送ったあとに同じ課題を開いたままにする）
   - 一覧は最後の通報が新しい順に100件まで（件数が増えたらページを分ける。あとで決めること）
   - 入力（信頼の境界）：`issue`（課題の番号。docs/spec/25.md の `parseIssueId`）、`reason`、`note`。形が違えば 400
   - 書き込みには国の確かめをかける（`writeGuard` の国の部分）。締め出しとレート制限はかけない
6. **運営の記録 `/unei`**：だれでも見られる
   - 上に非表示の基準（次の5つ）を出す
     - 登録から24時間たった別々の3人から通報があると、運営が確認するまで一時的に見えなくなります
     - 「同じ課題がほかにある」の通報では見えなくなりません
     - 運営が確認して問題がないとした課題は、そのあと通報があっても自動では見えなくなりません
     - 運営が見えなくするのは、人への攻撃・差別、宣伝・荒らしなど、課題として扱えないものだけです。理由はこの記録に残します
     - 通報した人や書いた人の名前は、ここには出しません
   - 下に `moderation_logs` を新しい順（`id` の大きい順）に50件ごと（`?page=2`。形の違う `page` と、2ページ目以降で記録がないときは 404。docs/spec/25.md 決めたこと4と同じ）。各行に、日時（日本時間）、課題の番号（ページへのリンク）、何をしたか（「自動で非表示」「非表示」「表示に戻した」）、だれが（「自動」「運営」「運営協力者」）、理由、メモ
   - 記録がなければ「まだ記録はありません」
7. **テスト用のログイン**：`/test-login` に `role`（`moderator`／`operator`。省略すると役職なし）を足す。新しく作る利用者にだけ付ける。形が違えば 400（信頼の境界）
8. **言葉**：画面の文言は `src/lib/copy/ja.ts` の `report`（通報）、`kanri`、`unei` に置く。実装用語（`auto_hidden` など）は出さない。締め出しの文言（`guard.banned`）は「課題の投稿・『わかる』・通報ができません」に直す
9. **締めのテストの変更**：`e2e/phase2.spec.ts` の通報する人（B・C・D）は登録から24時間たっていないので、決めたことの「新しいアカウントの通報は数えない」で、3人目でも非表示にならない。テスト用のログインに `days=2` を付ける形に直す（ユーザーの判断に合わせた変更）

## テストの方針

- 通報の入力の判定、自動非表示にするかの判定は、純粋な関数を Vitest で確かめる
- 自動非表示とレート制限（`counted` の決め方、`restored` で止まること、2回目を数えないこと、24時間に10件）は、画面のテストで確かめる（テスト用のログインの `days` で登録した日を変えられ、24時間を待つ必要がないため。記録を書くトリガーも wrangler の手元の D1 で通る）
- 画面は Playwright の2幅で、通報の流れ、非表示の見え方（本人とそれ以外）、`/kanri` の権限（表示と POST の両方）と操作、`/unei` を確かめる
- 信頼の境界の入力（通報の `reason`・`note`、`/kanri` の `issue`・`reason`・`note`、`/unei` の `page`、`/test-login` の `role`）は、形の違う値を送って断られることを確かめる

## あとで決めること

- 役職を画面から付け外しする機能と、運営だけができること
- 通報者への結果の知らせ、`/watashi` での通知の一覧
- 異議申し立ての窓口（公開前の安全策の Issue）、ガイドラインのページ
- 「同じ課題がほかにある」の通報からの統合（似た課題と統合の Issue）
- 委員長が決まったあとの、委員長と運営の分担（フェーズ5）
- 同じ回線からの通報の集中への対処（24時間たったアカウントを3つ持つ1人は、運営が確認するまで課題を一時的に隠せる）
- `/kanri` の一覧のページ分け
