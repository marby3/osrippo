# 賛同と発議要件（設計書）

仕様書にない次のことは、ユーザーと決めた（仕様書のドキュメントへの反映はユーザー側）。

Issue #41 の決めたこと（2026-11-04）

- 賛同者の数が発議要件に届いたら、提出者が「発議する」を押す。提出者自身は賛同の数に入れない（決めたこと2）
- 発議要件の母数は、一つ前の会期に何かをした人の数を会期の始めに固定する。前の会期に誰もいなければ最低人数の3人（決めたこと3）
- 賛同者は、発議の前なら賛同を取り消せる（決めたこと4）
- 下書きを作る・賛同する・発議するのは、登録から7日たったアカウントだけ（決めたこと6）

この Issue で決めたこと（2026-11-04）

- 5% の端数は切り上げる
- 提出者が下書きを保存すると、それまでの賛同は数えなくなり、集め直す。直す画面で先に知らせる
- 賛同は会期をまたいで持ち越す。発議要件は「発議する」を押した会期の人数と比べる
- 賛同の上限は「わかる」とは別に数える。1アカウント24時間に30回、5分に10回（付けるのも取り消すのも1回）。同じ法案に同じ回線から3アカウントまで。アカウントの上限を超えたら違反に数え、回線の上限は数えない

## 目的

賛同を集めて発議できるようにする。発議した法案の状態の進み方（付託・質疑・採決・廃案）と「終わった」のタブは #50。

## 範囲

- 入れる：表（賛同、会期ごとの今月の参加者）、`bills.proposed_at`、一覧の並びの索引（#48 のレビューで持ち越し）、賛同する・取り消す、発議する、発議要件の計算と固定、法案のページと一覧の賛同の数
- 入れない：状態の進み方（#50）、共同提出者と撤回（v0.4）、賛同者の名前を出すこと、発議の通知

## 表

`drizzle/0010_*.sql`（`drizzle-kit generate`）。どれも追加だけで、既存の表を作り直さない。generate のあとに SQL を読み、`bills`（`ADD COLUMN`）と `CREATE INDEX` のほかに既存の表に触っていないことを確かめる。

| 表 | 列 | 備考 |
| --- | --- | --- |
| `bill_supports` | `bill_id`（`bills` への外部キー）、`rev`、`user_id`（`user` への外部キー）、`created_at` | 主キー（`bill_id`, `rev`, `user_id`）。読むのは `bills.rev` と同じ `rev` の行だけ |
| `session_participants` | `committee_id`（`committees` への外部キー）、`session_key`（`Session.key`）、`active_count`、`fixed_at` | 主キー（`committee_id`, `session_key`）。その会期の発議要件の母数 |
| `bills`（列を足す） | `proposed_at`（整数、NULL 可） | 発議した時刻。#50 が、締切の前か後かを求めるのに使う |
| `bills`（索引を足す） | (`status`, `created_at`) | 審議中のタブの並び |

## 決めたこと

1. **賛同は版に結び付ける**：賛同の行は、賛同したときの `bills.rev` を持つ。数えるのは `bills.rev` と同じ `rev` の行だけ。保存すると `rev` が変わるので、行を消さなくても賛同は数えなくなる
   - 行を消す形にすると、`saveDraft` の最後の `UPDATE` と消す文の間に、新しい版へ付けた賛同を消してしまう。D1 と node:sqlite の両方で使う型に `batch` がないので、版で分ける（docs/spec/45.md 決めたこと1と同じ考え）
   - 賛同のフォームは、画面を開いたときの `rev` を送る。行を足す文は `bills.rev` がその値のときだけ入れる。開いたあとで直された法案には賛同できず、読み直すよう案内する（見ていない中身に賛同させない）
2. **発議要件の計算**（`proposalRequirement`。純粋な関数。`src/lib/domain/bills.ts`）：`max(3, ceil(今月の参加者 × 5 / 100))`。小数の誤差を避けるため、整数で `Math.ceil(n * 5 / 100)` と書く（`60 * 0.05` は 3 を超えて 4 になる）
   - 境界：60人で3人、61人で4人、100人で5人、101人で6人
3. **今月の参加者の固定**（`sessionParticipants(db, committeeId, session, previous, now)`）：その会期の行があれば読む。なければ、一つ前の会期（`sessionAt(session.startsAt - 1, minutes)`）の `actions` から数えて `INSERT … ON CONFLICT DO NOTHING` で入れ、入っている行を読み直す
   - 固定する時刻は、その会期で最初に読まれたとき。cron を使わない。前の会期は終わっているので、いつ読んでも同じ数になる（「最後に処理した時刻」に頼らない。Issue #41 レビュー）
   - 同時に読まれても、先に入った行で全員そろう
   - 数える `kind`：`issue_post`・`support_add`・`solution_post`・`reaction_add`・`bill_draft`・`bill_save`・`bill_support_add`・`bill_propose`（決めたこと3の「課題・わかる・解決策・解決策への反応・法案の起草・賛同」。起草には作る・保存する・発議するを入れる）。取り消しの `kind`、通報、`violation`、運営の操作は数えない
   - 数えるのは `user_id` の重なりを除いた人数（`COUNT(DISTINCT user_id)`）。委員会が1つのあいだはサイト全体
   - `created_at` だけの索引はないので、数えるときは `actions` を読む。1つの会期に1回なので、索引は足さない
4. **賛同する・取り消す**（`setBillSupport(db, actor, billId, expectedRev, op, now)`）
   - 確かめる順：ログイン → 日本から → 締め出し（`writeGuard`）→ 登録から7日（付けるときだけ）→ 法案の形（ある、下書き、提出者でない）→ 上限 → 書く
   - Turnstile は使わない（「わかる」と同じ）
   - いまと同じ状態への操作は何もせず、数えない（`setSupport` と同じ）
   - 行を足す文：`INSERT … SELECT … WHERE EXISTS (bills が draft で rev = expectedRev)`。発議や保存と同時でも、発議したあとの法案や古い版には入らない
   - 取り消す文：いまの `rev` の自分の行を消す。下書きのときだけ。発議のあとは取り消せない（仕様）
   - 発議のあとは、賛同を受け付けない
5. **発議する**（`proposeBill(db, actor, billId, now)`）：確かめる順は 4 と同じ。書くのは次の1文で、賛同の数の確かめも同じ文の中で行う

   ```sql
   UPDATE bills SET status = 'proposed', proposed_at = ?, updated_at = ?
   WHERE id = ? AND user_id = ? AND status = 'draft' AND rev > 0
     AND (SELECT count(*) FROM bill_supports s WHERE s.bill_id = bills.id AND s.rev = bills.rev) >= ?
   ```

   - 0行なら、賛同が足りないか、ほかの画面で発議済みか、提出者でない。読み直して理由を出す
   - 発議要件は、押したときの会期の `sessionParticipants` から求める
   - Turnstile は使わない。上限も足さない（発議できる法案は、下書きを作る上限で抑えられている）
   - 引用した解決策が非表示になっていても発議できる（法案そのものは見られる。Issue #46 決めたこと3）
6. **会期を求める**：`sessionAt(nowOf(event), sessionMinutes(import.meta.env.DEV, env.SESSION_MINUTES))` をホームと法案のページの両方で使うので、`src/lib/server/client.ts` に `sessionOf(event)` を置く
7. **画面**（SpBillSummary・PcBillSummary・SpBills・PcBills）
   - 法案のページ：提出者の行に「賛同 N人」。賛同者の名前は出さない
   - ほかの人（下書きのとき）：「賛同する」または「賛同を取り消す」。ログインしていなければ、押すとログインへ（`SolutionCard` と同じ）。登録から7日たっていなければ、ボタンの代わりにいつから賛同できるかを出す
   - 提出者（下書きのとき）：「発議する」と「発議にはあと N人」。届くまでボタンは押せない。提出者には賛同のボタンを出さない
   - 発議のあと：ボタンを出さず、「賛同 N人」だけを出す
   - 直す画面：いまの賛同が1人以上なら、「保存すると、いまの賛同 N人は数えなくなります。集め直しになります。」と出す
   - 一覧：スマホは「下書き ・ 賛同 N人」、PC は「賛同」の列（「N人」）
8. **一覧の賛同の数**：`listBills` の `select` に、`bills.rev` と同じ `rev` の行を数える副問い合わせを足す。並びには使わない（#48 決めたこと1）

## テストの方針

- 単体テスト：`proposalRequirement` の境界、`sessionParticipants`（数える `kind`、前の会期の範囲の端、同じ人を重ねない、一度固定したら行動が増えても変わらない）、`setBillSupport`（版に結び付く、古い `rev`、発議のあと、提出者、同じ状態、上限）、`proposeBill`（足りない、ちょうど、提出者でない、二重）、保存で賛同を数えなくなること。60人以上の参加者は画面のテストでは作らず、単体テストで確かめる
- 画面のテスト（2幅）：賛同と取り消し、登録から7日、提出者のあと N人と発議、発議のあとの表示、直す画面の知らせ、一覧の賛同の数、国と締め出し、信頼の境界（`rev`、法案の番号、`op`）

## あとで決めること

- 古い版の賛同の行を消すか（いまは消さない）
- 賛同した人への、直されたことの通知（通知の機能と一緒に）
- 同じ条文に触れる法案を発議の時点で束ねること（v0.4）
