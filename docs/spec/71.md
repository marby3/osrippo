# 会期の終わりの処理と結果のページ（設計書）

Issue #71。マイグレーションがあり、会期終了時の処理なので Careful。仕様の正は [docs/spec.md](../spec.md) の「採決と投票の公正さ」。票とルールは [docs/spec/65.md](65.md)、修正案は [docs/spec/68.md](68.md)、画面の案は `SpResult`・`PcResult`。

ユーザーと決めたこと（Issue #63 の決めたこと1・2・5・6。仕様書のドキュメントへの反映はユーザー側）。

- 定足数は有効票を棄権も含めて数える。母数は付託先の会期の今月の参加者で、その 20% を切り上げ、最低10人
- 有効票で、賛成が反対より多ければ可決。棄権は比べに入れない。同数は否決
- 有効票か参考票かは締切の時点で判定する
- 本番は Cron Trigger（日本時間0時）で走らせ、次の会期で最初に読まれたときにも同じ処理を呼ぶ。何度走っても結果が変わらない。進みは今までどおり時刻から求め、結果と IF世界の版だけを書き込む

次のことは仕様書にないので、この Issue の受入基準で確かめる（STOP 1 で確認する）。

- A. **Cron は毎日走らせ、直前の会期だけを処理する**。もっと古い会期の取りこぼしは、その法案のページか結果のページを読んだときに処理する
- A2. **締切から1分は処理しない**。Cron は日本時間 0時1分に走り、読むときの処理も締切の1分後から。締切の直前に受け付けた票の書き込みが、数えたあとに届かないようにする（決めたこと1）
- B. **最初に読まれたときの処理を呼ぶ場所**は、法案の一覧、法案のページ（全部のタブ）、結果のページだけ。すべての要求で確かめない
- C. **読むときの処理が失敗しても、ページは出す**。結果がなければ「結果を集計しています」と出し、次に読まれたときか次の Cron でやり直す
- D. **参考の票との比べ**は、参考の票が定足数に届いているときだけ行う（1票だけの参考の票で「可否が逆」と出さないため）。逆なら数字の上に目立つ形で出す。同じなら参考の票の欄に「結果は数えた票と同じでした」と出す。**数えた票が定足数に届かず廃案のときは比べない**（廃案には可否がないため）
- E. **締切の前の結果のページ**は、ログインなしで読め、題名と「結果は締切のあとに出ます」だけを出す。票の数は計算もしない
- F. **修正案の結果**は、本案より先に採決した修正案の状態（可決・否決など）を結果のページに並べる。票の数は出さない（締切のあとの処理で記録していないため。修正案のタブへのリンクを付ける）
- G. **画面の言葉**：否決は「IF世界の法律にはなりません」、廃案は「数えた票が定足数（N票）に届きませんでした」

## 目的

締切で票を数えて結果を記録し、可決・否決・廃案と票の数を、結果のページと法案のページ、一覧に出す。

## 決めたこと

1. **1本の法案の処理**（`settleBill(db, session, bill, participants, now)`。`src/lib/server/results.ts`）。順は次のとおり
   1. `settleAmendments` を呼ぶ。`false` が返ったら（別の実行と重なった）、結果を書かずに返す。次の実行で続きから進む
   2. `tallyVotes` で本案の票を数え、`billOutcome(counted, quorum)` で判定する
   3. 本案の版を読み直し、`INSERT ... ON CONFLICT DO NOTHING` で結果を入れる

   修正案の処理は結果より先なので、結果の行があれば修正案は当て終わっている。途中で失敗しても、やり直すと修正案の処理は続きから進み、次の不変条件により同じ結果になる。先に入った行が残る

   **数える材料は締切のあとに変わらない**（結果を何度計算しても同じになる根拠）
   - 票：`castVote`・`castAmendmentVote` は `now < session.endsAt` のときだけ書く。書き込みの途中の要求は締切から1分で終わるので、処理はそのあとに始める（決めたことA2）
   - 投票資格：`user.created_at` と、会期の始まりより前の `actions` だけを見る。今の状態を見ない
   - 割り当て：`vote_assignments` は固定で、法案の状態を見ない（docs/spec/65.md 決めたこと10）
   - **あとの Issue の決まり**：票の履歴の削除と退会で `votes`・`amendment_votes`・`actions`・`vote_assignments` を消すのは、その会期の結果の行が入ったあとだけにする。Cron が落ち続けた古い会期では、先に確定してから消す

2. **会期の処理**（`settleSession(db, session, previous, now)`）：その会期に採決する法案（`billsInVote` と同じ条件）のうち結果のない法案を、発議の早い順に処理する。`now < session.endsAt + 1分` なら何もしない。母数は法案の委員会ごとに `sessionParticipants(db, committeeId, session, previous, now)` で求め、その会期に固定した値を使い、なければ前の会期の行動から数えて固定する。結果のない法案がなければ、問い合わせ1回で終わる
   - **1本が失敗しても残りを続ける**。失敗した法案は1本ごとに捕まえ、最後にまとめて投げ直す（1本のせいで全部が「集計中」にならないように）。Cron の記録には失敗として残る
   - **#72 への条件**：「発議の早い順に反映する」は結果の行を書く順に頼らない。その会期のすべての法案の結果が入ってから、発議の順に反映する。また、結果を書いたあと反映の前に失敗してもやり直せるよう、反映は結果の有無とは別に「未反映」を判定する
   - 対象と画面の条件は一致する：`billsInVote` の条件（保存済み、`status = proposed`、発議が前の会期の3週目の始まりからこの会期の3週目の始まりの前まで）は `referralSession(proposedAt) = session` と同じで、#65 のテストで確かめてある。会期が終わった法案（`billProgress` が `lapsed`）は必ずどれかの会期の対象になる

3. **Cron**（`src/worker/scheduled.ts`）：`wrangler.jsonc` の `triggers.crons` に `1 15 * * *`（日本時間 0時1分。決めたことA2）を足す。`controller.scheduledTime` を「いま」にして、その時刻を含む会期の1つ前の会期に `settleSession` を呼ぶ。分の会期は使わない（`pnpm dev` だけの機能で、Cron がない）。失敗は投げ直し、Cron の記録に残す

4. **Worker の入口**：`@sveltejs/adapter-cloudflare` は `wrangler.jsonc` の `main` の場所に Worker を書き出すので、`main` を自前のファイルにできない。そこで `main` はそのままにし、`pnpm build` の最後に `scripts/wrap-worker.ts` を走らせる
   - `.svelte-kit/cloudflare/_worker.js` を `_app_worker.js` に移し、`fetch` はそれに任せ、`scheduled` を足した `_worker.js` を書く。手元の `wrangler dev` で、`/cdn-cgi/handler/scheduled` から呼べて D1 を読めることを確かめた
   - `.svelte-kit/cloudflare` は公開ファイルの置き場でもあるので、`.assetsignore` に `_app_worker.js` を足す。足さないとサーバーの入口が公開される
   - `src/worker/scheduled.ts` と、そこから間接的に読むものは、`cloudflare:workers` と `import.meta.env` と `#lib` に頼らない（Vite を通らず wrangler が束ねるため）。`src/lib/server/client.ts` を読まない
   - 2回走らせても壊れないよう、`_worker.js` がすでに包んだものなら何もしない。`export default` のほかの書き出しがあれば、ビルドを失敗させる（引き継ぎ漏れを防ぐ）。デプロイは `pnpm build` を通す

5. **最初に読まれたときの処理**（`settleOnRead(db, session, previous, now)`）：`settleSession` を呼び、失敗はログに出して飲み込む（決めたことC）。呼ぶ場所は次のとおり
   - 法案の一覧：`now` を含む会期の1つ前の会期
   - 法案のページ（レイアウト）と結果のページ：付託先の会期が終わっていて結果のない法案の、付託先の会期

   テストは年を分けて時計を動かしているので、一覧と Cron が処理するのは「1つ前の会期」だけにする。もっと前まで広げると、ほかのテストの採決中の法案を締めてしまう。隣の会期を別のテストで使わない（今の割り当ても年を分けている）

6. **法案の段階**（`billStage(progress, outcome)`。純粋な関数。`src/lib/domain/votes.ts`）：`billProgress` は今までどおり時刻から求める。会期が終わった法案（`lapsed`）だけ、結果を見て `passed`・`rejected`・`lapsed` にし、結果がなければ `counting`（「集計中」）にする。段階は結果の行より時刻を優先するので、会期が終わる前に結果の行があっても可決と出さない。書き込みの時期の判定（`postWindowOpen` など）は `billProgress` のままで変えない

7. **結果を読む**：付託先の会期と法案の番号の組（`session_key`, `bill_id`）で読む（`resultOf`）。`settled_at` の新しさでは選ばない（要調整で次の会期に採決する法案で、前の会期の結果を返さないように）。一覧は1ページの法案の番号（50件まで）の結果を1回で読み、法案ごとの付託先の会期と比べる

8. **結果のページ** `/saiketsu/<番号>/kekka`（SpResult・PcResult）。ログインは要らない。ない番号と下書きは 404（`postableBill`）
   - どの状態でも、紫の斜線の帯（`data-if-band`）と `noindex`。帯はスマホが「架空の法律です」、PC が「このページの条文は架空のものです。現実の法律ではありません。」（`src/lib/components/IfBand.svelte`。#72 も使う）。文言は Issue #63「テストの作り方」の決定（`SpResult`・`PcResult` の帯に合わせる）。「架空の法令」の文字は条文を出す `/if/hourei`（#72）に付ける
   - 締切の前：題名と「結果は締切のあとに出ます」と締切の日時。`bill_results` も票も読まない
   - 結果あり：「可決」「IF世界の法律になりました」など（決めたことG）、「ゲームの中の結果です。世論調査ではありません。」、「数えた票 N」、賛成・反対・棄権の帯と数、参考の票の欄、修正案の結果、法案のページへのリンク
   - 帯グラフは色だけで示さない（反対は斜線、棄権は白。数も必ず出す）。読み上げには数の文字を使い、グラフは `aria-hidden`
   - 参考の票の欄：スマホは開閉（`button`）、PC は最初から出す。見出しの文字は1か所だけに置く
   - 結果がまだない：「結果を集計しています」

9. **法案のページと一覧**
   - 状態の表示は `billStage` を使う。スマホは「いま：可決」、PC は段階の並びの最後が「可決（いまここ）」
   - 会期が終わった法案の概要に「結果を見る」のリンクを出す
   - 一覧の「終わった」のタブの段階の欄も同じ。タブの分け方（`lapsedBefore`）は変えない
   - `/saiketsu/<番号>` は、会期が終わった法案なら結果のページへ移す（今は法案のページ）

10. **置き場所と文言**：純粋な関数は `src/lib/domain/votes.ts`、DB に触れるものは `src/lib/server/results.ts`、文言は `ja.result` と `ja.bill.progress`
