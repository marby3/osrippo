# 統計ページ（設計書）

Issue #154。統計の匿名化の基準に触れるので Careful。仕様の正は [docs/spec.md](../spec.md) の「統計の公開」「匿名化の基準」「法案の橋渡しスコア（最初の版）」。前提の決定は Issue #147 の決めること20・21、受入基準と決めたことは Issue #154（2026-11-12 ユーザーと決定）。立場別の分布の集計は [87.md](87.md)、評価と「考えが変わった」の数え方は [67.md](67.md)、5%刻みは [149.md](149.md)。

## ユーザーと決めたこと（Issue #154）

1. **立場を超えた支持（法案）**：締切の時点のその法案への立場で賛成寄り・反対寄りに分け、それぞれの数えた票のうち「賛成」の割合の低いほうを採る。どちらかが10人未満の法案は順位に入れない。5%刻み
2. **「考えが変わった」の順位**：質疑と答弁のうち10人以上から付いたものを多い順に。付いた数は出さない
3. **範囲**：会期ごとに切り替え。最初はいちばん新しい終わった会期
4. **入り口**：PC はヘッダーに「データ」のタブ。スマホは下の5つのタブを変えず、メニュー（人の形のボタンの先）に「データ」

## この設計書で決めること

- A. **ページ**は `/toukei`、会期は `?kaiki=2050-05`（開発用の短い会期は `m8-123` の形）。ログインは要らない。IF世界の法案の結果を出すので、結果のページと同じく IF世界の帯（`ifBand`）と `noindex` を付ける（現実の統計と取り違えられないように。CLAUDE.md の決まり）
- B. **終わった会期**は、結果の行（`bill_results`）がある会期のうち、会期の終わり（`endsAt`）を過ぎたもの。並びは会期の始まり（`startsAt`）の新しい順（結果を記録した時刻は、Cron の取りこぼしを後で処理すると前後するので使わない。短い会期の番号も文字の順では並べない）。最初に出すのはその先頭
- C. **統計ページは会期の結果を作らない**（立場別の分布の集計は作る。下の F）。結果は今までどおり Cron（毎日0時1分）か、結果のページ・法案のページ・一覧の「終わった」のタブを読んだときに作られる（71.md の B）。統計ページはどの要求でも会期の処理を呼ばない（重い処理を公開のページに足さないため）。会期が終わってから Cron が走るまでは、その会期は選べない。会期の一覧を結果のある会期に限るのはわざと（結果のない会期は、選んでも出すものがない）。結果の行がまだない法案（集計中）は、法案の結果の表に出さない
- D. **`?kaiki=` の確かめ**：形が違えば 404。形が合っていても、まだ終わっていない会期（`now < endsAt`）は 404。終わっていて結果の行がない会期は 200 で、3つの欄に「この会期に採決した法案はありません」を出す（会期の一覧には出ない）。開発用の短い会期の番号は、いまの設定の分数と合うときだけ受ける
- E. **法案の結果**（基準3）：その会期の結果の行を、題名の順ではなく法案の番号の順に並べる。確認の行が `open` なら「結果を確認しています」だけ（可否と票の数をページのデータにも入れない）。`voided` なら「廃案」と出し、票の数は結果のページと同じく出す。ほかは可決・否決・廃案と、数えた票（賛成・反対・棄権）
- F. **立場を超えた支持の計算**（基準4）：#87 の `stanceStatsOf` で法案ごとの丸める前の人数を読み（なければ作る。確認中・無効は null。結果のページと同じく、読んだときに一度だけ書く。1会期の法案は多くて十数本）、ルールの関数 `billBridge(votes)` が `for` と `against` の合計がどちらも `STATS_MIN`（10）以上のときだけ `min(for.yes / for合計, against.yes / against合計)` を返す。未定の人は入れない（仕様は2グループ）。画面に渡すのは `roundRatio` で丸めた値だけ。並びは丸めた値の高い順、同じなら法案の番号の順（丸める前の値で並べると、同じ割合に見える法案の順から細かい差が分かるため）。10本まで
- G. **「考えが変わった」の数え方**（基準5）：今の `sessionPostScores(db, sessionKey)` の `changed`（評価の上限を当てた数。67.md の H・I。会期の評価をまとめて読む。上限が法案をまたぐので、別の数え方を作らずこれを使う）。1人が1つの投稿に付けられるのは1回なので、`changed` は付けた人の数。10以上の投稿を、`changed` の多い順、同じなら投稿の番号の順に10件。数は並びに使うだけで、ページのデータには入れない。投稿の状態が見えている（`POST_SHOWN`）ものだけを先に選び、そのあとで10件にする（`sessionPostScores` は「まとめた」投稿も数えるが、まとめた投稿は出さない）。答弁は親の質疑も見えているものだけ
- H. **順位に出す投稿の中身**：「質疑」か「答弁」かの別、本文のはじめの60字（コードポイントで数える。それより長ければ「…」）、法案の題名、`/houan/{法案}/shitsugi#shitsugi-{質疑の番号}` へのリンク（答弁なら親の質疑の番号）。投稿者の名前は出さない
- I. **入り口のスマホ**：メニュー（`/watashi`、ログインが要る）に「データ」のリンクを足す。ログインしていない人のために、ホーム（`/`）の下にスマホだけ「データを見る」を足す。採決のタブの一覧（`/saiketsu`、ログインが要る）の下にも「データを見る」を足す（スマホの下のタブは5つのまま）
- J. **「データ」のタブ**：`TABS` の最後（「法律」の右）に `toukei`（`/toukei`）を足し、PC のヘッダーにだけ出す（PC のタブは6つ。案の PcResult のとおり）。スマホの下のタブはいままでの5つ（`TABS` から `toukei` を除いて並べる）。`tabOf('/toukei')` は `toukei`

- K. **残る推定の余地（匿名化）**：立場を超えた支持は5%刻みでも、グループが10〜20人のときは1人の票で値が必ず動く（149.md の残る余地と同じ）。法案の数えた票の合計は結果のページですでに公開しているが、グループの人数は出さないので、合計と割合からグループの票を一意には戻せない。#87 で結果のページに立場ごとの割合（同じ基準）を出すことを決めており、統計ページはそれより細かい値を出さない。基準を上げるか丸めを粗くするかは、参加者が増えて区分が大きくなってから見直す

## 範囲

- 入れる：`/toukei` のページ、会期の一覧と確かめ、法案の結果、2つの順位、PC のタブ、スマホの入り口、文言
- 入れない：投票傾向の匿名マップ、立場の動きの再生、現実の国会との違い、委員会ごとの賛否の割れ方（#147 の決めること21）、会期をまたいだ順位、統計ページから結果を作ること（C）

## ルールの関数（`src/lib/domain/toukei.ts`）

- `sessionFromKey(key: string, minutes: number | null): Session | null`：`minutes` が null なら `YYYY-MM`（年は1000〜9999、月は01〜12）だけを受けてその月の会期。`minutes` があれば `m{分}-{番号}` で分が同じものだけ（`YYYY-MM` は受けない）。ほかは null
- `billBridge(votes: StanceStatsData['votes']): number | null`（F。丸める前）
- `rankBridges(rows: { billId; title; bridge: number | null }[]): { billId; title; ratio }[]`：null を除き、丸めた値の高い順・番号の順に10本
- `rankChanged(rows: { postId; changed }[]): number[]`：`changed >= STATS_MIN` を多い順・番号の順に10件の番号だけ
- `excerpt(body: string): string`（60字）

## サーバーの関数（`src/lib/server/toukei.ts`）

- `finishedSessions(db, now, minutes)`：B。`bill_results` の `session_key` を重ねずに読み、`sessionFromKey` で会期に戻し、終わったものだけを `startsAt` の新しい順に
- `sessionResults(db, session)`：E。結果の行と確認の行と法案の題名
- `bridgeRanking(db, session, rows, now)`：F。確認中・無効でない法案ごとに、選んだ会期の分を `stanceStatsIn(db, bill, session, now)` で読む（要調整で発議の日付が次の会期に動いた法案でも、発議の日付から会期を求めない）。結果のページへのリンク（`/saiketsu/{法案}/kekka`）は、そういう法案では次の会期の結果を開く（結果のページは法案ごとに1つで、会期を選べないため。要調整の法案は少なく、リンク先でも同じ法案の結果を読める）
- `changedRanking(db, session)`：G・H。`sessionPostScores` から10人以上の番号を選び、状態と親の質疑の状態だけを読んで見えているものを並べ、10件の本文と法案の題名を読む。番号は `json_each` で渡すので D1 の値の数の上限にかからない
- ページの読み込みが返すのは、題名・可否・票の数・丸めた割合・質疑か答弁かの別・本文のはじめ・リンクの番号だけ。確認中の法案は題名と番号と状態だけ。グループの人数と `changed` は返さない

## テスト

- **ルールのテスト**（`src/lib/domain/toukei.test.ts`）：`sessionFromKey`（月の形、13月、分の会期の分が違う）、`billBridge`（10人ちょうどと9人、未定は入れない）、`rankBridges`（丸めた値で並べ、同じなら番号の順）、`rankChanged`（10ちょうどと9）
- **画面のテスト**（`e2e/toukei.spec.ts`、2幅。基準ごとに1本。ほかのテストと会期がぶつからない年）
  - 基準1：PC はヘッダーの「データ」（いまのタブ）、スマホは下のタブが5つで「データ」がなく、わたしの記録と採決の一覧から行ける。ログインなしで 200
  - 基準2：最初に出る会期は選択肢の先頭（ほかのテストの会期も並ぶので、自分の会期かどうかでは確かめない）。自分の2つの会期が新しい順に並び、選ぶと URL に `?kaiki=` が付いて切り替わる。`?kaiki=abc`・まだ終わっていない会期で 404
  - 基準3：否決・廃案の法案の行（題名・結果・票の数・リンク。可決は IF世界の条文を変える準備が要り、ほかのテストとぶつかるので、表示の分岐が同じ否決で代える）。確認中の法案は「結果を確認しています」で、ページのデータに票の数も可否もない。運営が無効にすると「廃案」
  - 基準4：両方のグループが10人以上の法案に「立場を超えた支持 N%」。片方が9人の法案は入らない。ページのデータに人数がない
  - 基準5：10人が「考えが変わった」を付けた質疑と答弁が出て（答弁は「答弁」と出し、親の質疑へのリンク）、9人の質疑は出ない。ページのデータに数がない
  - 基準6：2幅で横にはみ出さない。実装用語（橋渡し、有効票など）を出さない。色は今までの `src/lib/styles/tokens.test.ts` が担う

基準3〜5の準備は重いので、同じワーカーの中で次の3つの会期を作って使い回す（#87 の画面のテストと同じ形）。1つの会期に法案が3本までなら、投票する人は全部の法案に割り当てられ、全部に投票しないと数えた票にならないため、会期を分ける。

- 主な会期：法案A（賛成寄り10人：賛成6・反対4、反対寄り10人：賛成2・反対8 → 否決、立場を超えた支持 20%）と法案B（同じ人で、反対寄りは9人 → 順位に入らない）。法案Aの質疑2件に、それぞれ10人と9人が「考えが変わった」を付ける。3件目の質疑に提出者が答弁し、その答弁に10人が付ける
- 廃案の会期：法案1本に3人が投票 → 廃案
- 確認中の会期：法案1本に10人が賛成し、うち5人が同じ回線 → 確認中。基準3の中で運営が無効にする
