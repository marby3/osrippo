# 課題の一覧・投稿・ページと「わかる」（設計書）

Issue #25。マイグレーションを足し、荒らし対策の境界を作るので Careful。仕様の正は [docs/spec.md](../spec.md) の「課題・解決策・法案」「不正・荒らし対策とモデレーション」「ドメイン・URL・メール」。ログインは [docs/spec/23.md](23.md)。

仕様書にない次のことは、2026-11-03 にユーザーと決めた（仕様書のドキュメントへの反映はユーザー側）。

- 課題は「お題」に関係なく自由に出せる。お題に沿った課題は全部議論して可決まで進め、お題から外れた課題は次の会期への持ち越しになりうる。課題は投稿者が自分で「お題に関係ある／ほかの話題」を選ぶ
- 荒らし対策は、fail2ban の考え方（制限を何度も超えたら、しばらく締め出す）と、Tailnet Lock の考え方（信頼が積み上がるまでできることを絞る）をアプリに移す
- 締め出すのはアカウントだけで、IP は締め出さない。日本の携帯回線は多くの人で1つの IPv4 を共有する（CGNAT）ため、1人の荒らしのせいで同じ回線の全員を止めないように。IP ごとの上限は残すが、それに当たって断ったことは違反に数えない
- ログイン・課題の投稿・「わかる」は、日本からのアクセスだけにする。閲覧は世界中から

## 目的

ログインした参加者が課題を書き、ほかの人が「わかる」をワンタップで付けられるようにする。最初の参加の入口を作る。

## 範囲

- 入れる：課題の一覧（`/kadai`）、課題のページ（`/kadai/[id]`）、課題を書く（`/kadai/kaku`）、「わかる」の付け外し、お題、Turnstile（課題の投稿とログイン）、レート制限、締め出し、国外からの書き込みの制限、トップページから一覧へのリンク
- 入れない（別の Issue）：似た課題の提示と統合、通報と非表示、解決策、法案、全文検索（一覧の「課題を探す」欄）、人物名の警告、立場を超えた支持の並び、委員長によるお題の付け直し、ヘッダーのナビ
- 画面の案（SpIssues・SpIssue・SpIssueNew・PcIssues・PcIssueNew）のうち、上の「入れない」に当たる部品（似た課題の欄、「解決策あり」「法案あり」、解決策と法案の欄、通報のリンク、議員の「検討中」、「課題を探す」）は出さない。それぞれの Issue で足す

## 表

`drizzle/0003_*.sql`（`drizzle-kit generate`）。お題の最初の1行はマイグレーションの末尾に手で `INSERT` を足す（本番でも同じ行ができるように。snapshot は表の形だけなので影響しない）。前の文との間には `--> statement-breakpoint` を入れる。

| 表 | 列 | 備考 |
| --- | --- | --- |
| `topics` | `id`（整数、主キー）、`name`、`created_at` | お題。最初の行は `1, '消費者保護'`。「今回のお題」は `id` が最大の行（会期はフェーズ3で作り、そのときに会期と結ぶ） |
| `issues` | `id`（整数、自動採番）、`user_id`（`user` への外部キー。`ON DELETE` は既定（消させない）。退会は「あとで決めること」）、`title`、`affected`（困っている人）、`example`（具体例）、`topic_id`（`topics` への外部キー、NULL＝ほかの話題）、`created_at` | 索引：`topic_id` |
| `issue_supports` | `issue_id`（`issues` への外部キー）、`user_id`（`user` への外部キー）、`created_at` | 主キー（`issue_id`, `user_id`）。取り消すと行を消す |
| `actions` | `id`、`kind`（`issue_post`／`support_add`／`support_remove`／`violation`）、`user_id`（`user` への外部キー）、`ip_hash`、`target_id`（NULL 可。「わかる」では課題の `id`）、`created_at` | レート制限を数えるための記録。索引：（`user_id`, `kind`, `created_at`）、（`ip_hash`, `kind`, `created_at`）、（`target_id`, `kind`, `created_at`） |
| `bans` | `user_id`（主キー、`user` への外部キー、`ON DELETE CASCADE`）、`until`、`created_at` | アカウントの締め出し。期限が来たら効かない（行は残してよい。次の締め出しでは上書きする） |

`created_at` と `until` はどれもミリ秒の整数（既存の表と同じ `timestamp_ms`）。`issue_supports` の外部キーも `ON DELETE` は既定。

## 決めたこと

1. **URL**：一覧 `/kadai`、課題 `/kadai/[id]`（`id` は `issues.id`。課題は公開のものなので番号が URL に出てよい）、書く `/kadai/kaku`。`id` は 1〜9999999999 の整数（先頭の0なし）だけを受け付け、それ以外の形（`abc`、`01` など）と存在しない `id` は 404（信頼の境界。`?/support` の POST も同じ）。仕様書の「パンくずの『課題 › #123』」のパンくずは、ヘッダーのナビと一緒に別の Issue で作る
2. **入力**（信頼の境界）：サーバーで確かめる。改行を `\n` にそろえ、前後の空白を除いてから数える。文字数はコードポイントで数える（`[...s].length`）。ブラウザの `maxlength` は UTF-16 の単位で数えるので、絵文字を含むとブラウザのほうが先に止まる（厳しい側にずれるだけなので、そのままにする）
   - 「制御文字」は `\p{Cc}` と、文字の向きを変える書式文字（U+202A〜U+202E、U+2066〜U+2069）。一覧で表示を偽れないように。ゼロ幅接合子などほかの `\p{Cf}` は絵文字に使われるので許す
   - タイトル（何に困っていますか）：1〜60字、改行と制御文字なし
   - 困っている人：1〜60字、改行と制御文字なし
   - 具体例：1〜400字。改行は可、ほかの制御文字なし
   - お題：`topic` が「今回のお題」の `id` か `none`。それ以外は誤り
   - 誤りがあれば保存せず、その欄の横に理由を出す（入力は残す）
   - 表示は Svelte の通常の差し込みで行い、`{@html}` は使わない（XSS対策）。具体例は `white-space: pre-wrap` で改行を出す
3. **課題を書く**：ログインが要る（`requireUser`、docs/spec/23.md 決めたこと7）。1つの `<form method="post">` を3つのステップ（1 タイトル／2 くわしく／3 確認）に分けて見せる。ステップの切り替えは画面の中だけで行い、送るのは確認のステップの「投稿する」だけ。
   - ステップ1：タイトル。「次へ」と「やめる」（`/kadai` へ）
   - ステップ2：困っている人、具体例、お題（「関係ある（消費者保護）」「ほかの話題」のラジオ。初めはどちらも選ばない）。「次へ」と「戻る」
   - ステップ3：入力した内容をそのまま並べ、Turnstile と「投稿する」。「戻る」。どの欄にも属さない誤り（国・締め出し・Turnstile・レート制限）はこの段に出す
   - 「次へ」はその段の欄をブラウザの検証（`required`・`maxlength`）で確かめてから進む。送るのは `use:enhance` で行い、サーバーで誤りが返ったら、誤りのある最初の欄の段を開き、Turnstile を作り直す（`turnstile.reset()`。トークンは1回しか使えず、判定で使い終わっているため）
   - Turnstile に JS が要るので、JS がないと投稿できない（3つの段は全部縦に並んで見えるが、投稿は通らない）。閲覧と「わかる」は JS なしでも動く
   - 投稿できたら `/kadai/[id]` へ 303
4. **課題の一覧**：ログインなしで見られる。並びは3つから選べる（ユーザーの希望、2026-11-03）。どれも最後は `id` の大きい順で決める（同じミリ秒の行でもページの境目でずれないように）。
   - 「わかる」の多い順（既定。`sort` なし）：仕様「投票履歴がたまるまでは『わかる』の数で並べる」
   - 新しい順（`?sort=new`）
   - 最近「わかる」が増えている順（`?sort=rising`）：直近7日に付いた「わかる」（`issue_supports.created_at`）の数、同じなら「わかる」の数。新しい課題が埋もれないように
   - 「立場を超えた支持順」は、橋渡しスコアの Issue で足す
   - 画面は画面の案の「並び：」の選択欄。選んだときに `sort` を付けた URL へ移る（既定の並びは `sort` を書かない URL にするため、フォームでは送らない。フォームで送ると `sort=support` になり 404 になる）。JS がなければ `<noscript>` の中に3つの並びのリンクを出す。絞り込みとページと組み合わせられる（並びや絞り込みを変えたら1ページ目へ）
   - `sort` は `new` と `rising` だけを受け付け、それ以外の形は 404（信頼の境界）
   絞り込みは「すべて」「今回のお題」（`?topic=current`）。1ページ50件、`?page=2` で次。`page` は 2〜9999 の整数（先頭の0なし。1ページ目は `page` なしの URL だけ）、`topic` は `current` だけを受け付け、それ以外の形は 404（信頼の境界）。課題のないページ（2ページ目以降）も 404。行には、タイトル（課題へのリンク）、わかるの数、お題の印（「お題：消費者保護」。ほかの話題なら出さない）。PC は表、スマホは縦の並び（画面の案どおり）。課題が1件もなければ「まだ課題がありません」と「課題を書く」。「今回のお題」で0件なら「今回のお題の課題はまだありません」
5. **課題のページ**：ログインなしで見られる。タイトル、お題の印、「困っている人」、「具体的には」、「わかる」のボタンと数、その下に「同じことで困っていたら押してください」。押した人には押した状態（`aria-pressed="true"`）で出し、もう一度押すと取り消す
6. **「わかる」**：課題のページのフォームの POST（`?/support`）。フォームの値 `op` で `add`（付ける）か `remove`（外す）を送る（いまの状態の反転にはしない。二度押しや再送信で状態が行き来しないように）。`add` を付いている状態で送っても、`remove` を付いていない状態で送っても、状態は変わらず、`actions` にも数えない。`op` がそれ以外の形なら 400（信頼の境界）。JS がなくても動き（ログインには Turnstile のために JS が要るので、既にログインしている人のとき）、JS があればページを読み直さずに数と状態を変える（`use:enhance`）。ログインしていなければ `/login?next=/kadai/[id]` へ送る。投稿者も自分の課題に付けられる。数は `issue_supports` の行の数
7. **アクセス元の国**：ログイン（`/login` の POST）、課題の投稿、「わかる」は、国が `JP` のときだけ受け付ける。国は Cloudflare が要求に付ける `request.cf.country`。SvelteKit 3 の adapter-cloudflare は `platform` を作らず、Worker が受け取った要求をそのまま `event.request` に渡すので、`event.request.cf.country` を読む。`CF-IPCountry` などのヘッダーでは補わない（クライアントが送れるため）。`T1`（Tor）、国が分からないときも断る。断るときは保存せず、「日本国内からのみ参加できます。見ることは国外からもできます」と出す（状態コード 403）
8. **Turnstile**：課題の投稿と、ログインの POST にかける。
   - 画面：ログインの画面は今の1つのフォーム（`formaction` で Google と LINE に振り分ける）に1つ置く。`https://challenges.cloudflare.com/turnstile/v0/api.js` を読み、サイトキーは `TURNSTILE_SITE_KEY`（公開してよい値。`wrangler.jsonc` の `vars`）。フォームに `cf-turnstile-response` が入る
   - サーバー：`https://challenges.cloudflare.com/turnstile/v0/siteverify` に、`TURNSTILE_SECRET_KEY`（秘密の値）、トークン、アクセス元の IP を送り、`success` が真で、応答の `hostname` が要求のホスト名と同じときだけ通す（サイトキーのドメインの設定を間違えたときの保険）。通らないとき・応答が返らないとき（5秒で打ち切り）は保存せず「確認できませんでした。もう一度お試しください」（状態コード 400）
   - 判定は `src/lib/server/turnstile.ts` の `verifyTurnstile(token, secret, ip, hostname, fetch)`。`fetch` を渡せるようにして、単体テストではダミーの応答を返す。`hostname` が `null`（手元）のときは比べない（テスト用の鍵の応答は自分のホスト名を返さないため）
   - **画面のテスト**：テストからは外部の API を呼ばない（e-Gov と同じ方針）。`TEST_LOGIN` が `1` かつ要求のホストが `localhost`／`127.0.0.1` のときだけ（docs/spec/23.md 決めたこと10と同じ条件）、siteverify を呼ばず、トークンが `test-pass` なら通す。画面のテストは Playwright の `page.route` で `api.js` を差し替え、`cf-turnstile-response` に `test-pass`（通らない例は `test-fail`）を入れる小さなスクリプトを返す。#23 のログインの画面のテストにも、この差し替えを足す
9. **アクセス元の IP**：`CF-Connecting-IP` ヘッダー。IP はそのまま保存せず、`HMAC-SHA256(IP_HASH_SECRET, ip)` の16進（`ip_hash`）だけを保存する。`IP_HASH_SECRET` は秘密の値（替えると、それまでの IP ごとの数えが途切れる。運用のメモ）。
   - IPv6 は省略表記（`::`）を展開して小文字にそろえ、先頭の /64 にしてからハッシュにする（1つの契約に /64 が割り当てられ、一時アドレスがよく変わるため）。`::ffff:a.b.c.d` は IPv4 の `a.b.c.d` として扱う。IPv4 はそのまま
   - 手元（要求のホストが `localhost`／`127.0.0.1`）：
     - 国：決めたこと8の画面のテストの条件（`TEST_LOGIN=1`）でヘッダー `x-test-country` があればその値、それ以外（ヘッダーがないときを含む）は `JP`。手元の wrangler は国を `US` などにするので、`pnpm dev` でもログインと投稿を試せるように。本番は公開のホスト名で届くので、この分岐に入らない（docs/spec/23.md 決めたこと10と同じ理由）
     - IP：画面のテストの条件ならヘッダー `x-test-ip`（同じ IP から複数のアカウントで押す例を作るため）、なければ `CF-Connecting-IP`、それもなければ `127.0.0.1`
   - 手元以外で `CF-Connecting-IP` がないとき（本番では Cloudflare が必ず付けるので、起きないはず）は、国が分からないときと同じく断る
10. **レート制限**：期間はどれも「いまから遡った長さ」（日付の区切りではない）。数えるのは `actions` の受け付けた操作だけ（断った操作は数えない）。どれかを超えたら保存せず、超えた内容と「しばらくしてからお試しください」を出す（状態コード 429）
    | 制限 | 数える `actions` | 上限 | 違反に数えるか |
    | --- | --- | --- | --- |
    | 課題の投稿（アカウント） | 同じ `user_id` の `issue_post` | 24時間に5件 | 数える |
    | 登録から24時間のアカウント（Tailnet Lock の考え方。`user.created_at` から24時間） | 同じ `user_id` の `issue_post` | 24時間に1件（上の5件より先に効く） | 数えない（登録したばかりの人が試しているうちに締め出されないように）。断るときは「{M月D日 H時mm分}から次の課題を書けます」と出す |
    | 課題の投稿（IP） | 同じ `ip_hash` の `issue_post` | 24時間に20件 | 数えない |
    | 「わかる」（アカウント） | 同じ `user_id` の `support_add` と `support_remove` | 24時間に50回、かつ5分に10回（付けるのも取り消すのも1回） | 数える |
    | 同じ課題への「わかる」（IP） | 同じ `ip_hash`・同じ `target_id` の `support_add` の、自分以外の `user_id` の種類の数 | 24時間に3アカウントまで（3以上なら4人目を断る。そのアカウントが24時間のうちにこの課題へ `support_add` していれば、どの IP からでも付け直しは断らない。取り消しは断らない） | 数えない |
    - 同じ課題への「わかる」を `issue_supports` から数えないのは、取り消すと行が消え、「付ける→外す→別の人が付ける」で何人でも付けられてしまうため
    - 違反に数えるものを断ったときは、`actions` に `violation` を1行書く。IP の上限は、同じ回線の別の人のせいで当たることがあるので数えない
    - 同じ課題への「わかる」で断るときの文言は「この回線からは、この課題にこれ以上『わかる』を付けられません」
11. **締め出し**（fail2ban の考え方）：アカウントの `violation` が24時間に3回になったとき、そのアカウントを3回目の時刻から24時間締め出す（`bans`）。IP は締め出さない（上の「ユーザーと決めたこと」）。
    - 締め出しの間は、そのアカウントの課題の投稿と「わかる」を断る（状態コード 429）。文言は「制限を何度も超えたため、{M月D日 H時mm分}まで、課題の投稿と『わかる』ができません」（日本時間。分は2桁：9時05分）
    - 締め出し中に断った操作は違反に数えない（締め出しが延び続けないように）
    - 期限が来たら自動で解ける。ログインと閲覧は締め出さない
12. **判定の置き場所**：数を受け取って許すか断るかを返す純粋な関数を `src/lib/domain/limits.ts` に置く（時刻は引数で渡す。単体テストで24時間後などを作れるように）。D1 から数えるのは `src/lib/server/issues.ts`（投稿と「わかる」の保存と同じ場所）。国・締め出しの確かめと、断るときの文言は `src/lib/server/client.ts`。投稿・「わかる」は、ログイン（`requireUser`）→ 国 → 締め出し → Turnstile（投稿のみ）→ 入力 → レート制限 → 保存、の順に確かめる
13. **同時の操作**：「わかる」の付け外しは `issue_supports` の主キーで重ならない（付けるのは `INSERT … ON CONFLICT DO NOTHING`、外すのは `DELETE`）。レート制限の数えと保存の間で同時に押されると、制限を1〜2回超えることがある。ゆるしてよい（D1 に行のロックがないため。荒らし対策として困るほどではない）
14. **秘密の値と設定**：`TURNSTILE_SECRET_KEY`、`IP_HASH_SECRET` を `wrangler.jsonc` の `secrets.required` に足す（`.dev.vars.example` にも名前を足す。`TURNSTILE_SECRET_KEY` には手元用として Cloudflare のテスト用の秘密の値 `1x0000000000000000000000000000000AA`（いつも通る）を書いておく。`pnpm dev` で siteverify が通るように）。`TURNSTILE_SITE_KEY` は `vars` に Cloudflare のテスト用サイトキー（`1x00000000000000000000AA`、いつも通る）を置き、本番とステージングの値はデプロイの Issue で決める。画面のテストのサーバー（`scripts/preview-test.ts`）は、ダミーの秘密の値を `--var` で渡す
15. **テスト用のログイン**：`/test-login` に `days`（0〜365 の整数。省略は 0）を足す。新しく作る利用者の `created_at` を、その日数だけ前にする（決めたこと10の「登録から24時間」を画面のテストで避けるため）。既にいる利用者は変えない。形が違えば 400
16. **言葉**：画面の文言は `src/lib/copy/ja.ts` の `issue` に置く。ログインでも使う断るときの文言（国、Turnstile、レート制限、締め出し）は `guard` に置く。画面に実装用語（IP、レート制限、Turnstile など）を出さない。断るときの文言は上の決めたことのとおり
17. **トップページ**：「課題を見る」（`/kadai`）のリンクを足す。ヘッダーのナビは別の Issue
18. **Better Auth のセッション**：Better Auth は既定で `x-forwarded-for` の IP を `session.ip_address` に保存する。基準9（IP はそのまま保存しない）に合わせ、`advanced.ipAddress.disableIpTracking` で保存させない（実装のレビューで見つかった）

## テストの方針

- 入力の判定（決めたこと2）、IP のハッシュ（決めたこと9。IPv6 の省略表記と `::ffff:` の例を含む）は、Vitest で純粋な関数を確かめる。レート制限と締め出し（決めたこと10・11）は、マイグレーションを当てた node:sqlite に D1 と同じ SQL を流し、時刻を引数で動かして確かめる（数える SQL と判定を一緒に確かめるため）
- `verifyTurnstile` は、ダミーの `fetch` で通る・通らない・返らないを確かめる
- 画面は Playwright の2幅で、一覧・ページ・書く・「わかる」の付け外し・ログインへの誘導を確かめる。レート制限は「わかる」の5分に10回（11回目で断る）と、同じ IP の4人目で配線を確かめる。国は `x-test-country: US` で断られること、Turnstile は `test-fail` で断られることを確かめる
- 画面のテストの DB は起動のときに1回作り直すだけなので、レート制限に触れるテストは、テストごと・幅ごとに別の `name`（テスト用のログイン）と `x-test-ip` を使い、数えがテストどうしで混ざらないようにする
- 信頼の境界の入力（タイトル・困っている人・具体例・お題・課題の `id`・「わかる」の `op`・一覧の `page`・`topic`・`sort`・`days`）は、形の違う値を1つずつ送って断られることを確かめる
