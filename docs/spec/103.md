# 修正案の通報と非表示（設計書）

Issue #103。修正案の採決と会期の処理（`settleAmendments`）に関わるので Careful。投稿の通報と非表示（[docs/spec/80.md](80.md)）の上に作る。修正案の決まりは [docs/spec/68.md](68.md)、通知は [docs/spec/78.md](78.md)。決定の記号は #80 を分ける前のものを保つ（K〜M は修正案だけの決定。A〜D、H、N〜Q、W、X は投稿の決定を修正案に広げるもの）。

投稿と違うのは次の4つで、ほかは docs/spec/80.md のとおり。

- 非表示は `status` と別の列に持つ（共同起草者と結果を `status` から求めているので）
- 発議のあとにも関わりが増える（修正案を出す、賛同する）ので、関わりは通報のときでなく数えるときに判定する
- 非表示にすると採決の対象から外れる。3人の通報で採決の直前に対抗案を外せないように、自動で非表示にしない時期を置く
- 修正案は更新できる（本案の版が変わったときに提案者が書き直す）。通報は本文でなく修正案に結び付ける（決定K）

## 決定

### 通報

- A. **対象**：修正案。理由と説明は投稿と同じ。時期の制限はない（結果のあとでも、理由の欄の攻撃は隠せるように）
- B. **自動非表示**：登録から24時間たった別々の3人の通報で自動で非表示。対象は `moderation_status = 'visible'` だけ。記録の理由は「通報が3件」
  - **数に入れない人**：その法案の提出者、どの版かの賛同者、共同提出者、抜けた共同提出者、同じ法案に修正案を出した人、**同じ法案のどれかの修正案に賛同している人**（どの本文の賛同でも。対抗案の賛同者が相手を隠せないように。取り消した人は行がないので数える）。投票は見ない
  - **判定は数えるときに行う**（自動の非表示の文の中で、そのときの関わりを見る。`counted` は登録から24時間たっているかだけ。先に対抗案を通報してから自分の修正案を出しても抜けられないように）。すでに非表示になったものは、あとで関わりが変わっても戻らない
  - **自動で非表示にしない時期**：`status = 'open'` の修正案は、採決の24時間前（`voteAt - 24時間`。`acceptOpen` と同じ境）から、会期の処理で `status` が変わるまで、自動で非表示にしない。文の条件は `(status <> 'open' OR now < 境)` で、期間でなく状態で書く（採決の締切から会期の処理までのあいだに非表示になって票が捨てられないように）。この時期も通報は受け付け、`/kanri` に出る。この時期に3件たまっても、処理のときには隠さない。**処理のあとの新しい通報のときに判定する**（それまでは `/kanri` の一覧に出ているので、運営が隠せる）
  - **境の時刻**は修正案の法案の `referralSession(bill.proposedAt, minutes).voteAt` から求める（`progressOf` の `session`）。今の時計の会期から求めない（締切のあとに次の会期へ進み、境の前に戻ってしまうので）。発議し直すのは結果のあとだけなので、`open` の修正案は必ずこの会期のもの
- C. **上限**：課題、解決策、投稿の通報と合わせて1アカウント24時間に10件（`reportsInDay`）。超えると違反に数える。1人1件で、2回目は何もしない。自分の修正案は通報できない
- D. **受け付けの順**（`?/reportAmendment`）：法案の番号と存在、変えられる条があるか（404）→ ログイン → 国 → 締め出し → 入力（`amendment`、`reason`、`note`。形が違えば 400）→ 修正案がその法案のものか（ない番号も含めて 404）→ 自分のもの（400）→ 状態（非表示なら 403 と「非表示の修正案には操作できません」）→ 2回目（200）→ 上限（429）→ 保存。登録から7日と Turnstile は使わない

### 見え方

- H. **本人と運営にだけ見せる**：書いた本人と、運営の画面の権限のある人には、修正案のタブの1ページ目の最後に、見出し「非表示の修正案」の欄を出す。自分の（運営はその法案の）非表示の修正案の条、本文、理由の欄、「非表示になっています」と非表示の理由を新しい順に。件数に上限は設けない。ほかの人には何も出さない。扱えない運営（決定O）には自分のものだけを出す。扱える運営には、自分のもの以外の各行に「運営として対応する」のリンクを出す

### 修正案

- K. **非表示は `status` と別の列**（`moderation_status`。値は `visible`・`auto_hidden`・`hidden`・`restored`）。`status` が何でも非表示にできる。非表示のあいだは次のとおり
  - 「修正案 N」と一覧に入れず、先議の数（`priorVoteCount`）にも入らない
  - 賛同、賛同の取り消し、投票、取り込み、更新ができない（403）。**賛同の取り消しも断る**（カードが見えないのに数が動かないように。投稿の評価の取り消しと同じ。STOP 1 で確認した）。賛同と票の行は残り、表示に戻すと数える
  - 書く文の条件にも入れる（確かめたあとに隠れても入らない）。**取り込みは版を進める文にも「対象の修正案が `open` で非表示でない」を入れる**（`advanceBill`。修正案の文だけが当たらず、隠れた本文が本案に入らないように）
  - 更新の画面（`/shusei/kaku?koushin=`）は欄を出さず理由を出す。送ると 403
  - **更新と通報**：通報は修正案に結び付け、更新しても残す（更新できるのは本案の版が変わったときの3週目だけで、通報を消せる抜け道にしないため）。`restored` は更新しても `restored` のまま自動では隠れず、通報は `/kanri` に出る。古い本文は持たないので、`/kanri` の行に「最後の通報のあとに本文が更新されました」と出す（通報の `revision` と比べる）
  - **出し直し**：新しく出すのはレート制限だけで、非表示の修正案を数えない。同じ本文を出し直すのは止めない（別の修正案として通報と運営の対応の対象になる）
- L. **会期の処理**：処理のときに非表示（`auto_hidden`・`hidden`）で `status` が `open` の修正案は採決しない（`inPriorVote` の条件に入れるので `unvoted` になる）。入っていた票は数えない。取り込み済みなどは変えない。結果が書かれたあとは、表示に戻しても採決はやり直さない。読んだあとに隠れて可決した場合は、決定Mと同じ（票の入ったあとの非表示）
  - 採決の期間に外せるのは、委員長か運営が理由を公開して行う操作だけ
  - **残る筋**：3週目の最後の24時間より前に3人の通報で自動で非表示になると、賛同を集める時期を逃す。会期のうちにだれも見なければ採決されない。運営が見るための時間として最後の24時間を残す（STOP 1 で確認した）
- M. **結果のあとの非表示**：取り込みや可決で本文に当たった変更と共同起草者は変えない（書き手の名前は共同起草者に出たまま。内容はすでに法案の本文）。結果のページの修正案の行（条と結果だけ）も変えない

### 運営の画面

- N. **`/kanri` に区画を足す**：「通報を受けた修正案」。自動で非表示が先、最後の通報が新しい順に100件。各行に法案の題名と修正案のタブへのリンク、条、本文、理由の欄、状態（表示の状態）、修正案の状態（取り込まれた、など）、通報の数（数に入るもの／入らないもの。決定Bと同じ式）、理由ごとの数、「その他」の説明、`restored` なら戻したあとの通報の数。`?amendment=<番号>` でそれを上に出す。形が違う、ない番号は 404。扱えない修正案は 100 件に絞る前に SQL で除く（`?amendment=` で指しても 404）
- O. **扱えない人**：自分の修正案、関わった法案（`involvedSql`）、同じ法案に修正案を出した人、同じ法案のどれかの修正案に賛同している人、委員長と理事は同じ法案のどれかの修正案に投票した人（対抗案を消せないように）。受け付けでも 403
- P. **操作**：`?/hideAmendment`（理由とメモ）、`?/restoreAmendment`（メモ）。確かめの順は、役職（404）→ 国（403）→ 入力（400）→ 存在（404）→ 自分のもの（403）→ 関わり（403）→ 状態（400）。移り変わりは `HIDEABLE`・`RESTORABLE`
- Q. **権限**：委員長と代行の理事は運営と同じ。委員長の役職で行った操作は「委員長の最後の操作」に数える（`bill_moderation_logs` を見ているので足すものはない）。代行の理事の操作は数えない

### 記録と通知

- W. **公開の記録**：`/unei` の区画の見出しを「法案の質疑と修正案への対応」に変え、修正案の行も出す（何か：修正案）。本文、書いた人、通報した人、番号は出さない
- X. **通知**：書いた人に `amendment_hidden`、`amendment_restored`。`target_id` は修正案の番号、`ref_id` は `moderation_changed_at`。文の題名は法案の題名、リンク先は修正案のタブ（`/houan/<番号>/shusei`）

## 決めたこと

1. **表**（`drizzle/0024_*.sql`。既存の表には `ADD COLUMN` だけ）：
   - `amendments` に `moderation_status`（NOT NULL、既定 `visible`）、`moderation_actor`、`moderation_actor_user_id`、`moderation_reason`、`moderation_note`、`moderation_changed_at`
   - `amendment_reports`：`post_reports` と同じ形（`amendment_id` は `amendments` への外部キー、`counted` は登録から24時間たっているかだけ、`revision` は通報したときの本文）。一意（`amendment_id`, `user_id`）。索引（`user_id`, `created_at`）。`reason` に CHECK
   - `bill_moderation_logs` に `amendment_id`（NULL 可。外部キーは付けない。付けると表が作り直されるおそれがある）
   - `amendment_votes` に索引（`amendment_id`, `user_id`）を足す（主キーの先頭が `session_key` で、委員長と理事の関わりの判定に使えないため）
   - トリガー `amendments_moderation_log`（手で書く）：`moderation_status` が変わったら同じ文の中で記録を書く。更新の文は `moderation_*` を全部書く。`schema.ts` に注意書きを足す

2. **ルール**（`src/lib/domain/`）：`AMENDMENT_SHOWN`、`autoHideClosesAt(voteAt)`（`voteAt - 24時間`。`acceptOpen` も同じ値を使う）、`inPriorVote` に `moderationStatus` を足す、`validateAmendmentAction`

3. **関わりの式**：`involvedSql` の利用者を値でも列でも渡せる形に変える（`string | SQL`）。`amendmentPartySql(user, role)`（`src/lib/server/amendment-moderation.ts`）は、`involvedSql` に、同じ法案の修正案を出したこと、同じ法案のどれかの修正案への賛同（委員長と理事は票も）を足した式。自動の非表示と `/kanri` の「数に入るもの」は同じ式 `countedReports` で数える（通報の `user_id` の列を渡し、票は見ない）

4. **読むところを直す**（`src` の `amendments` への参照を全部検索して洗い出した）：
   - `amendments.ts`：`amendmentCount`、`listAmendments`、`priorVoteCount`、`castAmendmentVote` の文は `AMENDMENT_SHOWN`。`setAmendmentSupport` は入れる文に条件を足し、取り消しも非表示なら断る。`updateAmendment` の文に条件を足す。`acceptAmendment` は読んだ行と、`advanceBill` の版を進める文と修正案の文に条件を足す（`status` を渡すときだけ。可決した修正案を当てるときは足さない。決定M）。本文は新しい版の行に書くだけで、版が進まなければ読まれない（`saveDraft` と同じ）ので、条件が要るのはこの2文で、順は今のまま版を進める文が先。`settleAmendments` は `inPriorVote` で外れる
   - `amendment-actions.ts`：賛同、票、取り込み、更新の受け付けで、修正案の存在のすぐあとに非表示を確かめる（403）
   - `shusei/kaku/+page.server.ts`：更新の画面の `blocked`。非表示なら本文を返さない（断る場合も本文を返していたので、番号でほかの人が読めないように）
   - 直さないもの：`coDrafters` と `results.ts` の `priorAmendmentResults`（決定M。後者は条と結果だけで本文を出さない）、`votes.ts`（票の数え方。対象は `settleAmendments` が決める）

5. **操作**（`src/lib/server/amendment-moderation.ts`。`cloudflare:workers` に頼らない）：`amendmentCloseOf`（境の時刻）、`reportAmendment`（投稿の `reportPost` と同じ形で、境の時刻を受け取る）、`changeAmendmentModeration`、`reportedAmendments`、`reportedAmendmentIds`（番号を並べず法案で引く）、`hiddenAmendmentsFor`、`amendmentStaffAccess`、`staffOnAmendments`。`reportsInDay` は4つの表を数える。`billModerationLogPage` は `posts` を左結合にし、`amendment_id` があれば修正案とする（表は `post_id` が NULL 可で `bill_id` を直接持つ。`lastChairAction` はこの表だけを見るので、修正案の操作も数える。確かめた）

6. **通知**（`src/lib/domain/notifications.ts`、`notification-page.ts`）：`NoticeTarget` に `amendment` を足し、`targetOf`、`hrefOf`、`resolveTargets` を直す

7. **修正案のタブ**：`AmendmentCard` に通報（`PostReport` を、送り先と欄の名前と基準の文を受け取る形に広げて使う）と「運営として対応する」のリンク（`/kanri?amendment=<番号>`。自分のものと扱えない運営には出さない）。前の会期のカードにも出す。扱えるかは法案の単位で決まる（決定O。自分のものを除く）ので、`staffOnAmendments` の結果をタブ全体で使う。カードが出ていなければ、結果は一覧の上に出す

8. **文言**：`ja.amendment`、`ja.report`、`ja.kanri`、`ja.unei`、`ja.notifications`

## 範囲

- 入れる：上の決定のすべて
- 入れない：異議申し立て、通報した人への結果の知らせ、修正案の統合、表示に戻したときの採決のやり直し
