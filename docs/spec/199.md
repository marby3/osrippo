# 招待コード（設計書）

Issue #199。受入基準と決めたことは Issue #198 の「招待コード」の節と、#190 の決めたこと3。新規登録の入口（認証）に触れるので Careful。β のあいだだけ使い、v0.7 の PR で外す。

## 受入基準（#198 から写す）

1. 運営は `/kanri` で招待コードを作り、取り消せる。使ったかどうかの一覧が見える。運営のほかの人には見えない
2. 新規登録は、使っていない招待コードがあるときだけ通る。コードがない・使用済み・取り消し済みなら断り、ログインの画面に理由が出る
3. 1つのコードで登録できるのは1人だけ（同時に使っても1人）
4. すでにアカウントのある人は、コードなしでログインできる。ログインしていない人も、いままでどおり全部の画面を読める

## 範囲

- 入れる
  - 表 `invites`
  - `/login` の招待コードの欄
  - Better Auth の `user.create` の hook での確かめと使い切り
  - `/kanri` の「招待コード」の区画
  - テスト用ログインの登録の経路
- 入れない
  - β版のお約束への同意（#200。同じログインの画面に置くが、別の Issue）
  - 最初の運営アカウントの招待を入れる SQL（本番の公開 #203 の手順書に書く）

## 表

マイグレーションは足すだけ。

| 表 | 列 | 備考 |
| --- | --- | --- |
| `invites` | `code`（文字、主キー）、`created_by`（`user` への外部キー）、`created_at`、`used_by`（`user` への外部キー、NULL 可、一意）、`used_at`（NULL 可）、`revoked_at`（NULL 可） | 行そのものが記録になる。公開の記録（`/unei`）には出さない（使った人が分かってしまうため） |

## 決めたこと

1. **コード**：`crypto.getRandomValues` で作る英大文字と数字の12文字。紛らわしい文字（0・O・1・I）は使わない。入力は前後の空白と大文字・小文字の違いを許してそろえる
2. **ログインの画面**（基準2・4）
   - Google と LINE のボタンの上に「招待コード（はじめての方）」の欄を置く。すでにアカウントのある人は空のままでよい
   - action は、いまの順（国 → Turnstile）のあと、コードが入っていれば形だけ確かめる（使えるかは見ない。使えるかを外から試せないように）
   - 形が合えば、HttpOnly・Secure・SameSite=Lax・Path=`/`・10分の Cookie `invite` に入れてから、提供元へ送る
   - 形が違えば、Cookie を入れずに `fail(400)` で欄の下に理由を出す
3. **確かめと使い切り**（基準2・3）
   - `databaseHooks.user.create.before` で、`getRequestEvent().cookies` の `invite` を読む。この hook は新規登録のときだけ動き、すでにアカウントのある人のログインでは動かない（Better Auth 1.7.15 は、提供元とアカウントの id で既存の人を見つけると user を作らない。`node_modules/better-auth/dist/oauth2/link-account.mjs:80`）
   - アカウントのつなぎ込みは切っている（`src/lib/server/auth.ts` の `accountLinking`）ので、Google で登録した人が LINE で入ると、新規登録として扱われ、コードが要る。#198 の決めたことのとおり、そのときは2つ目のコードを使う
   - 要求の外で呼ばれた（`getRequestEvent()` が投げる）ときは、登録を断る。いまは要求の外で Better Auth の user を作る場所はない（取り込みやシミュレーションは Better Auth を通らない）
   - Cookie がない、またはそろえたあと空なら、更新の文を流さずに `APIError` を投げる
   - 次の1文で使用済みにする：`UPDATE invites SET used_at = ? WHERE code = ? AND used_at IS NULL AND revoked_at IS NULL`。変わった行が1なら通す。0なら `APIError`（`invite_required`）を投げる
   - `new APIError('FORBIDDEN', { code: 'invite_required', message: … })` を投げる。Better Auth 1.7.15 は、コールバックの中のエラーを `errorCallbackURL`（ログインの action で `/login?error=1` と渡している。これを `/login` にする）へ `error=<code>` を付けて送る（`node_modules/better-auth/dist/api/routes/callback.mjs:151-153`）。ログインの画面はこれを見て「招待コードが使えませんでした。コードを確かめてください。」を出す
   - `user.create.after` で、`used_by` に新しい user の id を書き、Cookie を消す
   - 使用済みにしたあと user の作成に失敗すると、コードは使われたままになる（表示名の振り直しが5回重なったときなど、まれ）。運営が作り直して渡す
4. **必須かどうか**：コードの定数 `INVITE_REQUIRED = true`（`src/lib/domain/invites.ts`）で持ち、v0.7 の PR で `false` にする。環境変数にはしない（入れ忘れで開いたままにならないように。#190 の決めたこと7と同じ考え）
5. **運営の画面**（基準1）
   - `/kanri` に「招待コード」の区画を足す。出すのは、運営（`canVerify(role)` が真。`operator` だけが真になる。`src/lib/domain/verification.ts:48`）だけ。運営協力者（`moderator`）には出さない
   - 操作は「作る」（1回に1〜20個）と「取り消す」（使っていないものだけ）。確かめの順は、いまの認証の操作（`verifierOf`）と国の制限にそろえる
   - 一覧は新しい順で、次を出す
     - コード
     - 作った日
     - 状態（使っていない／使った日／取り消した日）
   - 使った人の名前は出さない
6. **テスト用ログイン**
   - いまの `/test-login` は user を直接書くので、hook を通らない。これまでのテストと `pnpm simulate` は、いままでどおり招待なしで動く
   - 新しく `signup=1` の引数を足す。このときは、`name` で決めたメールの人がまだいなければ、Better Auth の `testUtils` の `saveUser` で作る（`internalAdapter.createUser` を通るので hook が動く。`node_modules/better-auth/dist/plugins/test-utils/db-helpers.mjs:5`）。作れたら、いまと同じくその人でログインする。hook が断ったら、本物と同じ `/login?error=invite_required` へ送る。これで、ログインの画面で入れた Cookie を使った登録を、画面のテストで確かめられる
   - 本番とステージングにはテスト用ログインがない（`TEST_LOGIN` とホストの確かめはいまのまま）
7. **画面の言葉**：すべて `src/lib/copy/ja.ts`

## テストの方針

テストは受入基準ごとに1本と、信頼の境界（ログインの画面のコードの欄）の形の違う入力の1本で、合わせて5本。画面のテストは、ほかの画面のテストと同じく 390px と 1280px の2つのプロジェクトで回る（1本のテストを2幅で流すだけで、本数は増やさない）。下の箇条は、それぞれ1本のテストの中の手順。

- 基準1（画面）：運営が `/kanri` でコードを3つ作る。1つを取り消し、1つを `/login` と `/test-login?signup=1` で使う。一覧に「使っていない」「使った日」「取り消した日」が出る。運営協力者には区画が出ず、作る操作を送ると断られる
- 基準2（画面）：コードを入れて登録すると通る。同じコードで別の名前の人がもう一度登録すると `/login?error=invite_required` に戻り、理由が出る。コードなしでも同じく断られる
- 基準3（DB）：同じコードで使用済みにする関数を2回呼ぶと、1回だけ通る
- 基準4（画面）：アカウントのある人がコードなしで `/test-login?signup=1` から入れる（作らないので hook は動かない）。ログインしていない人がホームと課題の一覧を開ける。本物の提供元の経路は画面のテストで通せないので、既存の人で hook が動かないことは Better Auth の作り（上の引用）に頼る
- 形の違う入力（画面）：コードの欄に13文字や記号を入れると、Cookie が入らず400で理由が出る
