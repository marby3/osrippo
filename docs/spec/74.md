# 現実の改正の同期（設計書）

Issue #74。条文の内部IDと版を書き換え、外部の API を呼ぶので Careful。マイグレーションはない。仕様の正は [docs/spec.md](../spec.md) の「法令同期」「重いバッチ」「現実の改正の取り込み」。法令の版は [docs/spec/8.md](8.md)、IF世界は [docs/spec/72.md](72.md)。取り込み、衝突、一覧のページ、#55 は #95。

仕様のとおりにすること：法令の同期は**自宅サーバー**で毎日（Worker と Cron は e-Gov を呼ばない）。止まってもサービスは止まらない。会期中に IF世界の条文は変わらない（同期は現実の版だけを進める）。

ユーザーと決めたこと（#74 の STOP 1）。

- A. **IF世界が指した版（固定の版）までは変えず、それより後は作り直す**。公布と施行の順が逆の改正は普通に起こり（テストデータの対象3法の52版のうち14か所）、そのとき e-Gov 側でも後ろの版の中身が変わるので、追記だけでは正しくならない
- B. **固定の版より前に新しい版が来たら、履歴に入れず飛ばして続ける**（登録の遅れ。次の版の全文に中身が含まれるので、**次の版が入れば条文は正しくなる**。次の版が来るまで、その改正は現実の法令ページに出ない。履歴の1行は欠け、変わった条は次の版の変更として出る。飛ばしたことは入口が警告に出す）
- C. **現実の法令の廃止は扱わない**：API が廃止を返したら（`repeal_status` が `None` でない）、その法令の同期を止める

## 目的

現実の改正を毎日 DB に入れ、現実の法令ページをいまの法律に保つ。

## 範囲

- 入れる：`src/lib/egov/`（API の呼び出しと応答の確かめ）、続きから作る履歴、同期、入口のスクリプト
- 入れない：IF世界への取り込み、衝突、#55（#95）。本番の D1 につなぐこと、自宅サーバーへの設置、タイマー、失敗の通知（デプロイの Issue）。2017年より前の履歴、公開ミラー

**固定の版**：この Issue では分岐した版（`if_branches`）。#95 で「分岐した版と取り込んだ版のうち最後の版」に広げる。内部IDを指すのは `provision_versions` のほかに `bill_changes`・`amendments`・`if_added_articles`、版を指すのは `provision_versions` のほかに `bill_laws.base_revision_id`・`if_branches` で全部（マイグレーションで確かめた）。`bill_changes`・`amendments` が指す内部IDは IF世界の条（＝固定の版までの条）だけ、`bill_laws`・`if_branches` が指す版は分岐した版だけなので、それより後は変えてよい。`if_added_articles` の内部IDは `provision_versions` の行を持たないので作り直しの対象にならない。`hikaku` の URL は版の番号なので、版が消えない限り変わらない。画面に内部IDは出ない。

## 決めたこと

1. **API**（`src/lib/egov/client.ts`）：`https://laws.e-gov.go.jp/api/2/law_revisions/<法令>` と `.../law_data/<版>`。形はテストデータと同じ（手元で1回確かめた）。呼び出しは `FetchJson`（URL を受けて JSON を返す関数）で受け、本物は30秒まで（`AbortSignal.timeout`）で HTTP の失敗は例外、テストはテストデータを渡す。番号は `encodeURIComponent` を通す

2. **応答の確かめ**（信頼の境界。同じファイル）：一覧は `revisions` が配列で各行に `law_revision_id` があること。**固定の版と、それより後の版**について、`law_title` が文字列、`law_title_kana` が文字列か NULL、`amendment_enforcement_date` が日付の形（「政令で定める日」の版も上限の日付が入る。テストデータ89版で確かめた）、`current_revision_status` が `CurrentEnforced`・`PreviousEnforced`・`UnEnforced` のどれか、`repeal_status` が `None`。本文は `revision_info.law_revision_id` が求めた版と同じ、`law_full_text` の根が `Law`、条が1件以上。違えば例外（その法令の同期が止まる）。固定の版より前の古い版の値では止めない。状態の対応は `src/lib/egov/revision.ts` に置いて `seed.ts` と共有する（`seed.ts` は Worker からも読むので、e-Gov を呼ぶ `client.ts` に届かないように）

3. **続きから作る履歴**（`extendHistory(start, revisions, { nextId })`。`src/lib/domain/law/history.ts`）：`start` は起点の版の番号と、**DB の行の形**（`provisionsAt` の戻りの `id`・`kind`・`parentId`・`num`・`caption`・`text`）。そこから条・項・号の木を**番号の順（`compareNum`。条文の並びと同じ）で**組み立てて `buildHistory` と同じ処理を続ける。戻り値は `provisions`・`versions`・`nextId` と、起点の行を閉じる `closes`（`provisionId`・`toRevisionId`）。`buildHistory` は同じ本体を共有する

4. **同期**（`syncLaw(db, lawId, fetchJson)`。`src/lib/server/law-sync.ts`）
   戻り値は `changed`（作り直したか）と `skipped`（飛ばした版）。
   1. 分岐を固定する（`ifBranchOf`。現実の版が進む前に）。これが固定の版
   2. 版の一覧を読み、**逆にして**古い順にする（同じ施行日の順は一覧の位置で決まる。日付で並べ直さない）
   3. 一覧で固定の版の位置を探す。**ないか、状態が施行済み（`CurrentEnforced`・`PreviousEnforced`）でなければ止める**（例外）
   4. 固定の版より後のうち、DB で固定の版以前にある版を除いたものを「作るべき末尾」とする。固定の版より前で DB にない版は飛ばす（決定B）。戻り値に飛ばした版の番号を入れ、入口が警告に出す
   5. DB の固定の版より後の版と、版の番号と状態（`enforced`・`scheduled` にまとめた値）の列が同じなら、題名だけ見て終わる。だから施行予定の版の中身は、次に作り直すまで前のまま。**施行済みになるときには必ず読み直す**ので、施行された版の中身はその時点の e-Gov と同じになる
   6. 違えば、末尾の版の本文を**先に全部読む**（読めなければ DB に触らない）。起点の行は `provisionsAt`。消す内部IDも先に読む（`from_revision_id` が古い末尾の行があり、それより前の行のない内部ID）。**全文を読んだあと、batch の直前に**内部IDと行の番号の `MAX` を読み、`extendHistory` を走らせる
   7. **1つの法令を1つの `db.batch`** で入れ替える。順は、古い末尾の検索の行 → 行（`from_revision_id` が末尾）→ 閉じた印を戻す（`to_revision_id` が末尾なら NULL）→ 末尾だけの内部ID（`json_each` で1文。親子は同じ文で消す）→ 古い末尾の版 → 新しい版 → 起点の行を閉じる → 内部ID → 行 → 検索の行 → 題名。途中で失敗すれば入れ替えは何も変わらず（1の分岐の固定は残る）、次の日にやり直す
   - 内部IDと行の番号はこの batch だけ DB の `MAX + 1` から振る（木を先に作るため）。内部IDは `extendHistory` の `nextId` で振り、行の番号は入れるときに振る。読むときの反映は内部IDを DB に採番させるので、反映の側は失敗しない。`MAX` を読んでから batch までに反映が入れば、同期の batch が失敗し、次の日にやり直すだけで壊れない。D1 の1文の値の上限（100個）に合わせて文を分ける。内部IDは作った順（親が先）に入れる。D1 の batch は値つきの `db.run` を受け付けないので、検索の表も builder で書く（メモリの DB では動くので、テストでは気づかない。`pnpm sync:laws` を手元の D1 で動かして確かめた）
   - 題名と読みは、一覧の**施行済みの最新の版**から取る（`seed.ts` と同じ）。法令の題名は1つで、IF世界の画面も同じ題名を出す
   - `law-sync.ts` と `client.ts` は Cron と同じく、`cloudflare:workers`、`import.meta.env`、`#lib` に頼らない

5. **入口**（`scripts/sync-laws.ts`、`pnpm sync:laws`）：`getPlatformProxy` で手元の D1 の binding を受ける（`db.batch` が Worker と同じ）。`laws` の全部の法令を順に同期する（`syncAll(db, fetchJson)`）。法令ごとに失敗を受け止めて続け、1つでも失敗すれば終了コード1で終わる。`--persist-to` で D1 の場所を変えられる。**本番の D1 につなぐ引数はここでは作らない**（本番の D1 がなく確かめられない。デプロイの Issue で足す）。Worker のサーバーと同時に手元の D1 を開かない（Issue #17）
