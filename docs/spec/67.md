# 評価（筋が通っている・考えが変わった）と評価スコア（設計書）

Issue #67。マイグレーション（表と列の追加）を足すので Careful。仕様の正は [docs/spec.md](../spec.md) の「質疑と評価」と「評価スコアの計算」。画面は `SpBillQA`・`PcBillQA`。質疑のタブは [docs/spec/66.md](66.md)。

ユーザーと決めたこと（Issue #63。仕様書のドキュメントへの反映はユーザー側）。

- 3秒以上画面に出たか、展開したら「読んだ」とする（決めたこと13）
- 同じ相手への評価でスコアに数えるのは1会期3件まで（決めたこと13）
- 答弁のあるカードのボタンは答弁の評価、答弁待ちのカードは質疑の評価（テストの作り方）
- 考えと評価のボタンは `aria-pressed` で押した状態を示す（テストの作り方）

次のことは仕様書にないので、この Issue の受入基準で確かめる（STOP 1 で確認する）。

- A. 答弁が2件以上あるカードは、答弁ごとに1組のボタンを出す（1件のカードは案のとおりカードに1組）
- B. 押せるのは、登録から7日たった人。Turnstile は要らない。自分の投稿には押せない。提出者と賛同者も、ほかの人の投稿には押せる
- C. 押した評価は取り消せる。押し直すと、押した時点の立場で記録し直す
- D. 押せる時期と読んだ記録を取る時期は、3週目から採決の締切まで
- E. 読む前に押したら、読んだことにする。読んだあとで考えを変えて押した人は、評価の立場の「読んだ人」に数える
- F. 投稿者の立場は、書いた時点の立場で固定する。ただし答弁を書いた時点で未定なら、賛成寄りとして扱う（提出者と賛同者は法案を支持しているので）
- G. 投稿者が未定のときも、未定の人を数える（仕様の式のとおり2グループ）
- H. 「考えが変わった」は立場を問わず数え、スコアに混ぜず別の数で持つ。実績への足し方はフェーズ5
- I. 同じ相手の上限は、法案をまたいで同じ会期で数え、種類ごとに3件。超えた分は、評価にも読んだ人にも数えない
- J. スコアも押された数も画面に出さない（案のカードに数がない）。スコアを画面に出すのはフェーズ5の実績

## 目的

質疑と答弁に評価を付けられるようにし、読んだ記録と評価から評価スコアを計算できるようにする。

## 範囲

- 入れる：表、評価のボタン、読んだ記録、スコアの計算、レート制限、PC の説明文（案の「考えが違っても、筋が通っていると思えば…」）
- 入れない：スコアの画面（フェーズ5）、実績の計算（フェーズ5）、評価と読んだ記録の統計（フェーズ5。10人未満の区分を出さない決まりと一緒に）、通報で非表示にした投稿の評価の扱いの見直し（#80）、議員アカウントが評価できないこと（フェーズ5）

## 表

`drizzle/0013_*.sql`（`drizzle-kit generate`）。既存の表は `posts` に列を足すだけで、作り直さない。generate のあとに SQL を読み、`ALTER TABLE ... ADD` と `CREATE` だけであることを確かめる。

| 表 | 列 | 備考 |
| --- | --- | --- |

## 決めたこと

1. **ボタンの出し方**（`QuestionCard.svelte`）
   - 評価できるのは質疑と答弁だけ。補足には出さない（仕様「評価スコアの対象は法案の質疑と答弁に限る」）
   - 答弁待ちのカード：質疑の評価を1組
   - 答弁が1件のカード：答弁の評価を1組。スマホでは案のとおり、開閉の外に置く（閉じていても押せる）。閉じたまま押したら、評価した答弁が読めるように開く
   - 答弁が2件以上のカード：答弁ごとに1組。スマホでは開閉の中に置く
   - 答弁がついたあとは質疑のボタンを出さない。それまでに押した質疑の評価は残り、スコアにも数える
   - 自分の投稿にはボタンを出さない（`load` が質疑と答弁のそれぞれに `mine` を返す）
   - ログインしていなければ、押すとログインへ（戻り先は今の絞り込みとページ）
   - 登録から7日たっていない人と、時期の外には出さない
   - 押された数は出さない。見ている人の押した状態（`aria-pressed`）だけを返す
   - PC は、右の列の「質疑を書く」の下に案の説明文を出す。スマホは案にないので CSS で隠す
2. **押す・取り消す**（`?/evaluate`。`evaluationAction`）：フォームの値は `post`（番号）、`kind`、`op`（`add`・`remove`）。押した状態を読み直して反転させるのではなく、画面の状態を送る（2つのタブで押しても、見ていた状態のとおりになる）
   - 確かめの順：法案の番号と存在（ない・下書きは 404）→ ログイン（なければログインへ 303）→ 国 → 締め出し（`writeGuard`）→ 登録から7日（403）→ 入力（形が違えば 400）→ 時期（409）→ 投稿（404）→ 自分の投稿（403）→ レート制限（429）→ 保存
   - 投稿は、同じ法案の同じ会期の、`kind` が質疑か答弁で、`status = 'visible'` の行。違えば 404
   - ページを開いたあとで答弁がつくこともあるので、答弁のある質疑への評価も受け付ける
   - 保存：`add` は読んだ行（決めたこと4）を足してから、次の1文で評価を足す。立場を別に読まないので、立場を変えるのと重なっても、どちらかの立場で1行だけ残る。`remove` は行を消す。読んだ行は消さない

     ```sql
     INSERT INTO evaluations (post_id, user_id, kind, stance, created_at)
     SELECT ?, ?, ?, COALESCE((SELECT stance FROM stances WHERE session_key = ? AND bill_id = ? AND user_id = ?), 'undecided'), ?
     WHERE true
     ON CONFLICT DO NOTHING
     RETURNING post_id
     ```

   - 記録（`evaluation_add`・`evaluation_remove`）は行が変わったときだけ足す。`target_id` は投稿の番号（同じ投稿に同じ回線から押した数を数えるため）。今月の参加者に数えるのは `evaluation_add` だけ（#65 のとおり）
   - 失敗したら、そのボタンの下に理由を出す（`role="alert"`。失敗の応答に投稿の番号を入れて返す）
3. **レート制限**（`checkEvaluation`。`limits.ts`）：「わかる」と同じ数を別枠で持つ。1アカウント24時間に50回、5分に10回（付けるのも取り消すのも1回）。同じ投稿に同じ回線から付けられるアカウントは3つまで（解決策の反応と同じく、24時間のうちに自分が付けたことのある投稿は数えない）。アカウントの上限は違反に数え、回線の上限は数えない
4. **読んだ記録**
   - 「画面に出た」は、投稿の要素の半分以上が画面に入っていること（`IntersectionObserver`、しきい値 0.5）。続けて3秒で読んだことにする。途中で画面から外れたら数え直す。タブを切り替えて隠れているあいだは数えない（`document.visibilityState`）
   - 「展開」は、スマホの「答弁を読む」を開いたとき。カードの答弁をすぐに読んだことにする
   - 記録するのは、ログインしていて、登録から7日たっていて（押せない人を分母に入れないため）、時期の中で、自分の投稿ではないとき。画面はその条件のときだけ送り、サーバーも確かめる
   - 送り方：読んだ番号をためて1秒ごとに `?/read` へ送る（`fetch`。`x-sveltekit-action: true`、`keepalive: true`）。同じページで同じ番号を2回送らない。読み直して送っても行は増えず、立場も変わらない
   - `?/read` の確かめの順：法案の番号と存在（404）→ ログイン（401）→ 国 → 締め出し → 登録から7日（403）→ 入力（`post` が1〜50個の番号でなければ 400）→ 時期（409）→ 保存。応答は画面に出さない。失敗しても黙って捨てる（評価を押せばそのとき読んだことになる）
   - 保存は次の1文。番号はこの法案の見える質疑と答弁に絞り、自分の投稿を除く。ほかの番号は黙って無視する（D1 の1文の値の数の上限に収めるため、番号は JSON の1つの値で渡す）

     ```sql
     INSERT INTO post_views (post_id, user_id, stance, created_at)
     SELECT p.id, ?, COALESCE((SELECT s.stance FROM stances s WHERE s.session_key = p.session_key AND s.bill_id = p.bill_id AND s.user_id = ?), 'undecided'), ?
     FROM posts p
     WHERE p.bill_id = ? AND p.session_key = ? AND p.kind IN ('question', 'answer') AND p.status = 'visible' AND p.user_id <> ?
       AND p.id IN (SELECT value FROM json_each(?))
     ON CONFLICT DO NOTHING
     ```

   - レート制限は掛けない。行は1人1投稿に1行で増えず、`actions` にも足さない（閲覧は今月の参加者に数えない。#63）
5. **評価の立場**：押した時点の立場で固定する。あとで考えを変えても行は変わらない。行がなければ未定
6. **投稿者の立場**（`postStance(kind, stance)`。`src/lib/domain/evaluations.ts`）：`createPost` が書いた時点の立場を `posts.stance` に入れる。答弁を書いた時点で未定なら賛成寄り。提出者と賛同者が反対寄りを選んでいれば、そのまま
   - あとで考えを変えても `posts.stance` は変わらない（書いたあとで立場を変えてスコアを動かせないように）
7. **スコアの計算**（`postScores(posts, views, evaluations)`。`src/lib/domain/evaluations.ts`。純粋な関数）：α = 5。読んだ人が3人未満の判定はグループごとに行う
   1. **数える評価**：`reasonable` のうち、投稿者と違う立場か未定の人のもの（投稿者が未定なら全員）。押した時刻の古い順（同じ時刻は投稿の番号順）に並べ、同じ人から同じ投稿者へは会期で3件まで。超えた分を「上限の外」とする
   2. **読んだ人**：`post_views` の行を、評価（上限の外も含む）を押した人はその立場、ほかの人は読んだ立場に分ける。投稿者本人の行と、上限の外の人の行は除く。評価の行があって `post_views` の行がなければ（押したときに足すので、ふつうは起きない）、読んだ人に足す
   3. **p0**：法案ごとに、数える評価の合計 ÷ 読んだ人の合計。数えるのは投稿者と同じ立場を除いた人（投稿者が未定なら全員）。読んだ人がいなければ 0
   4. **割合**：`r_g = (e_g + α p0) / (n_g + α)`
      - 投稿者が賛成寄りなら、相手側は反対寄り。反対寄りなら賛成寄り
      - 投稿者が未定なら、`r_opp` は賛成寄りと反対寄りの `r` の平均、`n_opp` はその人数の合計
   5. **スコア**：`(n_opp r_opp + n_und r_und) / (n_opp + n_und)`。`n_opp` も `n_und` も3人未満なら `null`（評価不足。0点にしない）
   6. **考えが変わった**：`changed` を、立場を問わず、同じ人から同じ投稿者へ会期で3件まで数えた数。スコアに足さない
   - 仕様の計算例（0.28、0.19）を単体テストで確かめる
8. **会期の分を読む**（`sessionPostScores(db, sessionKey)`。`src/lib/server/evaluations.ts`）：上限が法案をまたぐので、会期の質疑と答弁（`status = 'visible'`）と、その読んだ行と評価の行をまとめて読み、`postScores` に渡す。返すのは投稿ごとの `score` と `changed` だけで、誰が押したかを返さない
   - この Issue では画面から呼ばない（フェーズ5の実績が呼ぶ）
   - 非表示の投稿は、スコアにも上限の数え方にも入らない。#80 で見直す
9. **本人にしか渡さない**：`load` は見ている人の評価の行だけを読む。ほかの人の評価・読んだ記録・立場を返さない。`evaluations` と `post_views` の `stance` は個人の考えに近いので、画面の `load` から読むのは見ている人の押した状態（`post_id` と `kind`）だけにする
10. **画面の言葉**：すべて `src/lib/copy/ja.ts`。登録から7日の案内は「質疑や答弁を書いたり、評価したりできます」に直す

## テストの方針

受入基準ごとに1本。フォームの信頼の境界に1本。

- 単体テスト（`src/lib/domain/evaluations.test.ts`）：計算例、同じ立場、投稿者が未定、評価不足、上限、考えが変わった、`postStance`
- DB のテスト（`src/lib/db/evaluations.test.ts`）：評価の立場の固定と押し直し、読んだ記録の立場と絞り込み、投稿者の立場、会期をまたいだ上限、`checkEvaluation`
- 画面のテスト（2幅。`e2e/hyouka.spec.ts`）：ボタンの出し方、押す・取り消す、読んだ記録（3秒、開く）、信頼の境界

読んだ記録の POST が増えるので、`e2e` で「次の POST を待つ」手順は `?/read` を除いて待つ形に直す。

## あとで決めること

- スコアの画面と実績（フェーズ5）
- 通報で非表示にした投稿の評価と読んだ記録の扱い（#80）
- 退会を入れるときの `post_views`・`evaluations` の扱い。立場を含むので、退会で消す方向（#66 の `stances` と一緒に）
- 修正案の取り込みで版が進むと、提出者と賛同者の答弁の扱いは変わらない（`posts.role` と `posts.stance` は書いた時点の値）。#68 で賛同者の定義を変えても影響しない
- 要調整で次の会期に審議するとき（#72）は、`session_key` ごとに分けて数える
