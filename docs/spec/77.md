# 委員長選挙と理事、解任動議（設計書）

Issue #77。マイグレーションがあり、運営の画面の権限と結果の確認に関わるので Careful。決定は Issue #63 の決めたこと16「立候補はその会期に質疑か答弁を1件以上書いた人。投票は1人1票で最多得票、同数はくじ。解任動議は今月の参加者の 20%、理事の代行は7日」。仕様は [docs/spec.md](../spec.md) の「委員長の選び方」。画面の案はない（`SpVote`・`PcVote` にそろえる）。

仕様のとおりにすること：次の会期の委員長は前の会期の4週目に選挙で決める。立候補制。初回の会期は委員長を置かず、運営が事務局として行う。任期は1会期で、連続は2会期まで。次点を理事とする。運営は選任に関与しない。委員長の仕事は、質疑の整理、通報の一次対応、類似課題の統合、「確認中」法案の確認。

次のことは仕様書に定めがないので、この Issue の受入基準で確かめる（STOP 1 で確認する）。

### 選挙

- A. **時期**：立候補は4週目の前半、投票は4週目の全部（`voteAt`〜`endsAt`。法案の採決と同じ期間）。最後に立候補した人にも票が入る時間を残す。立候補は前半のあいだ取り下げられる。票は締切まで変えられる（法案の票と同じ）
- B. **立候補できる人**：その会期に、その委員会の法案に質疑か答弁を1件以上書いた人（非表示は数えない。決定16。**#80 で数え方を変えた。docs/spec/80.md の決定J**）。登録から7日、国、締め出し、Turnstile を確かめる。**連続して2会期務めた委員長は立候補できない**（いまの会期と前の会期の委員長。解任された任期も数える。解任された人も、この条件に当たらなければ立候補できる）。**運営と運営協力者は立候補できない**（仕様の「運営は選任に関与しない」。投票と署名も同じ）。あとで質疑が非表示になっても、立候補は取り消さない。仕様の「実績が一定以上」は、実績の計算がフェーズ5なので、決定16のとおりここでは見ない
- C. **投票できる人**：法案の数えた票と同じ資格（`isEligibleVoter`。「参考の票」はない。資格のない人には押させず理由を出す）。登録から7日、国、締め出し、Turnstile を確かめる。自分に入れてもよい。運営と運営協力者は投票できない。入れたあとで締め出された人の票は、法案の票と同じくそのまま数える。**1回線から同じ選挙に入れられるのは3アカウントまで**（課題の賛同の上限 `supportAccountsPerIp` と同じ数。回線の上限は違反に数えない）
- D. **結果**：最多得票が委員長、次の3人までが理事。1票以上入った候補だけで、確定までに運営か運営協力者になった候補は除く（仕様の「運営は選任に関与しない」）。**締め出されている候補は除かない**（締め出しは「24時間に違反3回で24時間」の一時的なもので、最後の1日の上限超えで1か月の任期を失うのは重すぎる。当選しても締め出しのあいだは権限がない。決めたこと4）。同数はくじ。候補がいないか票が0なら、次の会期は委員長なし（運営が事務局のまま）。公開するのは委員長と理事の名前だけで、得票数も合計の票数も順位も出さない（少ない票数で誰が入れたか推測できるのを避ける。理事は名前の順に出す）。立候補を取り下げると、その候補への票も消す（再び立候補しても古い票は戻らない。入れた人は投票のフォームが未投票に戻るので分かる）。結果は書き込んだら変えない。**選挙には「確認中」の経路がない**（使われ方を見て足す。STOP 1 で確認する）
- E. **確定**：会期の終わりの処理で（Cron と、委員会のページを読むとき）。締切から1分は処理しない（`SETTLE_GRACE`）。何度走っても同じ

### 委員長の権限

- F. **できること**：運営協力者と同じく、運営の画面（`/kanri`）の操作ができる。課題と解決策の非表示と表示に戻す、類似課題の統合、「確認中」法案の確認の4つで、`/kanri` の操作はこれで全部（確かめた）。非表示の課題と解決策を読めるのも運営協力者と同じ（`kadai/[id]`・`kaiketsu` の `staff`）。通報者の情報は今も運営に出していない。提出者や賛同者や本人の課題を扱えない決まりは今のまま。**自分の課題と解決策の行には、通報の自由記述を渡さない**（委員長はふつうの参加者なので、自分への通報の文面を読めると報復の材料になる。数と理由は今のまま。法案の確認で関わった人に数を渡さないのと同じ考え。運営と運営協力者にも同じく適用して決まりを1つにする）。運営と運営協力者の権限は変えない（委員長がいても運営は操作できる）。記録の `actor` は `chair` か `director` で、画面には「委員長」「理事」と出す
- G. **「質疑の整理」（似た質疑をまとめる）はこの Issue に入れない**：質疑の操作の記録の仕組みが要るので、質疑の通報と非表示（#80）と一緒に作る（#80 を分けたので #104）

### 解任動議

- H. **署名が今月の参加者の 20%（最低10人）に届くと解任する**（**仕様の「署名で解任動議を出せる」の読み替え**で、動議のあとの投票はしない。任期が1か月なので、投票を挟むと終わってしまうため。STOP 1 で確認する）。最低10人は定足数と同じで、参加者が少ない月に数アカウントで解任できないようにする。署名できるのは法案の数えた票と同じ資格の人で、登録から7日、国、締め出し、Turnstile を確かめる。委員長本人、理事、運営、運営協力者は署名できない。**1回線から同じ動議に署名できるのは3アカウントまで**（選挙の票と同じ）。解任の前なら署名を取り消せる。だれが署名したかは出さず、人数と必要な人数だけ出す。解任は元に戻せない。**解任にも「確認中」の経路がない**（STOP 1 で確認する）
- I. **解任のあと**は理事が代行する。理事がいなければ運営が事務局に戻る。解任された人は、その任期の委員長の権限を失う。結果の表示に「解任」と出す

### 理事の代行

- J. **委員長が7日何もしないと、理事が代行できる**（決定16）。「何もしない」は、任期の始まりか、委員長の最後の操作（`moderation_logs` に残る課題と解決策の操作と統合、`vote_reviews` の確認。委員長の役職で行ったものだけ）から7日。**委員長が締め出されているあいだは権限がなく、理事がすぐ代行できる**（締め出しが終わると戻る）。締め出された理事にも権限はない。理事は全員が同じ権限で、順位はない。委員長が操作すると代行は止まる（時刻から求めるので、状態を書き込まない）。代行の操作の記録の `actor` は `director`。7日たつ前の理事に権限はない

## 目的

委員会の参加者が委員長を選び、委員長が通報や確認中の法案を扱えるようにする。運営の負担を分ける。

## 範囲

- 入れる：立候補、投票、結果の確定、委員会のページ、解任動議、代行、`/kanri` の権限
- 入れない：質疑の整理（#104）、実績の計算（フェーズ5）、立候補の抱負、委員長への通知（#78）、新しい委員会を作ること（委員会は今1つ）、任期の途中の辞任（解任か任期の終わりまで。使われ方を見て足す）

## 決めたこと

1. **ルール**（`src/lib/domain/chairs.ts`。純粋な関数）：
   - `candidacyOpen(session, now)`：`voteAt <= now < voteAt + (endsAt - voteAt) / 2`（整数の時刻に切り捨て）。`electionOpen(session, now)`：`voteAt <= now < endsAt`
   - `electionResult(candidates, votes, random)`：得票の多い順、同数はくじ（`random` を受ける）。1票以上の候補だけ。返すのは順位つきの列
   - `DIRECTOR_MAX = 3`、`CHAIR_ACCOUNTS_PER_IP = LIMITS.supportAccountsPerIp`、`recallRequirement(participants) = max(10, ceil(participants * 0.2))`、`ACTING_AFTER = 7日`
   - `consecutiveLimit`：いまの会期と前の会期の両方で委員長（`role = 'chair'`。解任された任期も数える）なら立候補できない

2. **選挙**（`src/lib/server/chairs.ts`）：`standForChair`、`withdrawCandidacy`、`castChairVote`、`electionPage`。理由を出すために期間と資格と回線の上限を先に読み（期間の外 409、資格がない 403、運営 403、ない候補 409、回線の上限 429。上限は新しく入れるときだけで、票を変えるときは見ない。`voteLimit` と同じく先に読むだけ）、`castChairVote` は候補の行があることを書く文の条件に入れる（`INSERT ... SELECT ... ON CONFLICT DO UPDATE`。期間は受け付けの時刻で決まるので、文の条件には入れない）。`withdrawCandidacy` は候補の行と票を `db.batch` で一緒に消す。受け付けの順は、ログイン → 国 → 締め出し → 登録から7日 → Turnstile → 入力 → 期間 → 資格。取り下げと署名の取り消しは、ログイン → 国だけ（締め出された人も取り下げられる。賛同の取り消しと同じ）

3. **確定**（`settleElection(db, committeeId, session, now, random, minutes)`）：`now < endsAt + SETTLE_GRACE` なら何もしない。`chair_elections` に行があれば何もしない。候補の票を集計し、運営と運営協力者になった候補を除いて `electionResult` を求め、`chair_elections` の行と `chair_terms` の行（次の会期 `sessionAt(session.endsAt, minutes)` を任期にする）を `db.batch` で入れる（batch の中は builder。値つきの `db.run` は本物の D1 でだけ落ちる）。`chair_elections` の主キーで2回目の実行は何も変えない：`chair_terms` の文は `ON CONFLICT DO NOTHING`、同時に走って違うくじを引いても、先に入った行だけが残るよう、**`chair_terms` の文に「この会期の `chair_elections` の行の `settled_at` がこの実行の値」を条件に入れる**（同じ時刻の実行は順位の UNIQUE に当たって何も変えない）。呼ぶのは `runSessionEnd` の最後（取り込みのあと。確定の失敗で取り込みが飛ばされないように）と委員会のページの読み込み。Cron で失敗しても法案の処理と取り込みは止まらない（`causes` に積んで最後に投げ直す）。読み込みで失敗してもページは出す（`settleOnRead` と同じ）

4. **権限**（`chairPowerOf(db, userId, now, minutes)`。短い会期のキーで引くので `minutes` を受ける。`runSessionEnd` からも読むので `chairs.ts` の中では `sessionsAt` を使わない）：いまの会期の `chair_terms` を読む。
   - 締め出されている人は null
   - `role = 'chair'` で `recalled_at` が NULL なら `chair`
   - `role = 'director'` で、委員長が解任された、委員長が締め出されている、委員長の最後の操作（なければ任期の始まり）から7日たった、のどれかなら `director`
   - 最後の操作は、`moderation_logs`（`actor_user_id` が委員長で `actor = 'chair'`。課題と解決策の操作と統合）と `vote_reviews`（`decided_by` が委員長で `decided_role = 'chair'`）のうち、任期の会期の中で一番新しい時刻
   - `staffRoleOf(db, userId, now, minutes)`：`user.role` があればそれ、なければ `chairPowerOf`（運営は立候補できず確定でも除くので、当選のあとで運営になった人だけが両方に当たる。その人は運営の権限で動き、委員長の最後の操作には数えない）。`/kanri`（`staffOf`）、`kadai/[id]`、`kadai/[id]/kaiketsu` はこれを使う。`roleOf` を読むところは全部で3か所（確かめた）
   - `ROLES`（`user.role` の値）は変えない。`schema.ts` に `STAFF_ROLES = [...ROLES, 'chair', 'director']` を足し、`Role` の型と `decided_role` の enum と `decideReview` の `staff.role` をこれにする。`MODERATION_ACTORS` に `chair`・`director` を足す。どれも TypeScript の型だけで、SQL は変わらない。`ja.unei.actors` に足す
   - `/kanri` の `load` は、`mine` の行の `notes` を空で渡す（課題と解決策。`row.mine` の判定は今のまま）

5. **結果の確認**：`pendingReviews` と `decideReview` は `staff.role` をそのまま使う。関わりの判定（`involvedInBill`）は、委員長と理事に限って投票した法案も含める（票は非公開で、利害が外から見えないため。STOP 2 で確認済み）。運営と運営協力者は今のまま

6. **解任**（`signRecall`、`cancelRecallSignature`）：理由を出すために先に読み（委員長がいない、解任のあと 409。本人、理事、運営、資格がない 403、回線の上限 429）、署名の文の条件にも「解任されていない委員長の行があること」を入れる。署名の行と確定の文を `db.batch` で一緒に流す。確定の文：`UPDATE chair_terms SET recalled_at = ? WHERE committee_id = ? AND session_key = ? AND role = 'chair' AND recalled_at IS NULL AND (SELECT count(*) FROM recall_signatures ...) >= 必要な人数`。必要な人数は今月の参加者（`sessionParticipants`。会期ごとに固定）から求める。委員長がいないか解任のあとは署名できない（409）。取り消しは解任の前だけ

7. **ページ** `/iinkai`（ログインなしで読める。国の制限は書き込みだけ）：
   - いまの委員長と理事の名前（なければ「今月は委員長がいません。運営が事務局を務めています」）。解任されていれば「解任されました」、委員長の操作から7日たっていれば「理事が代行しています」（締め出しのあいだの代行は出さない。締め出しを推測させないため）。確定を待つあいだ（締切から1分）は「選挙の結果を集計しています」
   - 選挙の区画：期間の案内、候補の名前（質疑と答弁の数は出さない。匿名の投稿と結びつくため）、立候補と取り下げのボタン、投票のフォーム（自分の票が分かる。ほかの人の票は出さない）。候補の順は読むたびに混ぜる（上に並ぶ人が有利にならないように。テストと同じ順を頼らない）。`load` は名前と候補の行の番号だけを返し、`votes`・`rank`・`user_id`・`ip_hash` を渡さない（投票のフォームは候補の行の番号で指す）
   - 解任動議の区画：署名の人数と必要な人数、署名と取り消しのボタン
   - `noindex` を付ける（実在の利用者の名前が「委員長」「解任されました」と並ぶので、検索に載せない）。IF世界の条文は出さないので、帯は付けない。入口は採決の一覧（`/saiketsu`）と結果のページの「委員会」のリンク（全体のメニューは #85）

8. **受け付け**（`/iinkai` の `?/stand`・`?/withdraw`・`?/vote`・`?/recall`・`?/cancelRecall`）：Turnstile は `stand`・`vote`・`recall`。形が違えば 400

9. **文言**：`ja.chair`。`ja.unei.actors`、`ja.kanri` の説明を「運営と委員長」に直す
