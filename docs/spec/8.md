# 法令と版の DB（設計書）

Issue #8（予定）。Careful の Issue なので、受入基準より先にこの設計書をレビューに通す。仕様の正は [docs/spec.md](../spec.md) の「法令データとブランチ」「技術構成」。ここではフェーズ1に要る分だけを決める。

## 目的

法令ページ（改正履歴、条ごとの「何年変わっていないか」）と2時点の比較が、DB から読めるようにする。条・項・号には番号とは別の内部IDを振り、版をまたいで追えるようにする（Issue #6 の対応付けを使う）。

## 範囲

- 入れる：Drizzle のスキーマとマイグレーション、ローカル D1、テストデータ（`tests/fixtures/egov/`）から対象3法を入れる取り込み
- 入れない：e-Gov API からの毎日の同期（取り込みは毎回すべて作り直す）、IF世界の版、全文検索（フェーズ2）、本番とステージングの D1 の作成

## テーブル

| テーブル | 1行が表すもの | 主な列 |
| --- | --- | --- |
| `laws` | 法令 | `id`（e-Gov の law_id）、`title`、`title_kana`、`law_num` |
| `law_revisions` | 法令の版（改正1回分） | `id`（e-Gov の law_revision_id）、`law_id`、`branch`（今は `real` だけ）、`seq`（法令とブランチの中での古い順の番号）、`enforcement_date`、`status`（`enforced`／`scheduled`）、`amendment_law_title`、`amendment_law_num`、`amendment_promulgate_date` |
| `provisions` | 条・項・号そのもの（内部ID） | `id`（整数）、`law_id`、`kind`（`article`／`paragraph`／`item`）、`parent_id`（項→条、号→項） |
| `provision_versions` | 条・項・号の、ある版から次に変わるまでの中身 | `provision_id`、`from_revision_id`、`to_revision_id`（次に変わった版。今も有効なら NULL）、`num`、`caption`（条だけ）、`text`（項・号だけ。条は空）、`change`、`similarity`、`unconfirmed_of` |

`change` の値：

| 値 | 意味 | 「改正された」に数えるか |
| --- | --- | --- |
| `baseline` | 取り込みの起点の版（2017年4月1日時点で効力のあった版）から有効 | 数えない（「2017年4月より前から変更なし」） |
| `added` | その版で新しくできた | 数える |
| `amended` | その版で本文が変わった（条は、中の項・号のどれかが変わったときも） | 数える |
| `renumbered` | 本文は同じで、番号だけ変わった | 数えない |
| `unconfirmed` | 確認待ち（前の版に同じ番号があったが、似ている度合いが 0.5 未満）。`unconfirmed_of` に、その番号だった前の版の条・項・号を入れる | 数える（運営が確定するまで別の条） |

「なくなった」は行を作らず、前の行の `to_revision_id` を閉じる。

## 決めたこと

1. **版の中身は差分で持つ**：版ごとに全条をコピーせず、変わったときだけ `provision_versions` に行を足す。ある版の条文は `from.seq ≤ 版.seq < to.seq`（to が NULL なら上限なし）で引く。「最後に改正された日」は、`change` が数える値の行のうち最新の `from_revision` の施行日。
2. **版の順番**：施行日の古い順。同じ施行日の版が複数あるときは、e-Gov の改正履歴の一覧で後ろにあるほうを古いとみなす（一覧は新しい順に並んでいる）。この順を `seq` に入れる。
3. **起点の版**：2017年4月1日より前に施行された版のうち、いちばん新しい1つだけを起点として入れる（例：消費者契約法は 2016-10-01 の版）。それより前の版は入れない。
4. **施行予定の版**（e-Gov の `UnEnforced`）：版として入れ、`status = scheduled` にする。中身の行も作る。現在の条文や「何年変わっていないか」の計算には使わない。
5. **内部ID**：取り込みの順に振る整数。取り込みは決まった順（法令ID順 → 版の古い順 → 条・項・号の出てくる順）で行うので、同じデータからは何度作り直しても同じIDになる。画面には出さない。
6. **項・号の親**：項と号は、Issue #6 のとおり結び付いた親の中でだけ対応付けるので、親は変わらない。`parent_id` は `provisions` に持つ。
7. **置き場所**：版の列から行を作る部分は純粋な関数として `src/lib/domain/law/` に置く。それを SQL にしてローカル D1 に入れる部分は `scripts/` に置く。

## 取り込みの流れ（ローカル）

1. `drizzle/` のマイグレーションをローカル D1 に当てる（`wrangler d1 migrations apply --local`）
2. `scripts/` の取り込みが、対象3法の改正履歴と各版の本文を `tests/fixtures/egov/` から読み、版の順に Issue #6 の `parseLaw` と `alignArticles` で前後を対応付け、行を作って SQL に書き出す
3. その SQL をローカル D1 に流す（`wrangler d1 execute --local --file`）

`pnpm db:reset` で 1〜3 をまとめて行う。画面のテスト（Playwright）のサーバーは、起動の前にこれを実行する。

## テストの方針

- 取り込みで作った SQL とマイグレーションを、Node の `node:sqlite`（メモリ上）に流し、D1 と同じ SQL で確かめる（SQLite の方言は同じ）
- 往復の確認：各版について、DB から組み立て直した条・項・号が、その版の本文を `parseLaw` した結果と一致する

## あとで決めること

- IF世界の版：IF世界の版は `law_revisions.branch = 'if'` の版として足す想定。分岐した時点より後に現実側で閉じた行（`to_revision_id`）を IF世界の表示でどう扱うかは、フェーズ4の設計で決める
- 毎日の同期：今回の取り込みは毎回作り直す。公開後に作り直すと内部IDが変わりうるので、同期は追記だけで行う方式をフェーズ4までに別 Issue で決める
- 「削除」になった条：Issue #6 の決まりでは確認待ちになる。扱いを変えるかは別 Issue
