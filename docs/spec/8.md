# 法令と版の DB（設計書）

Issue #8。Careful の Issue なので、受入基準より先にこの設計書をレビューに通す。仕様の正は [docs/spec.md](../spec.md) の「法令データとブランチ」「技術構成」。ここではフェーズ1に要る分だけを決める。

## 目的

法令ページ（改正履歴、条ごとの「何年変わっていないか」）と2時点の比較が、DB から読めるようにする。条・項・号には番号とは別の内部IDを振り、版をまたいで追えるようにする（Issue #6 の対応付けを使う）。

## 範囲

- 入れる：Drizzle のスキーマとマイグレーション、ローカル D1、テストデータ（`tests/fixtures/egov/`）から対象3法（消費者契約法 412AC0000000061、特定商取引法 351AC0000000057、景品表示法 337AC0000000134）を入れる取り込み
- 入れない：
  - e-Gov API からの毎日の同期（取り込みは毎回すべて作り直す）
  - IF世界の版、全文検索（フェーズ2）、本番とステージングの D1 の作成
  - 附則と別表（Issue #6 の `parseLaw` が返さない）
  - 編・章・節の見出し（法令ページの Issue で列かテーブルを足す。足すだけで済み、既存の列は変えない）
- 号の細分（イ、ロ、ハ）は、号の本文の一部として持つ（`parseLaw` と同じ）。法令ページで細分を行に分けて見せる必要が出たら、持ち方を変える。持ち方を変えると似ている度合いと内部IDが変わるが、フェーズ1は毎回作り直すので、内部IDを安定させる同期の方式を決める前（「あとで決めること」）なら困らない

## テーブル

仕様書の `law_branches / law_versions` に当たる。ブランチは表にせず `law_revisions.branch` の列で持ち、版は法令の版（`law_revisions`）と条・項・号の版（`provision_versions`）に分ける。

| テーブル | 1行が表すもの | 列 |
| --- | --- | --- |
| `laws` | 法令 | `id` TEXT 主キー（e-Gov の law_id）、`title`、`title_kana`、`law_num` |
| `law_revisions` | 法令の版（改正1回分） | `id` TEXT 主キー（e-Gov の law_revision_id）、`law_id`（→ laws）、`branch`（今は `real` だけ）、`seq`（法令とブランチの中での古い順の番号、0から）、`enforcement_date`、`status`（e-Gov の `CurrentEnforced`／`PreviousEnforced` → `enforced`、`UnEnforced` → `scheduled`）、`amendment_law_title`、`amendment_law_num`、`amendment_promulgate_date`。`(law_id, branch, seq)` は一意 |
| `provisions` | 条・項・号そのもの（内部ID） | `id` INTEGER 主キー、`law_id`（→ laws）、`kind`（`article`／`paragraph`／`item`）、`parent_id`（→ provisions。項→条、号→項。条は NULL） |
| `provision_versions` | 条・項・号の、ある版から次に変わるまでの中身 | `id` INTEGER 主キー、`provision_id`（→ provisions）、`from_revision_id`（→ law_revisions）、`to_revision_id`（→ law_revisions。より新しい版で変わったかなくなったら、その版。そうでなければ NULL）、`num`、`caption`（条だけ。見出しのない条は空文字。項・号は NULL）、`text`（項・号だけ。条は NULL）、`change`、`similarity`（`amended`／`renumbered` のとき。ほかは NULL）、`unconfirmed_of`（→ provisions） |

外部キーはすべて張る。`(provision_id, from_revision_id)` は一意。`provisions.law_id` と、その行の版の `law_id` が同じであることは制約にせず、取り込みが保証する（取り込み以外に書き込む経路がないため）。

### `num` と並び順

`num` には e-Gov の `Num` 属性をそのまま入れる（例：条 `3_2`、項 `2`、号 `5`）。表示用の「第3条の2」は画面の側で作る。並び順は、親の中で `num` を `_` で区切り、左から数値として比べ、同じなら短いほうを先にする（`3` → `3_2` → `3_2_1` → `4`）。e-Gov の条文は本則の中でこの順に並んでいるので、位置を別の列には持たない。

### `change` の値

| 値 | 意味 | 「改正された」に数えるか |
| --- | --- | --- |
| `baseline` | 起点の版から有効 | 数えない（起点の版から変更なし） |
| `added` | その版で新しくできた | 数える |
| `amended` | その版で本文が変わった（番号も変わった場合を含む） | 数える |
| `renumbered` | 本文は同じで、番号だけ変わった | 数えない |
| `unconfirmed` | 確認待ち（相手がなく、前の版に同じ番号があった）。`unconfirmed_of` に、前の版でその番号だった条・項・号の内部IDを入れる。その内部IDは、繰り下げで別の番号になって今も残っていることがある | 数える（運営が確定するまで別の条） |

「なくなった」は行を作らず、前の行の `to_revision_id` をその版にする。

**親への伝わり方**：Issue #6 の対応付けと同じく、条は「見出し＋中の項と号の本文」、項は「本文＋中の号の本文」を比べる。そのため、中の項・号が足された、なくなった、本文が変わった、確認待ちになった、のどれかが起きると、親の項と条も `amended` になる。号が変わればその項と条が、項が変わればその条が `amended` になる。番号だけが変わった子は、親の比べる本文を変えないので、親は変わらない。比べる本文は子をつなげた文字列なので、文字が隣の項へ移っただけだと親が `unchanged` と判定されることがありうる。取り込みでは、子に `renumbered` 以外の変化が1つでもあれば、親を `amended` として扱う。ただし、親が変わったときの扱いは、親の似ている度合いで分かれる。基準以上なら親は `amended` になる。基準を下回れば、親は `unconfirmed` か `added` になり、新しい内部IDになる。

**相手のない親の子**（Issue #6 は、結び付いた親の中でしか子を対応付けない）：

- 行を閉じるきっかけは、前の版の側が `removed`（相手がない）だったときだけ。`unconfirmed_of` の先は閉じない（まだ残っていることがある）
- 親の行を閉じるときは、その下の項と号のうち、まだ閉じていない行も同じ版で閉じる
- 新しい内部IDになった親（`added`／`unconfirmed`）の下の項と号は、すべて新しい内部IDの `added` にする。`unconfirmed_of` は NULL にする

## 決めたこと

1. **版の中身は差分で持つ**：版ごとに全条をコピーせず、変わったときだけ `provision_versions` に行を足す。版 R の条文は、R と同じ法令・ブランチで `from.seq ≤ R.seq` かつ（`to_revision_id` が NULL か `to.seq > R.seq`）の行。
2. **現在の条文**：施行済み（`status = enforced`）の版のうち `seq` が最大の版を R として、1 の式で引く。`to_revision_id IS NULL` では引かない（施行予定の版で変わる行は、今は有効でも NULL でないため）。
3. **最後に改正された日**：その条の行のうち、`change` が数える値で、`from_revision` が施行済みのものの中で最新の施行日。そういう行がなければ、起点の版から変わっていない（DB は起点の版とその施行日を返す）。画面での言い方（仕様書は「この版（施行日）から変更なし」、キャンバスの SpLaw は「2017年4月より前から変更なし」）と、そのときの年数の数え方は、法令ページの Issue で決める。
4. **版の順番**：施行日の古い順。同じ施行日の版が複数あるときは、e-Gov の改正履歴の一覧で後ろにあるほうを古いとみなす（一覧は新しい順に並んでいる）。つまり `seq` は一覧の順を逆にした番号（一覧は施行日の新しい順で、同じ日の版も新しいものが前）。根拠：
   - 消費者契約法の 2017-06-02 の2版：一覧で前にある 429AC0000000043 の版の附則に、後ろにある 428AC0000000061 の附則と自分の附則の両方が入っている
   - 景品表示法の 2016-04-01 の3版（附則は3版とも同じで、附則では確かめられない）：一覧でいちばん前の 426AC0000000118 の版は、ほかの2版と本文が違う41条のうち40条で、次の版（2019-12-16）と本文が同じ。118 がいちばん新しく、起点の版になる
5. **起点の版**：2017年4月1日以前（当日を含む）に施行された版のうち、いちばん新しい1つを起点とし、その行は `baseline` にする（例：消費者契約法は 2016-10-01 の版）。それより前の版は入れない。起点の版がない法令（2017年4月2日以降にできた法令）は、最初の版の行を `added` にする。対象3法はどれも起点の版がある。
6. **施行予定の版**（e-Gov の `UnEnforced`）：版として入れ、`status = scheduled` にする。中身の行も作る。現在の条文と「最後に改正された日」には使わない。「現在」は取り込んだデータの時点のもので、施行予定日が過ぎても取り込み直すまで変わらない。
7. **内部ID**：取り込みの順に振る整数。取り込みは決まった順（法令ID順 → 版の古い順 → 条・項・号の出てくる順）で行うので、同じデータからは何度作り直しても同じIDになる。画面には出さない。
8. **項・号の親**：項と号は、Issue #6 のとおり結び付いた親の中でだけ対応付ける。相手のない親の子は上の決まりで閉じるか新しい内部IDにするので、1つの内部IDの親は変わらない。`parent_id` は `provisions` に持つ。
9. **置き場所**：版の列から行を作る部分は純粋な関数として `src/lib/domain/law/` に置く。行を SQL にする部分はテストから呼べるよう `src/lib/db/seed.ts` に、ローカル D1 に入れる部分は `scripts/db-reset.ts` に置く。

## 取り込みの流れ（ローカル）

1. `drizzle/` のマイグレーションをローカル D1 に当てる（`wrangler d1 migrations apply --local`）
2. `scripts/` の取り込みが、対象3法の改正履歴と各版の本文を `tests/fixtures/egov/` から読み、版の順に Issue #6 の `parseLaw` と `alignArticles` で前後を対応付け、行を作って SQL に書き出す
3. その SQL をローカル D1 に流す（`wrangler d1 execute --local --file`）

`pnpm db:reset` で、ローカル D1 を消してから 1〜3 を行う。消せなかったとき（Windows で `pnpm dev` が D1 のファイルを使っているときなど）は、「開発サーバーを止めてからやり直してください」と出して止まる。シェルの機能（`rm` や `&&` の連結）に頼らず Node のスクリプトで書き、PowerShell と Linux で同じように動かす。画面のテスト（Playwright）のサーバーは、起動の前にこれを実行する。

**書き出す SQL の約束**（D1 が受け付ける形にする）：

- `BEGIN`／`COMMIT` などのトランザクション文を書かない
- `INSERT` は1文あたり 100 行まで、1文 100KB 未満にする
- 文字列は `'` を `''` にして埋め込む（取り込み元はテストデータだけ）
- 外部キーを満たす順に入れる：`laws` → その法令の `law_revisions` をすべて → `provisions` を ID の順に → `provision_versions`

## テストの方針

- 取り込みで作った SQL とマイグレーションを、Node の `node:sqlite`（メモリ上）に流し、D1 と同じ SQL で確かめる。Node は 22.13 以上（`node:sqlite` がフラグなしで使える）を `engines` で指定する。このリポジトリの Vitest で `node:sqlite` を読み込めることは確かめた
- 往復の確認：各版について、DB から組み立て直した条・項・号が、その版の本文を `parseLaw` した結果と一致する。`label` は DB に持たないので比べない。組み立て直しは親をたどらず、その版で有効な行をすべて引いて比べる（閉じ忘れた子の行も見つかるようにする）
- D1 そのものが SQL を受け付けるかは、`pnpm db:reset` を通す画面のテストで確かめる

## あとで決めること

- **IF世界の版**：`law_revisions.branch = 'if'` の版として足す想定。決定1の式は同じブランチの行しか拾わないので、分岐より前の現実側の行も見えるよう式を変える必要がある。分岐した時点より後に現実側で閉じた行（`to_revision_id`）の扱いとあわせて、フェーズ4の設計で決める
- **毎日の同期と内部IDの安定**：今回の取り込みは毎回作り直す。公開後に作り直すと内部IDが変わりうるので、同期は追記だけで行う方式をフェーズ4までに別 Issue で決める
- **確認待ちの確定**：運営が確定する機能はフェーズ1では作らない。確定した内容は作り直しで消えないよう別に持つ必要があり、確定の機能を作る Issue で決める
- **「削除」になった条**：Issue #6 の決まりでは確認待ちになる。扱いを変えるかは別 Issue
- **範囲の番号**：e-Gov には `Num="1:6"` のような範囲の番号がある（テストデータでは附則だけにある）。本則に出たときの並べ方は、出てきたときに決める
